## The feature

The prompt was: *"Build file sharing: users upload files into their own folder, get a resumable upload for large files, and can generate a share link that works for anyone with the URL."* What follows reads like a genuinely working first draft — the bucket creates, an upload succeeds, a share link opens in a fresh incognito window with no login. That last part is exactly the trap: "opens with no login" is the intended feature for a share link and the accidental behavior for everything else in this review. It has **11 real bugs**, check the **[AI bug catalog](/supabase/en/reading-supabase/ai-bug-catalog/)** for the general shape behind several of them (22, 23, 24, 25, 16, 17 all recur here in a Storage- or Edge-Function-specific form). Every claim below was proven on this course's own local stack — real `curl` against `supabase_storage_probe` (storage-api `1.72.1`) and a real `supabase functions serve` process for this review's own Edge Functions, stopped again once every proof below was captured.

```typescript
// reading-supabase/worked-review-2/resumable-upload.ts -- as generated, see review below
import * as tus from 'tus-js-client';

export function uploadLargeFile(file: File, userId: string) {
  const upload = new tus.Upload(file, {
    endpoint: `${process.env.SUPABASE_URL}/storage/v1/upload/resumable`,
    headers: {
      authorization: `Bearer ${process.env.SUPABASE_ANON_KEY}`,
      'x-upsert': 'true',
    },
    chunkSize: 4 * 1024 * 1024, // 4MB chunks
    metadata: {
      bucketName: 'wr-files',
      objectName: `${userId}/${file.name}`,
      contentType: file.type,
      cacheControl: 3600,
    },
    onError: (error) => console.error('upload failed', error),
    onSuccess: () => console.log('upload complete'),
  });
  upload.start();
}
```

## The review walk

### A public bucket, "for simplicity"

`storage.buckets` is inserted with `public: true`. Proven: a file uploaded through the normal, policy-checked path is then readable by a request carrying **no credentials at all**:

```bash
# scripts/reading-supabase/worked-review-2/public-bucket-leak.sh
curl -s -w "\nHTTP=%{http_code}\n" "$SUPABASE_URL/storage/v1/object/public/wr-files/$DANA_ID/secret-report.txt"
```

```text
dana's private-looking file

HTTP=200
```

No `Authorization`, no `apikey` even — the public object endpoint (`/storage/v1/object/public/...`) is specifically the one PostgREST-equivalent path that **does not evaluate `storage.objects` RLS at all** for a public bucket, by design, since "public" means exactly that.

<SpotTheBug lang="sql" code={`insert into storage.buckets (id, name, public)
values ('wr-files', 'wr-files', true);
-- AI comment: "public for simplicity, we'll lock it down later"`}>
Every RLS policy written for this bucket later in the same migration is genuinely correct and genuinely irrelevant for reads, because `public: true` routes read access around `storage.objects` RLS entirely through a separate endpoint — "we'll lock it down later" describes a step that has to happen on the bucket itself, not a policy that can compensate for it. The fix is `public: false` from the first migration; per-file "share" access is a **signed URL** (below), never bucket-level public.
</SpotTheBug>

### No folder scoping — the path convention is decoration, not enforcement

The generated `insert`/`select` policies check `bucket_id = 'wr-files'` only. The `$userId/$filename` path shape in the upload client is a **convention**, not something either policy verifies. Proven: Erin, with no relationship to Dana at all, writes directly into what looks like Dana's folder:

```bash
# scripts/reading-supabase/worked-review-2/no-folder-scoping.sh
curl -s -w "\nHTTP=%{http_code}\n" -X POST "$SUPABASE_URL/storage/v1/object/wr-files/$DANA_ID/erin-intrusion.txt" \
  -H "Authorization: Bearer $ERIN_TOKEN" -H "apikey: $SUPABASE_ANON_KEY" -H "Content-Type: text/plain" \
  --data-binary @erin-intrusion.txt
```

```text
{"Key":"wr-files/56d4732b-ab57-4f1b-a6e0-a667455cf4a4/erin-intrusion.txt","Id":"7fbc5a00-51f1-4673-bce8-14cdb596d48f"}
HTTP=200
```

<SpotTheBug lang="sql" code={`create policy wr_files_insert on storage.objects
  for insert to authenticated
  with check ( bucket_id = 'wr-files' );`}>
This is the storage twin of [ai-bug-catalog entry 22](/supabase/en/reading-supabase/ai-bug-catalog/): a `bucket_id` check alone scopes to the **bucket**, never to a path inside it. Client code that always uploads to `${userId}/...` creates the *appearance* of per-user isolation with none of the enforcement — any authenticated user can write (and, with the matching `select` policy, read) any path in the bucket. The fix is `(storage.foldername(name))[1] = auth.uid()::text` in every policy's `using`/`with check`, proven below to reject the identical request.
</SpotTheBug>

### `upsert: true`, insert and update policies, no `select` policy

The TUS client sets `x-upsert: true`, and a later migration (not shown above) adds an `update` policy scoped correctly by folder — but never a `select` policy, on the theory that "they can already insert and update, why would they need to select." Proven with a real re-upload of a path that already exists:

```bash
# scripts/reading-supabase/worked-review-2/upsert-no-select.sh
curl -s -w "\nHTTP=%{http_code}\n" -X PUT "$SUPABASE_URL/storage/v1/object/wr-files/$DANA_ID/secret-report.txt" \
  -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $SUPABASE_ANON_KEY" -H "Content-Type: text/plain" -H "x-upsert: true" \
  --data-binary @dana-secret-v2.txt
```

```text
{"statusCode":"403","error":"Unauthorized","message":"new row violates row-level security policy","code":"AccessDenied"}
HTTP=400
```

<SpotTheBug lang="sql" code={`create policy wr_files_insert_own_folder on storage.objects for insert to authenticated with check (...);
create policy wr_files_update_own_folder on storage.objects for update to authenticated using (...);
-- no select policy -- "they can already insert and update"`}>
Exactly [ai-bug-catalog entry 23](/supabase/en/reading-supabase/ai-bug-catalog/): `upsert` compiles to `INSERT ... ON CONFLICT DO UPDATE`, and Postgres needs a **`select`**-policy-visible existing row to even evaluate the conflict path — without one, the exact same call that succeeds on a brand-new path (pure insert) fails the moment the same path is re-uploaded, with no message anywhere mentioning "select" to explain why. The fix, proven below, is adding the `select` policy: the identical request then succeeds.
</SpotTheBug>

### A signed URL with a 10-year expiry

`createSignedUrl(path, 315360000)` — 315,360,000 seconds. Proven: the API accepts it with no validation at all, and the token it issues really does carry that span:

```bash
# scripts/reading-supabase/worked-review-2/ten-year-signed-url.sh
curl -s -X POST "$SUPABASE_URL/storage/v1/object/sign/wr-files/$DANA_ID/secret-report.txt" \
  -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $SUPABASE_ANON_KEY" -H "Content-Type: application/json" \
  -d '{"expiresIn": 315360000}'
```

```text
{"signedURL":"/object/sign/wr-files/56d4732b-.../secret-report.txt?token=eyJhbGc..."}
HTTP=200
```

Decoding the returned token's own `iat`/`exp` claims confirms it, in seconds:

```text
{'url': 'wr-files/56d4732b-.../secret-report.txt', 'scope': 'download', 'iat': 1790671228, 'exp': 2106031228}
years: 9.99315537303217
```

<SpotTheBug lang="ts" code={`.createSignedUrl(path, 315360000) // "a share link that never expires, basically"`}>
There is no server-side cap on `expiresIn` to catch this — confirmed above with a real, accepted request. A "share link" is meant to expire; a signed URL that outlives almost every session, password rotation, and offboarding process at a real company is functionally a second, un-revocable password for that one file, since Supabase Storage signed URLs cannot be individually invalidated before their `exp` — the only way to cut one off early is rotating the bucket/project-level signing mechanism, which invalidates every other outstanding signed URL too. The fix is a short, deliberate expiry (minutes to low hours for a share link, chosen per feature, never a number that reads as "basically forever").
</SpotTheBug>

### `cacheControl: 3600` as a number, and as a raw seconds count either way

Two separate mistakes stacked on one field. First, the TUS metadata sets `cacheControl: 3600` — a **number** — where the type is `string`:

```ts
// @expect-error Type 'number' is not assignable to type 'string'.
import { createClient } from '@supabase/supabase-js';
const supabase = createClient('http://x', 'x');
await supabase.storage.from('wr-files').upload('x/y.txt', new Blob(), {
  cacheControl: 3600,
});
```

```text
error TS2322: Type 'number' is not assignable to type 'string'.
```

Second, even fixed to the string `'3600'`, that value is taken **completely literally** as the header's contents, not converted into a valid `Cache-Control` directive:

```bash
# scripts/reading-supabase/worked-review-2/cachecontrol-literal.sh
curl -s -X POST "$SUPABASE_URL/storage/v1/object/wr-files/$DANA_ID/cache-test.txt" \
  -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $SUPABASE_ANON_KEY" -H "cache-control: 3600" \
  --data-binary @dana-secret.txt
curl -sI "$SUPABASE_URL/storage/v1/object/wr-files/$DANA_ID/cache-test.txt" -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $SUPABASE_ANON_KEY" | grep -i cache-control
```

```text
cache-control: 3600
```

<SpotTheBug lang="ts" code={`metadata: {
  ...
  cacheControl: 3600,
},`}>
`Cache-Control: 3600` (bare, no directive name) is not valid HTTP — a spec-compliant cache has no obligation to honor it, and confirmed above, the storage API stores and serves back exactly the literal string it was given, with zero validation that it forms a real directive. Whatever browsers or CDNs do with an invalid header value is undefined behavior, not a guarantee. The fix is `cacheControl: '3600'` (a string, satisfying `tsc`) formatted as an actual directive — `'max-age=3600'` — which is what every other real example in this course's Storage lesson uses.
</SpotTheBug>

### TUS chunk size not 6MB — and a local/hosted gap worth saying out loud

Docs are explicit and narrow here, quoted directly from [supabase.com/docs/guides/storage/resumable-uploads](https://supabase.com/docs/guides/storage/resumable-uploads) (fetched fresh for this review): *"chunkSize: 6 * 1024 * 1024, // NOTE: it must be set to 6MB (for now) do not change it."* The generated client sets `chunkSize: 4 * 1024 * 1024`. Proven directly against this review's own bucket — a real 10,000,000-byte upload, first chunk exactly 4,000,000 bytes (not 6MB):

```bash
# scripts/reading-supabase/worked-review-2/tus-wrong-chunk.sh
curl -s -w "\nHTTP=%{http_code}\n" -X PATCH "$LOCATION" \
  -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $SUPABASE_ANON_KEY" \
  -H "Tus-Resumable: 1.0.0" -H "Upload-Offset: 0" -H "Content-Type: application/offset+octet-stream" \
  --data-binary @wr-chunk1-4mb.bin
```

```text
HTTP=204
```

...and the full 10,000,000-byte upload completed with no error at any point:

```text
{"id":"...","bucket_id":"wr-files","size":10000000,...}
```

<SpotTheBug lang="ts" code={`chunkSize: 4 * 1024 * 1024, // 4MB chunks`}>
On **this local stack specifically**, `docker exec supabase_storage_probe env` shows `STORAGE_BACKEND=file` — a filesystem backend, not the S3 multipart backend hosted Supabase uses, which is exactly why the 6MB requirement (an S3 multipart minimum-part-size constraint the docs pass straight through, not an arbitrary Supabase limit) never triggers a real error here, proven above. Shipping this exact client against **hosted** Supabase (S3-backed) is expected to fail differently and for real, per the docs' own explicit warning — this is a genuine local-vs-hosted gap this review is saying out loud rather than papering over: a passing local test here would be false confidence. The fix is simply following the docs literally: `chunkSize: 6 * 1024 * 1024`, unchanged.
</SpotTheBug>

### Edge Function signs URLs with the anon key — RLS blocks everyone, including the file's own owner

`share-link`'s function body creates its Supabase client with `SUPABASE_ANON_KEY` and never forwards the caller's own `Authorization` header, so every request the function makes runs as genuinely anonymous — no `auth.uid()` at all. Proven: Dana, the real, authenticated owner of the file, asks the function for a link to her own file:

```bash
# scripts/reading-supabase/worked-review-2/edge-anon-blocks-owner.sh
curl -s -w "\nHTTP=%{http_code}\n" -X POST "$FUNCTIONS_URL/wr-share-link-anon" \
  -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $ANON_KEY" -H "Content-Type: application/json" \
  -d '{"path":"'"$DANA_ID"'/secret-report.txt"}'
```

```text
{"data":null,"error":{"name":"StorageApiError","message":"Object not found","status":400,"statusCode":"404","code":"NoSuchKey"}}
HTTP=200
```

The function itself returns `HTTP 200` — the *request* to the function succeeded — while the *storage call inside it* failed for everyone, with an error message ("Object not found") that gives no hint the real cause is RLS denying a request with no identity at all, not a missing file.

<SpotTheBug lang="ts" code={`const client = createClient(
  Deno.env.get('SUPABASE_URL')!,
  Deno.env.get('SUPABASE_ANON_KEY')!,
)
const { data, error } = await client.storage.from('wr-files').createSignedUrl(path, ...)`}>
This is the inverse failure mode of [ai-bug-catalog entry 25](/supabase/en/reading-supabase/ai-bug-catalog/) (which ships `service_role` too broadly): here the function is scoped too narrowly, and RLS — correctly protecting every other caller — also blocks the one caller who is supposed to succeed, because the function never identifies who is actually calling. The fix is not "switch to `service_role`" by itself (that alone would recreate the `service_role`-in-the-wrong-place bug from the previous review, letting anyone request anyone's file) — it is `service_role`, used **only after** the function has verified the real caller's identity itself and checked that the requested path belongs to them, proven below.
</SpotTheBug>

### The fixed function, and what "scoped correctly" actually requires

The corrected function identifies the caller with the **anon** key plus their own forwarded token (`anon.auth.getUser(token)`), checks the requested path's folder against that verified id, and only then uses **`service_role`** — deliberately, for exactly that one already-checked path — to mint the signed URL. Proven twice: Dana's own file succeeds, and Dana requesting Erin's file by path is rejected by the function's own check, not by RLS:

```bash
# scripts/reading-supabase/worked-review-2/edge-fixed-own-and-forbidden.sh
curl -s -w "\nHTTP=%{http_code}\n" -X POST "$FUNCTIONS_URL/wr-share-link" \
  -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $ANON_KEY" -H "Content-Type: application/json" \
  -d '{"path":"'"$DANA_ID"'/secret-report.txt"}'

curl -s -w "\nHTTP=%{http_code}\n" -X POST "$FUNCTIONS_URL/wr-share-link" \
  -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $ANON_KEY" -H "Content-Type: application/json" \
  -d '{"path":"'"$ERIN_ID"'/erin-own.txt"}'
```

```text
--- dana's own file ---
{"data":{"signedUrl":"http://kong:8000/storage/v1/object/sign/wr-files/56d4732b-.../secret-report.txt?token=..."},"error":null}
HTTP=200

--- dana requesting erin's file by path ---
{"error":"forbidden: not your file"}
HTTP=403
```

### A bare specifier import — the same `BOOT_ERROR` a different function gets

A separate small function in this review, meant to reuse the project's client the same way another lesson's `deno.json` import map does, imports `'supabase'` with no import map configured for **this** function. Proven with a real invocation:

```bash
# scripts/reading-supabase/worked-review-2/bare-import-boot-error.sh
curl -s -w "\nHTTP=%{http_code}\n" "$FUNCTIONS_URL/wr-bare-import" -H "Authorization: Bearer $ANON_KEY" -H "apikey: $ANON_KEY"
```

```text
{"code":"BOOT_ERROR","message":"Worker failed to boot (please check logs)"}
HTTP=503
```

<SpotTheBug lang="ts" code={`import { createClient } from 'supabase'`}>
Exactly [ai-bug-catalog entry 16](/supabase/en/reading-supabase/ai-bug-catalog/): Deno resolves `jsr:`, `npm:`, and full URL specifiers, but a bare package name resolves to nothing unless **this function's own** `deno.json` maps it — copying an import line from a function that has one, into a function that doesn't, is enough to break the whole function at boot, before any request-handling code runs at all. The fix is `import { createClient } from 'jsr:@supabase/supabase-js@2'` (or a matching `imports` entry in this function's own `deno.json`).
</SpotTheBug>

### Missing CORS headers on the actual response — masked by Kong locally on `OPTIONS`

Neither generated function sets its own CORS headers. On **this local stack**, Kong answers every `OPTIONS` preflight itself before either function ever sees the request (documented already in [Writing and Invoking a Function](/supabase/en/edge-functions/writing-and-invoking-a-function/)) — so an `OPTIONS` probe against both functions looks identical and gives no signal. The real difference only shows up on the actual response:

```bash
# scripts/reading-supabase/worked-review-2/cors-real-response.sh
curl -s -i -X POST "$FUNCTIONS_URL/wr-share-link" -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $ANON_KEY" \
  -H "Content-Type: application/json" -H "Origin: https://example.com" -d '{"path":"'"$DANA_ID"'/secret-report.txt"}' \
  | grep -i access-control

curl -s -i -X POST "$FUNCTIONS_URL/wr-share-link-anon" -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $ANON_KEY" \
  -H "Content-Type: application/json" -H "Origin: https://example.com" -d '{"path":"'"$DANA_ID"'/secret-report.txt"}' \
  | grep -i access-control
```

```text
--- fixed function's real response headers ---
access-control-allow-origin: *
access-control-allow-headers: authorization, apikey, content-type
access-control-allow-methods: POST, OPTIONS

--- broken function's real response headers ---
Access-Control-Allow-Origin: *
(nothing else -- no access-control-allow-headers, no access-control-allow-methods, from the function itself)
```

<SpotTheBug lang="ts" code={`Deno.serve(async (req) => {
  const { path } = await req.json()
  // no OPTIONS handling, no CORS headers set anywhere in this function
  ...
})`}>
Kong injects a bare `Access-Control-Allow-Origin: *` on every response regardless, which is exactly what makes this bug invisible to a `curl` OPTIONS probe and to casual local testing — a real browser's preflight check also needs `Access-Control-Allow-Headers` to explicitly list every non-simple header the actual request sends (here, `authorization` and `apikey`), which only the fixed function sets. The fix is answering `OPTIONS` explicitly and setting the same CORS headers on every response, proven above, not relying on the gateway's default.
</SpotTheBug>

### `verify_jwt` — and a shared-stack gap worth being honest about

Neither function sets `verify_jwt = false`, so the default (`true`) should gate every request at the gateway before the function's own code runs — exactly as proven for `edge-hello` in [Writing and Invoking a Function](/supabase/en/edge-functions/writing-and-invoking-a-function/). Proven on **that** already-running function, in this exact shared stack, right now:

```bash
# scripts/reading-supabase/worked-review-2/verify-jwt-existing-function.sh
curl -s -w "\nHTTP=%{http_code}\n" "$FUNCTIONS_URL/edge-hello"
```

```text
{"code":"UNAUTHORIZED_NO_AUTH_HEADER","message":"Missing authorization header","msg":"Missing authorization header"}
HTTP=401
```

But the identical missing-header request against **this review's own**, newly-added function does not get that gateway-level rejection at all — it reaches the function's own code, which returns its own `401` instead:

```bash
# scripts/reading-supabase/worked-review-2/verify-jwt-new-function.sh
curl -s -w "\nHTTP=%{http_code}\n" -X POST "$FUNCTIONS_URL/wr-share-link" -H "apikey: $ANON_KEY" -H "Content-Type: application/json" -d '{"path":"x"}'
```

```text
{"error":"not authenticated"}
HTTP=401
```

<Callout title="A shared-stack artifact, not a security property">
This course's harness never restarts the shared local stack (per this module's own hard rules) — and Kong's declarative gateway configuration, including its per-function `verify_jwt` route, is provisioned when the stack (or `supabase functions serve`) starts from the function list on disk **at that moment**. A function added to the filesystem afterward, on an already-running shared stack, is served by the Edge Runtime but never gets that gateway-level check retroactively wired in without a restart this course deliberately never performs. This is a local/shared-stack development artifact, confirmed above by the identical check succeeding for an *earlier* function (`edge-hello`) and failing for a brand-new one in the *same* running stack — not a statement about hosted Supabase, which provisions `verify_jwt` per function at deploy time. It is exactly why the fixed function in this review re-verifies the caller's identity in its **own code** (`anon.auth.getUser(token)`) rather than trusting `verify_jwt` config alone — the one layer of defense that stays correct regardless of gateway state.
</Callout>

## The corrected code

```sql
-- supabase/migrations/7402_wr_files_storage.sql
insert into storage.buckets (id, name, public)
values ('wr-files', 'wr-files', false);

create policy wr_files_insert_own_folder on storage.objects
  for insert to authenticated
  with check ( bucket_id = 'wr-files' and (storage.foldername(name))[1] = auth.uid()::text );

create policy wr_files_select_own_folder on storage.objects
  for select to authenticated
  using ( bucket_id = 'wr-files' and (storage.foldername(name))[1] = auth.uid()::text );

create policy wr_files_update_own_folder on storage.objects
  for update to authenticated
  using ( bucket_id = 'wr-files' and (storage.foldername(name))[1] = auth.uid()::text );
```

```ts
// supabase/functions/wr-share-link/index.ts
import { createClient } from 'jsr:@supabase/supabase-js@2'

const corsHeaders = {
  'Access-Control-Allow-Origin': '*',
  'Access-Control-Allow-Headers': 'authorization, apikey, content-type',
  'Access-Control-Allow-Methods': 'POST, OPTIONS',
}

Deno.serve(async (req) => {
  if (req.method === 'OPTIONS') {
    return new Response(null, { headers: corsHeaders })
  }

  const authHeader = req.headers.get('Authorization') ?? ''
  const token = authHeader.replace('Bearer ', '')

  const anon = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_ANON_KEY')!,
  )
  const { data: userData, error: userErr } = await anon.auth.getUser(token)
  if (userErr || !userData.user) {
    return new Response(JSON.stringify({ error: 'not authenticated' }), {
      status: 401,
      headers: { ...corsHeaders, 'Content-Type': 'application/json' },
    })
  }

  const { path } = await req.json()
  const ownerFolder = path.split('/')[0]
  if (ownerFolder !== userData.user.id) {
    return new Response(JSON.stringify({ error: 'forbidden: not your file' }), {
      status: 403,
      headers: { ...corsHeaders, 'Content-Type': 'application/json' },
    })
  }

  const admin = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!,
  )
  const { data, error } = await admin.storage.from('wr-files').createSignedUrl(path, 3600)
  return new Response(JSON.stringify({ data, error }), {
    headers: { ...corsHeaders, 'Content-Type': 'application/json' },
  })
})
```

## Mental Model

The bucket-level bugs (1) and the RLS-shaped bugs (2, 3) all share one property: they compile, they run, and the **wrong** request is the one that "just works" — a public bucket serves everyone happily, a folder-less policy lets any upload through, `upsert` on a fresh path succeeds and only breaks on the second attempt. The two Edge Function identity bugs (7, and its inverse in the fixed version) show the same shape from opposite directions: too broad (anon-catalog-25-style) breaks nobody visibly but exposes everyone, too narrow (this review's actual bug) breaks the one caller who should succeed. The infrastructure-adjacent bugs (6, 10, 11) are the most honest ones to get wrong: each has a real, documented requirement or limit that simply doesn't manifest as an error on **this specific local stack**, for a reason worth understanding (file backend vs. S3 backend; Kong's config snapshot timing; a commented-out local flag) rather than memorizing as "it just works here."

## Trade-offs

- **A public bucket is genuinely the right choice for content that is meant to be public** (marketing assets, a public avatar) — the bug here isn't "public buckets are wrong," it's using one for content a feature description called "sharing," which implies scoped, revocable access a public bucket cannot express at all.
- **`service_role` inside an Edge Function, used only after an explicit identity check, is more code than trusting RLS alone** — at the benefit of the function being able to enforce authorization logic RLS genuinely cannot express on its own (here: "the folder must match the verified caller," which storage.objects RLS could also do, but a real app's sharing rules often need a lookup RLS can't see, like an explicit grants table).
- **A short signed-URL expiry is safer but less convenient** — a share link that expires in an hour means legitimately re-sharing it later requires generating a new one, which is friction a 10-year expiry "solves" by removing the safety property entirely rather than by being more convenient in a good way.

## Common Misconceptions

- **"A `bucket_id` check in a storage policy scopes access to that user's files."** Proven above: it scopes to the *bucket*, which every authenticated user in this review shares — folder-level isolation is an explicit `storage.foldername(name)` check the AI-generated policy never wrote.
- **"If `curl -X OPTIONS` looks fine, the function's CORS setup is fine."** Proven above with two functions that give an identical `OPTIONS` response locally (Kong answers before either function runs) and a genuinely different real POST response — only one of them actually sets the headers a browser's preflight needs.
- **"`verify_jwt = true` (the default) always protects a function before its own code runs."** Proven above on this exact shared, never-restarted stack: it does for a function present when the stack last started, and does not, right now, for a function added afterward — which is exactly why the fixed function in this review checks identity in its own code too.
