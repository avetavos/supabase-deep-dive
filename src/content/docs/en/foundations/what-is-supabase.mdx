## The idea in one sentence

Supabase is an open-source **Backend as a Service** built around a real, unmodified **Postgres** database — you get an auto-generated API, auth, storage, and realtime for free, but the core is still plain Postgres you can query with plain SQL any time you want.

## Postgres first, services second

If you built a backend from scratch, you would end up writing an authentication service, some kind of query API, a realtime layer for pushing live updates, and a file storage service — on top of whatever database you chose. Supabase's pitch is that it gives you all of that already built, wired together, and running against **a database you fully own and can query directly**.

That last part is the important distinction from Firebase. Firebase's Firestore is a proprietary, schemaless NoSQL document store — your data model and your queries are locked into Firebase's specific API shape, and there is no SQL escape hatch. Supabase is the opposite bet: the database is standard Postgres, so:

- You can connect with `psql`, any Postgres driver, or any ORM that speaks Postgres.
- Your schema is relational tables, foreign keys, and constraints — not implicit document shapes.
- If you ever need to leave Supabase, you can `pg_dump` your database and run it anywhere Postgres runs.

```sql
-- This is just Postgres. No proprietary query language, no vendor-specific data model.
select id, username, created_at
from public.profiles
where created_at > now() - interval '7 days'
order by created_at desc;
```

## The core services at a glance

One Supabase project is one Postgres database plus a set of managed services layered around it. Each of these gets its own module later in this course, so keep this as an orientation map, not the deep dive:

- **Postgres database** — the actual data store, plain SQL, full relational features.
- **Auto-generated API** — a REST/RPC API via **PostgREST**, and a GraphQL API via **pg_graphql**, generated directly from your schema.
- **Auth (GoTrue)** — user sign-up, sign-in, session management, and social/SSO providers.
- **Storage** — an S3-compatible object store for files, with its own access policies.
- **Realtime** — subscribe to database changes, or use ephemeral broadcast/presence channels, over WebSockets.
- **Edge Functions** — custom server-side logic written in TypeScript, running on Deno at the edge.

All of it is configurable from the **Supabase Studio** dashboard (a web GUI) or from the **Supabase CLI**, which you will set up in the next lesson.

```typescript
import { createClient } from '@supabase/supabase-js';

const supabase = createClient(
  process.env.SUPABASE_URL!,
  process.env.SUPABASE_ANON_KEY!
);

// Under the hood this is a PostgREST request against the profiles table.
const { data, error } = await supabase
  .from('profiles')
  .select('id, username, created_at')
  .order('created_at', { ascending: false });
```

## What one `supabase start` actually boots

The service list above is not a marketing diagram — it is one Docker Compose stack, and every box in it is a real, individually-named container. This is the real `docker ps` output for this course's own local stack (one unrelated sibling-course container filtered out):


Every one of those names ends in `_probe` because this course's `project_id` is `probe` — your own project's containers carry your project's own id instead. `supabase_edge_runtime_probe` and `supabase_imgproxy_probe` are part of the same stack but report **stopped**: the CLI starts them lazily, on first real use (an Edge Function invocation, an image transformation), not eagerly at `supabase start`.

**Kong is the one piece the diagram above simplifies away**: nothing talks to PostgREST, GoTrue, Realtime, or Storage directly — every request, whether it is `supabase-js`, `curl`, or the Studio UI, goes through **Kong**, an API gateway, first. Kong is what turns "several independent services on several different ports" into the single `API_URL` (`http://127.0.0.1:55321` on this stack) you have been using since the previous lesson, routing each request onward by path (`/rest/v1/...` to PostgREST, `/auth/v1/...` to GoTrue, and so on).

## Why not just roll your own?

Nothing here is magic you could not build yourself — PostgREST, GoTrue, and the rest are open-source projects you could self-host individually. What Supabase actually saves you is the integration work: one project, one set of credentials, one dashboard, and services that already know how to talk to each other and to the same Postgres instance. You still write the schema, the SQL, and the access rules — Supabase just removes the plumbing around them.

## Reading AI-generated code

An AI assistant, prompted with "add a bio field when creating a profile" and shown a Firebase-flavored example from its training data, produced this:

<SpotTheBug lang="sql" code={`-- An AI assistant's attempt at "just add a bio field", Firebase-habit style
insert into public.fnd_profiles_demo (id, username, bio)
values (gen_random_uuid(), 'ada', 'wrote the first algorithm');
`}>
Run for real against this lesson's own table:

\`\`\`text
ERROR:  column "bio" of relation "fnd_profiles_demo" does not exist
LINE 2: insert into public.fnd_profiles_demo (id, username, bio)
\`\`\`

This is the "Postgres first" section's whole point, made concrete: unlike Firestore, where writing an extra field to a document just adds it, Postgres has a fixed, declared set of columns per table, and an `insert` naming a column that was never created with `alter table ... add column` fails loudly instead of silently accepting arbitrary shape. The fix is not a query change — it is a migration (`alter table public.fnd_profiles_demo add column bio text;`, the subject of the next lesson) that declares the column first. An AI assistant trained heavily on schemaless-database examples will reach for "just include the field" out of habit; Supabase's relational core rejects that instinct at the database layer, every time, which is exactly the portability and validation trade described above.
</SpotTheBug>

## Mental Model

Treat every Supabase service as a **client of the same Postgres database**, not as a separate product that happens to share a project dashboard. `supabase-js`'s `.from('profiles').select()` is not a special Supabase primitive — it is a thin wrapper that asks PostgREST to run `select * from public.profiles`, over HTTP, through Kong. Auth's sign-up flow is not magic — it is GoTrue inserting a row into `auth.users`. When something behaves unexpectedly, the reliable move is to ask "what SQL did this actually turn into, and what does `psql` say if I run that directly" — which is exactly the debugging path this course keeps returning to.

## Trade-offs

- **A real, unmodified Postgres core buys full SQL power, every extension in the Postgres ecosystem, and a `pg_dump`-shaped exit ramp** — **at the cost of schema discipline you do not pay with a schemaless store**: every column must be declared before it can be written, proved above by the AI-generated insert that failed instantly instead of "just working."
- **Bundling Auth, Storage, Realtime, and Edge Functions as managed services saves the integration work of wiring five separate open-source projects together** — **at the cost of a wider surface to learn up front**: this course's seven modules exist because there are genuinely seven distinct services' worth of behavior to understand, not one.
- **Configuring everything through Studio or the CLI keeps day-to-day changes fast** — **at the cost of needing migrations (next lesson) to keep any of it reviewable and reproducible**, the same "GUI edit vs. version-controlled file" tension that shows up in every infrastructure-as-code discipline.

## Common Misconceptions

- **"Supabase is just Firebase, but with SQL instead of NoSQL."** The data model difference is not cosmetic — it changes what a write can do at all, proved above: a Firestore-habit `insert` with an undeclared field fails hard in Postgres instead of silently succeeding.
- **"Since it's Postgres, the Supabase-specific services are optional add-ons I can ignore."** They are real, separate processes with their own containers (proved by the `docker ps` output above), not thin SQL views — GoTrue genuinely manages sessions and JWTs, Storage genuinely proxies an S3-compatible object store, and understanding each one's actual behavior (not just "it's Postgres under there") is most of this course.
- **"Everything goes through PostgREST."** Proved above: Kong routes by path to five *different* backend services (PostgREST, GoTrue, Realtime, Storage, the Edge Runtime) — PostgREST is only the one handling `/rest/v1`.

<Callout title="The one-line takeaway">
Supabase is **Postgres plus a set of services layered around it** — a REST/RPC API (PostgREST) and GraphQL API (pg_graphql), **Auth**, **Storage**, **Realtime**, and **Edge Functions** — all managed through **Studio** or the **CLI**, and unlike Firebase, the underlying data model is always plain, portable, queryable Postgres.
</Callout>
