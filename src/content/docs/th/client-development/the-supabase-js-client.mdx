## ไอเดียในหนึ่งประโยค

`createClient` สร้าง object เดียวที่แอปของคุณใช้คุยกับ Postgres, Auth, Storage และ Realtime ควร initialize ด้วย public `anon` key เสมอในโค้ดฝั่ง client — ไม่ใช่ `service_role` key — เพราะ **row level security (RLS)** ไม่ใช่ความลับของ key ตัวนี้ คือสิ่งที่ปกป้องข้อมูลจริง และทุก option ที่ส่งเข้าไป (`auth`, `db`, `global`, `realtime`) มีผลจริงเฉพาะเจาะจง พิสูจน์ได้ ไม่ใช่แค่ configuration ที่ดูดีเฉย ๆ

## Initialize client

ทุกแอป `supabase-js` เริ่มแบบเดียวกันหมด import `createClient` ใส่ project URL กับ key เข้าไป แล้วได้ object กลับมาที่มี `.from()`, `.auth`, `.storage` และ `.channel()` พร้อมใช้

```typescript
import { createClient } from '@supabase/supabase-js';

// Safe to ship in browser bundles: this is the anon key, not the service_role key
const supabase = createClient(
  process.env.SUPABASE_URL!,
  process.env.SUPABASE_ANON_KEY!
);
```

ข้อนี้ควรพูดซ้ำให้ชัดเพราะสลับกันผิดง่ายมาก client ฝั่ง browser หรือ mobile ต้อง initialize ด้วย **`anon` key** เสมอ `anon` key ถูกออกแบบมาให้เป็น public อยู่แล้ว key นี้ติดไปกับ JavaScript bundle ที่ใครก็อ่านได้ และนั่นไม่ใช่ปัญหา สิ่งที่กันไม่ให้คนแปลกหน้าอ่านหรือเขียน row ที่ไม่ควรแตะได้คือ **row level security (RLS)** บน table ของคุณ ไม่ใช่ความลับของ key ตัวนี้ ส่วน **`service_role` key** เป็นคนละเรื่องเลย key ตัวนี้ bypass RLS ทั้งหมด ซึ่งทรงพลังมากและเป็นเหตุผลว่าทำไมห้ามให้ไปโผล่ในโค้ดฝั่ง client เด็ดขาด ควรอยู่แค่ใน server environment ที่เชื่อถือได้ (เช่น Edge Function หรือ backend process) ที่ไม่มีทางไปถึง browser

## Generated type เปลี่ยน `.from()` ให้กลายเป็น typed API

Supabase CLI อ่าน schema จริงของคุณแล้ว generate TypeScript `Database` type ที่ตรงกันให้

```bash
supabase gen types typescript --project-id abcdefghijklmnopqrst > database.types.ts
```

คำสั่งนี้ inspect ทุก table, column และ constraint ในโปรเจกต์ แล้ว generate type ที่มี shape `Row`, `Insert` และ `Update` ให้แต่ละ table `Database['public']['Tables']['movies']['Row']` คือ column ที่ `select` จะคืนกลับมาเป๊ะ ๆ `Insert` คือหน้าตาของ row ใหม่ที่ valid และ `Update` คือหน้าตาของ partial patch เอา type นี้ไปเป็น generic ให้ `createClient` ก็จะผูก query builder ทั้งหมดเข้ากับ type นั้นทันที

```typescript
import { createClient } from '@supabase/supabase-js';
import type { Database } from './database.types';

const supabase = createClient<Database>(
  process.env.SUPABASE_URL!,
  process.env.SUPABASE_ANON_KEY!
);

// Autocomplete on table names, column names, and the shape of data
const { data, error } = await supabase
  .from('movies')
  .select('id, title, year');
```

พอ schema เปลี่ยน ก็แค่รัน CLI command เดิมซ้ำเพื่อ regenerate `database.types.ts` แล้ว type ของทั้งแอปก็จะ sync กับ database ทันที — บทถัดไปจะพิสูจน์เต็ม ๆ ว่าถ้าลืมทำสิ่งนี้จะเกิดอะไรขึ้น ทั้งสองด้านเลย

## Singleton ในฝั่ง browser, per-request ฝั่ง server

`supabase-js` client มักจะถูกสร้างแค่ **ครั้งเดียว** ในฝั่ง browser แล้ว reuse ทั่วทั้งแอป — แบบ singleton — แทนที่จะสร้างใหม่ทุก component render

```typescript
// lib/supabase.ts — created once, imported wherever it is needed
import { createClient } from '@supabase/supabase-js';
import type { Database } from './database.types';

export const supabase = createClient<Database>(
  process.env.SUPABASE_URL!,
  process.env.SUPABASE_ANON_KEY!
);
```

มีเหตุผลจริงสองข้อ ข้อแรก client เก็บ **session state** ไว้ใน memory (และใน browser ก็เก็บใน `localStorage` ด้วย) การสร้างใหม่จะทิ้งหรือทำ state นั้นซ้ำซ้อน แล้วอาจทำให้ auth listener ทำงานไม่สอดคล้องกัน ข้อสอง client จัดการ network resource ของตัวเอง รวมถึง WebSocket connection ที่ Realtime ใช้ — สร้าง client ใหม่ทุก component แปลว่าได้ connection ซ้ำซ้อนแทนที่จะเป็น connection เดียวที่แชร์กันและ reuse ได้

ฝั่ง server มีข้อจำกัดตรงข้ามกัน คือต้องรองรับ request ของ **user ที่ต่างกัน** พร้อมกันใน process เดียวกัน ดังนั้น **singleton ตัวเดียวที่แชร์กันจะทำให้ session รั่วข้าม user** ทางแก้ — ที่พิสูจน์ไว้แล้วในบท [Sessions and JWTs](/supabase/th/auth-and-row-level-security/sessions-and-jwts/) ของโมดูล Auth — คือ `createServerClient` จาก `@supabase/ssr` ที่สร้างใหม่ทุก request จาก cookie ของ request นั้นเอง

```typescript
// src/lib/supabase-server.ts
import { createServerClient } from '@supabase/ssr';
import { cookies } from 'next/headers';

export async function createClient() {
  const cookieStore = await cookies();

  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return cookieStore.getAll();
        },
        setAll(cookiesToSet) {
          try {
            cookiesToSet.forEach(({ name, value, options }) =>
              cookieStore.set(name, value, options)
            );
          } catch {
            // called from a Server Component with no way to set cookies —
            // safe to ignore if middleware is refreshing the session
          }
        },
      },
    }
  );
}
```

อ้างอิง: [supabase.com/docs/guides/auth/server-side/creating-a-client](https://supabase.com/docs/guides/auth/server-side/creating-a-client) กติกาง่าย ๆ คือ **singleton ในฝั่ง browser** (user เดียว อายุ process เดียว) **client ต่อ request ในฝั่ง server** (หลาย user แชร์ process เดียวกัน) version ของ package ที่ติดตั้งคู่กับ `@supabase/supabase-js@2.117.2` ของคอร์สนี้ ตรวจด้วย `npm view @supabase/ssr version` คือ **`0.12.7`**

## Config client: `auth`, `global`, และ `db`

argument ตัวที่สามของ `createClient` ถูกแบ่งเป็น sub-object เพื่อไม่ให้ option จาก sub-library ต่างกันชนชื่อกัน (ตรวจสอบกับ source of truth ปัจจุบัน คือ blog ประกาศ v2 ของ `@supabase/supabase-js` เอง):

```typescript
const supabase = createClient(apiURL, apiKey, {
  auth: {
    persistSession: true,       // store the session (localStorage in a browser; in-memory in Node — proved next lesson)
    autoRefreshToken: true,     // silently refresh the access token before it expires
    detectSessionInUrl: true,   // parse a PKCE `?code=` or implicit `#access_token` from the URL on load
    flowType: 'pkce',           // 'pkce' (default, recommended) or 'implicit' — see the next lesson
  },
  db: {
    schema: 'public',           // which Postgres schema .from() targets by default
  },
  global: {
    headers: { 'x-app-version': '1.4.0' }, // merged into every request's headers
    fetch: customFetch,                    // override the fetch implementation (proved below)
  },
  realtime: {
    params: { eventsPerSecond: 10 },
  },
});
```

`persistSession`/`autoRefreshToken`/`detectSessionInUrl` ทั้งหมดเป็น default ที่ **เน้นฝั่ง browser** (`true`) ที่ client แบบ per-request ฝั่ง server มักจะปิด — ตัวอย่าง `@supabase/ssr` ข้างบนตั้ง `persistSession: true` แต่อ่าน/เขียนผ่าน cookie แทน `localStorage` และ server client ทั่วไปที่ไม่มี `cookies` adapter เลยควรตั้ง `autoRefreshToken: false`/`detectSessionInUrl: false` เพราะไม่มี tab ที่อยู่นานให้ background refresh timer มีความหมาย และไม่มี URL bar ให้ parse code ออกมา `db.schema` คือสิ่งที่ `supabase.schema('other')` override เป็นรายครั้ง พิสูจน์ด้านล่าง `global.headers` merge เข้าไปใน **ทุก** request จาก client ตัวนี้ — พิสูจน์ด้านล่างเช่นกัน รวมถึงจุดพลาดจริงเมื่อเอาไปใช้กับอะไรที่ไม่ควร static

## สัญญา `{ data, error }`: พิสูจน์ ไม่ใช่แค่กล่าวอ้าง

ทุก call ของ `supabase-js` resolve เป็น `{ data, error }` — ไม่ throw แม้จะเป็น error ที่ควรจะเป็น HTTP status 4xx/5xx พิสูจน์ด้วย table ที่ไม่เคยมีอยู่ใน schema นี้เลย:

```ts
// src/cli-client-never-throws.ts
// @run
import { createClient } from '@supabase/supabase-js';

const supabase = createClient(process.env.SUPABASE_URL!, process.env.SUPABASE_ANON_KEY!);

try {
  const { data, error } = await supabase.from('cli_nonexistent_table').select('*');
  console.log('never-throws: data =', data, '| error.code =', error?.code, '| error.message =', error?.message);
} catch (e) {
  console.log('THREW (would be unexpected):', e);
}
```

```text
never-throws: data = null | error.code = PGRST205 | error.message = Could not find the table 'public.cli_nonexistent_table' in the schema cache
```

`try/catch` ไม่ทำงานเลย `error` ที่มีค่าจริงกลับมาเป็น resolved value ปกติ — นี่คือเหตุผลที่ pattern มาตรฐานทั่วทั้งคอร์สนี้คือเช็ค `error` ตรง ๆ ไม่เคยห่อ call ด้วย `try/catch` เพื่อจับ failure

เวลาที่ *ต้องการ* ให้ throw จริง ๆ — เช่นให้ error boundary หรือ `try/catch` ด้านนอกจัดการ call หลาย ๆ ตัวพร้อมกัน — `.throwOnError()` เปิดให้ call เดียว throw กลับมาได้:

```ts
// src/cli-client-throw-on-error.ts
// @run
import { createClient } from '@supabase/supabase-js';

const supabase = createClient(process.env.SUPABASE_URL!, process.env.SUPABASE_ANON_KEY!);

try {
  await supabase.from('cli_nonexistent_table').select('*').throwOnError();
  console.log('throwOnError did not throw (unexpected)');
} catch (e: any) {
  console.log('throwOnError threw ->', e.constructor?.name, ':', e.message);
}
```

```text
throwOnError threw -> PostgrestError : Could not find the table 'public.cli_nonexistent_table' in the schema cache
```

ค่าที่ throw ออกมาคือ `PostgrestError` object ตัวเดียวกันเป๊ะกับที่ปกติจะถูกคืนมาเป็น `error` — `.throwOnError()` เปลี่ยนวิธีส่งมอบ ไม่ได้เปลี่ยน shape

## ยกเลิก query ที่กำลังทำงานอยู่ด้วย `AbortSignal`

query builder call ทุกตัวรับ `.abortSignal(signal)` ผูกกับ `AbortController` มาตรฐาน:

```ts
// src/cli-client-abort-signal.ts
// @run
import { createClient } from '@supabase/supabase-js';

const supabase = createClient(process.env.SUPABASE_URL!, process.env.SUPABASE_ANON_KEY!);

const controller = new AbortController();
controller.abort(); // abort before the request is even sent
const { error } = await supabase.from('cli_nonexistent_table').select('*').abortSignal(controller.signal);
console.log('aborted request -> error.name =', error?.name, '| message =', error?.message);
```

```text
aborted request -> error.name = undefined | message = AbortError: This operation was aborted
```

ยังคงเป็น `{ data, error }` ไม่ใช่ throw — request ที่ถูก abort ก็แค่ error อีกแบบหนึ่ง ส่งมอบด้วยวิธีเดียวกับ failure อื่น ๆ ทั้งหมด (postgrest-js ห่อ `AbortError` ดิบเข้า `PostgrestError` shape ของตัวเอง จึงเป็นเหตุผลที่ `error.name` กลับมาเป็น `undefined` ในขณะที่ `error.message` มีข้อความ `AbortError:` เดิมอยู่ — การห่อไม่ได้โยน error เดิมต่อ แต่ re-package ใหม่) นี่คือกลไกที่ React Query และ library แบบเดียวกันใช้ยกเลิก query เมื่อ component unmount หรือ dependency เปลี่ยนกลางคัน (ยืนยันจาก reference example ของ `@supabase/supabase-js` เองที่โชว์ pattern `if (signal) query = query.abortSignal(signal)` แบบนี้เป๊ะ ๆ กับ `AbortSignal` จาก caller อย่าง React Query)

## สิ่งที่ออกไปบน wire จริง ๆ

query builder ของ `supabase-js` เป็น layer typed บาง ๆ เหนือ HTTP call ธรรมดาไปหา PostgREST การส่ง `global.fetch` แบบ custom เข้าไป — option เดียวกับตารางด้านบน — ทำให้เห็นชัดด้วยการ intercept request จริงก่อนที่จะถูกส่งไป:

```ts
// src/cli-client-wire-shape.ts
// @run
import { createClient } from '@supabase/supabase-js';

let seen: { method: string; url: string; headers: Record<string, string> } | undefined;
const supabase = createClient(process.env.SUPABASE_URL!, process.env.SUPABASE_ANON_KEY!, {
  global: {
    fetch: (input, init) => {
      const url = typeof input === 'string' ? input : (input as Request).url;
      const headers = Object.fromEntries(new Headers(init?.headers).entries());
      seen = { method: init?.method ?? 'GET', url, headers };
      return fetch(input, init);
    },
  },
});

await supabase.from('cli_nonexistent_table').select('id,title').eq('id', 1).limit(5);
console.log(JSON.stringify(seen, (k, v) => (k === 'apikey' || k === 'authorization' ? '<redacted>' : v), 2));
```

```text
{
  "method": "GET",
  "url": "http://127.0.0.1:55321/rest/v1/cli_nonexistent_table?select=id%2Ctitle&id=eq.1&limit=5",
  "headers": {
    "accept-profile": "public",
    "apikey": "<redacted>",
    "authorization": "<redacted>",
    "x-client-info": "supabase-js/2.117.2; runtime=node; runtime-version=24.13.0"
  }
}
```

ไม่มีเวทมนตร์อะไรเลย `.select('id,title').eq('id', 1).limit(5)` compile ออกมาเป็น `GET` ธรรมดาที่มี `select`, `id` และ `limit` เป็น **query parameter** — request shape ของ PostgREST แบบเดียวกับที่ตัวอย่าง `curl` ดิบ ๆ ของโมดูล auto-generated-api สร้างขึ้นเองด้วยมือ `accept-profile: public` คือ `db.schema` จากตารางด้านบน ที่กลายเป็นรูปธรรม — มันบอก PostgREST ว่าจะค้นหา schema ไหน และสลับด้วย `.schema('other')` พิสูจน์ถัดไป `x-client-info` คือ SDK บอกตัวตนตัวเอง รวม version และ runtime จริง ๆ — ข้อมูล version/runtime ฟรี ๆ ที่เห็นได้ในทุก request โดยไม่ต้องเพิ่มอะไรเอง

## หลาย schema: `supabase.schema('other')`

`db.schema` ตั้ง schema *default*; `.schema('name')` override เป็นรายครั้ง แต่ schema ต้องอยู่ใน allowlist ของ schema ที่ expose ของโปรเจกต์ — `api.schemas` ใน `config.toml` — ไม่งั้น PostgREST จะปฏิเสธทันที ก่อนที่จะเช็คด้วยซ้ำว่า schema นั้นมีอยู่จริงไหม:

```ts
// src/cli-client-unexposed-schema.ts
// @run
import { createClient } from '@supabase/supabase-js';

const supabase = createClient(process.env.SUPABASE_URL!, process.env.SUPABASE_ANON_KEY!);
const { error, status } = await supabase.schema('cli_client_dev').from('whatever').select('*');
console.log('status =', status, '| error.code =', error?.code, '| error.message =', error?.message);
```

```text
status = 406 | error.code = PGRST106 | error.message = Invalid schema: cli_client_dev
```

`PGRST106` จริง ๆ ไม่ใช่ error แบบ table-not-found — PostgREST เช็ค allowlist ก่อน local stack ของคอร์สนี้ expose แค่ `["public", "graphql_public"]` (block `[api]` ใน `tools/probe/supabase/config.toml` — ค่า default ของ CLI คือ `public` และ `graphql_public` เท่านั้น) การเพิ่ม schema ต้องแก้ `api.schemas` ใน `config.toml` แล้ว restart stack — [supabase.com/docs/guides/api/using-custom-schemas](https://supabase.com/docs/guides/api/using-custom-schemas) — บทนี้ไม่ได้ restart shared local stack เพื่อพิสูจน์ success path ดังนั้นให้เชื่อ behavior ของ schema ที่เปิดใช้แล้ว (response `{ data, error: null }` ปกติเมื่อ schema อยู่ใน list) ตามคำของ docs แทนการพิสูจน์แบบ local

## Browser vs. Node: `fetch` กับ `WebSocket`

`supabase-js@2.117.2` **ไม่** bundle fetch หรือ WebSocket polyfill มาด้วย — `package.json` ของตัวมันเองมีแค่ package พี่น้อง `@supabase/*` ทั้งห้าตัวเป็น dependency ไม่มี `cross-fetch`, `node-fetch`, `isows` หรือ `ws` เลย มันพึ่ง global ของ runtime เองล้วน ๆ:

```text
node -e "console.log(typeof globalThis.WebSocket, typeof globalThis.fetch)"
function function
```

ทั้งคู่เป็น `function` — จริงบน Node 24 (runtime ของคอร์สนี้) — เพราะ Node มี global `fetch` มาตั้งแต่ Node 18 และ global `WebSocket` มาตั้งแต่ Node 22 ส่วน browser มีทั้งคู่มาตลอด module `websocket-factory` ของ Realtime เอง อ่านตรงจาก package ที่ติดตั้งจริง เช็คหา global `WebSocket` แล้วถ้าไม่เจอจะ fail ด้วยข้อความที่ specific และแก้ได้จริง แทนที่จะเป็น `undefined is not a function` ที่งง ๆ:

```text
# tools/probe/node_modules/@supabase/realtime-js/dist/main/lib/websocket-factory.js (installed 2.117.2, read directly)
"Node.js detected but native WebSocket not found."
"Ensure you are running Node.js 22+ or provide a WebSocket implementation via the transport option."
```

## อ่านโค้ดที่ AI สร้าง

AI assistant ที่ถูกขอให้ "ทำให้ทุก request จาก client นี้ authenticated เสมอ" สร้างโค้ดนี้:

<SpotTheBug lang="ts" code={`// src/lib/supabase.ts — created once, imported everywhere
import { createClient } from '@supabase/supabase-js';
import type { Database } from './database.types';

const session = await getStoredSession(); // read whatever token is on disk right now

export const supabase = createClient<Database>(
  process.env.SUPABASE_URL!,
  process.env.SUPABASE_ANON_KEY!,
  {
    global: {
      headers: { Authorization: \`Bearer \${session?.access_token}\` },
    },
  }
);
`}>
ดูเหมือนจะแนบ token ของ user ที่ signed-in เข้าไปทุก request ได้ถูกต้อง — และมันก็แนบจริง สำหรับ token ตัวเดียว ตลอดกาล `global.headers` ถูก merge เข้าไป **ครั้งเดียว** ตอน `createClient` ทำงาน แล้ว reuse ทุก call ถัดไปจาก singleton ตัวนี้ ไม่ได้ถูก re-evaluate ตอน sign-in, sign-out หรือตอน token refresh อัตโนมัติที่ตารางค่า config ของบทนี้ระบุว่าเป็น default (`autoRefreshToken: true`) พิสูจน์ตรง ๆ ว่า: สร้าง client ด้วย `global.headers.Authorization` แบบ static แล้ว sign-in ผ่าน client **ตัวเดียวกัน** ด้วย `supabase.auth.signInWithPassword()` แล้วตรวจ header ที่ออกไปจริง (เทคนิค wire-inspection เดียวกับในบทนี้) จะเห็นว่า **ค่าเก่าก่อน sign-in ยังถูกส่งอยู่** — sign-in สำเร็จและอัปเดต session state ของ `supabase.auth` เองแล้ว แต่ header แบบ static ไม่รู้เรื่องด้วยเลย นี่คือ pattern เดียวกับที่ตัวอย่าง `global.headers` ของ docs เองใช้ถูกต้องสำหรับ Edge Function (`Authorization: req.headers.get('Authorization')!` ตั้งครั้งเดียวต่อการเรียก function ที่อายุสั้น ๆ) — bug คือเอา pattern "ตั้งครั้งเดียว" แบบเดียวกันไปใช้กับ singleton ที่อายุยืน ที่ auth state ควรจะเปลี่ยนได้ตลอดอายุของมัน ทางแก้คือแค่ไม่ต้องตั้ง `global.headers.Authorization` เลยใน client ปกติ `supabase-js` แนบ token ของ session ปัจจุบันให้ทุก request อัตโนมัติอยู่แล้ว อ่านใหม่สดทุกครั้ง ไม่ต้อง override ผ่าน `global.headers` เลย
</SpotTheBug>

## Mental Model

`createClient` ไม่ได้ "login" เข้าอะไรทั้งนั้น — มันสร้าง HTTP/WebSocket client แบบ typed บาง ๆ แล้วผูก sub-client ไม่กี่ตัว (`.auth`, `.storage`, `.functions`, `.realtime` และ query builder ของ PostgREST จาก `.from()`) เข้ากับ configuration เดียวที่แชร์กัน ทุก option ที่ส่งเข้าไปจริง ๆ ก็แค่คำถามว่า: ค่านี้ไปอยู่ใน request ตรงไหน แล้วถูกคำนวณใหม่บ่อยแค่ไหน `db.schema` กับ `global.headers` คือค่าที่ bake เข้าไปตอนสร้างแล้ว reuse; token ของ `Authorization` ใน session เป็นข้อยกเว้นเดียวที่ตั้งใจ *ไม่* bake เข้าไป แต่อ่านใหม่สดจาก live state ของ `supabase.auth` ทุก request — นี่คือเหตุผลที่ header `Authorization` แบบ static ที่เขียนเอง (`SpotTheBug` ของบทนี้) สู้กับ design ของ client เองแทนที่จะทำงานร่วมกัน พอมองว่า `createClient` เป็น "configuration object เดียว reuse ข้ามทุก request เท่าที่เป็นไปได้" ที่เหลือ — `persistSession`, `autoRefreshToken`, `global.fetch` — ก็แค่คำตอบของ "state เก็บไว้ที่ไหน แล้วใครมี intercept request ก่อนออกจาก process ได้บ้าง"

## Trade-off

- **Singleton client ฝั่ง browser เลี่ยง WebSocket connection ซ้ำซ้อนและทำให้ auth listener สอดคล้องกัน** — แลกกับการผิดจริง ๆ บน server ที่ process เดียวรองรับหลาย user แล้ว client ที่แชร์กันจะทำให้ session รั่วข้าม user
- **`global.fetch`/`global.headers` เป็นจุด intercept ที่ทรงพลังและง่าย** (พิสูจน์ด้านบนทั้งสำหรับ wire inspection และ bug ของ `Authorization` แบบ static) — แลกกับการใช้ผิดง่ายกับอะไรที่ควรจะ dynamic เพราะถูก evaluate แค่ครั้งเดียว ไม่ใช่ต่อ request
- **`.throwOnError()` ให้ call เดียวเลือก throw exception เพื่อใช้กับ error boundary หรือ `try/catch` รอบ call หลายตัว** — แลกกับ call ตัวนั้นทำงานต่างจาก `{ data, error }` call อื่น ๆ ในโค้ดเดียวกัน ซึ่งเป็นเหตุผลที่คอร์สนี้ default ให้เช็ค `error` ตรง ๆ ทุกที่
- **ไม่ bundle fetch/WebSocket polyfill ทำให้ package เล็กลงและเลี่ยง transitive dependency สองตัว** — แลกกับ runtime floor จริงแต่แคบ (Node 18+ สำหรับ fetch, Node 22+ สำหรับ WebSocket หรือต้องส่ง `transport`/`fetch` เอง)

## ความเข้าใจผิดที่พบบ่อย

- **"call ของ supabase-js ที่ fail จะ throw ต้องห่อด้วย try/catch"** พิสูจน์แล้วว่าผิด: `PGRST205` จริงของ table ที่ไม่มีอยู่ resolve เป็น `{ data: null, error }` ปกติ `try/catch` ไม่ทำงานเลย เช็ค `error` ตรง ๆ แล้วใช้ `.throwOnError()` เฉพาะตอนที่ตั้งใจอยากได้ผลตรงข้าม
- **"`global.headers` คือที่ที่ถูกต้องสำหรับแนบ token ของ user ปัจจุบัน"** พิสูจน์แล้วว่าผิด และพิสูจน์ *เหตุผล* ด้วย: มัน evaluate แค่ครั้งเดียวตอนสร้าง ไม่ใช่ต่อ request — header `Authorization` แบบ static จะอยู่รอดจาก sign-in โดยไม่เปลี่ยน เหมือน `SpotTheBug` ของบทนี้เป๊ะ client แนบ token ของ session ปัจจุบันให้อัตโนมัติอยู่แล้ว `global.headers` มีไว้สำหรับค่าที่ static จริง ๆ ตลอดอายุ client เช่น header app-version คงที่
- **"`.schema('name')` ใช้ได้กับ schema ชื่อไหนก็ได้ ตราบใดที่มีอยู่จริงใน Postgres"** พิสูจน์แล้วว่าผิด: schema ที่มีอยู่จริงแต่ไม่ได้ expose ถูกปฏิเสธด้วย `PGRST106` ก่อนที่ PostgREST จะเช็คด้วยซ้ำว่ามันมีอยู่ไหม — allowlist `api.schemas` ใน `config.toml` ของโปรเจกต์เป็นด่านแยกต่างหากที่มาก่อน
- **"`supabase-js` ต้องการ package polyfill fetch/WebSocket บน Node เหมือนเมื่อก่อน"** พิสูจน์แล้วว่าผิดจากการอ่าน `package.json` ของ package ที่ติดตั้งจริง: ไม่มี dependency `cross-fetch`/`isows`/`ws` อีกแล้ว — มันพึ่ง global `fetch` (18+) และ `WebSocket` (22+) ของ Node เอง แล้ว fallback เป็น error message จริงที่แก้ได้ (อ่านตรงจาก source ที่ติดตั้ง) แทน shim ที่ bundle มา เมื่อไม่มีทั้งคู่
