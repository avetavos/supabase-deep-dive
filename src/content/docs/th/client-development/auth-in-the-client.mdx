## ไอเดียในหนึ่งประโยค

`supabase.auth` ให้ `signUp`, `signInWithPassword` และ `signOut` มาขับเคลื่อน session, `onAuthStateChange` มาคอย sync UI ของแอปกับ session นั้นอัตโนมัติ — ตามลำดับจริงที่พิสูจน์ได้ — และกติกาเหล็กที่ต้องจำตลอดบทนี้: การเช็ค session ในโค้ดฝั่ง client เป็นแค่ความสะดวกด้าน UX ส่วน row level security บน database คือ security boundary ตัวจริง

## Flow sign-up, sign-in, sign-out แบบครบวงจร

ทุก call เหล่านี้ resolve เป็น `{ data, error }` ไม่ throw ดังนั้นต้องเช็ค `error` ก่อนเชื่อผลลัพธ์ — pattern เดียวกับที่จะถูก formalize ในบทถัดไป

```typescript
// Sign up a new user
const { data: signUpData, error: signUpError } = await supabase.auth.signUp({
  email: 'jane@example.com',
  password: 'correct-horse-battery-staple',
});

if (signUpError) {
  console.error('sign up failed:', signUpError.message);
}

// Sign in an existing user
const { data: signInData, error: signInError } = await supabase.auth.signInWithPassword({
  email: 'jane@example.com',
  password: 'correct-horse-battery-staple',
});

if (signInError) {
  console.error('sign in failed:', signInError.message);
}

// Sign out the current user
const { error: signOutError } = await supabase.auth.signOut();

if (signOutError) {
  console.error('sign out failed:', signOutError.message);
}
```

`signUp` หรือ `signInWithPassword` ที่สำเร็จจะเก็บ session (access token กับ refresh token) ไว้ใน client และทุก request ถัดไปจาก client นี้จะถูกส่งในฐานะ user ที่ authenticated แล้ว

## `onAuthStateChange`: ลำดับ event จริง พิสูจน์สด

แทนที่จะ track ด้วยมือว่า user signed in อยู่ไหม ให้ subscribe แค่ครั้งเดียว มักจะตอนแอป startup สิ่งที่ fire จริงและลำดับของมันไม่ใช่การเดาในบทนี้ — sign-in, refresh ด้วยมือ แล้ว sign-out บน client จริงตัวเดียว log ทุก event ที่เข้ามา:

```ts
// src/cli-auth-state-sequence.ts
// @run
import { createClient } from '@supabase/supabase-js';

const API_URL = process.env.SUPABASE_URL!;
const admin = createClient(API_URL, process.env.SUPABASE_SERVICE_ROLE_KEY!);

const email = 'cli-client-dev-authseq@example.com';
const password = 'cli-pw-authseq-12345';
let user = (await admin.auth.admin.listUsers()).data.users.find((u) => u.email === email);
if (!user) user = (await admin.auth.admin.createUser({ email, password, email_confirm: true })).data.user!;

const client = createClient(API_URL, process.env.SUPABASE_ANON_KEY!);
const events: string[] = [];
client.auth.onAuthStateChange((event, session) => {
  events.push(`${event} (session=${session ? 'yes' : 'no'})`);
});

await new Promise((r) => setTimeout(r, 300)); // let INITIAL_SESSION fire
await client.auth.signInWithPassword({ email, password });
await new Promise((r) => setTimeout(r, 300));

await client.auth.refreshSession(); // force a token refresh instead of waiting on the timer
await new Promise((r) => setTimeout(r, 300));

await client.auth.signOut();
await new Promise((r) => setTimeout(r, 300));

console.log('event sequence:', JSON.stringify(events));
await admin.auth.admin.deleteUser(user.id);
```

```text
event sequence: ["INITIAL_SESSION (session=no)","SIGNED_IN (session=yes)","TOKEN_REFRESHED (session=yes)","SIGNED_OUT (session=no)"]
```

Event จริงสี่ตัว เรียงตามลำดับนี้เป๊ะ: **`INITIAL_SESSION`** fire ครั้งเดียว ทันทีหลัง client ถูกสร้าง ไม่ว่าจะมี session อยู่แล้วหรือไม่ (`session=no` ที่นี่เพราะ client เริ่มใหม่); **`SIGNED_IN`** fire ตอนเรียก `signInWithPassword` ข้างบน แต่ตาม reference docs ของ SDK เองมัน fire ตอนอื่นที่เป็นการ (re-)establish session ด้วยเหมือนกัน — เช่น tab กลับมา focus — ดังนั้นโค้ดแอปควรเช็ค `session.user` ที่ได้รับ แทนที่จะสมมติว่า `SIGNED_IN` แปลว่า "เพิ่ง sign-in ใหม่จริง ๆ" เสมอ; **`TOKEN_REFRESHED`** fire ทั้งตอน background refresh อัตโนมัติ (ขับเคลื่อนด้วย `autoRefreshToken` ค่า default จากตารางค่าของบทที่แล้ว) และตามที่พิสูจน์ที่นี่ การเรียก `refreshSession()` ด้วยมือ; **`SIGNED_OUT`** fire ตอน `signOut()` และทุกครั้งที่ session กลายเป็น invalid ด้วยเหตุผลอื่นเช่นกัน (หมดอายุเกิน refresh window, ถูก revoke จากอุปกรณ์อื่น และอื่น ๆ) การผูก state ของแอปเข้ากับ callback ตัวเดียวนี้ทำให้ UI เป็นภาพสะท้อนของ session จริงของ client เสมอ ไม่ต้องจำไปเรียกมันเองหลัง auth action แต่ละครั้ง

อีกสอง event ที่บทนี้ไม่ได้ทดสอบ แต่ callback เดียวกันก็ส่งให้เหมือนกัน: **`USER_UPDATED`** (หลัง `updateUser()` สำเร็จ) และ **`PASSWORD_RECOVERY`** (แทนที่ `SIGNED_IN` ตอน user เข้าหน้าผ่าน password-recovery link)

## Session อยู่ที่ไหนจริง ๆ: browser vs. Node

`persistSession: true` เป็นค่า default แต่ *เก็บไว้ที่ไหน* ขึ้นกับ runtime ไม่ใช่คำตอบตายตัว ใน browser จะเป็น `localStorage` โดย default ใน Node — environment พิสูจน์ของคอร์สนี้ ที่ไม่มี `localStorage` global — `supabase-js` fallback เป็น store แบบ **in-memory** ที่ scope อยู่กับ client instance ตัวนั้นตัวเดียว พิสูจน์ด้วยการสร้าง client ตัวที่สองที่เป็นอิสระสมบูรณ์ใน process เดียวกัน แล้วเช็คว่ามันเห็น session ของตัวแรกไหม:

```ts
// src/cli-auth-storage-location.ts
// @run
import { createClient } from '@supabase/supabase-js';

const API_URL = process.env.SUPABASE_URL!;
const ANON_KEY = process.env.SUPABASE_ANON_KEY!;
const admin = createClient(API_URL, process.env.SUPABASE_SERVICE_ROLE_KEY!);

const email = 'cli-client-dev-storage@example.com';
const password = 'cli-pw-storage-12345';
let user = (await admin.auth.admin.listUsers()).data.users.find((u) => u.email === email);
if (!user) user = (await admin.auth.admin.createUser({ email, password, email_confirm: true })).data.user!;

const clientA = createClient(API_URL, ANON_KEY);
await clientA.auth.signInWithPassword({ email, password });
const sessionA = await clientA.auth.getSession();
console.log('clientA (signed in) session present =', !!sessionA.data.session);

const clientB = createClient(API_URL, ANON_KEY); // fresh instance, same process, no storage option passed
const sessionB = await clientB.auth.getSession();
console.log('clientB (fresh instance) session present =', !!sessionB.data.session);

await admin.auth.admin.deleteUser(user.id);
```

```text
clientA (signed in) session present = true
clientB (fresh instance) session present = false
```

`clientB` มองไม่เห็น session ของ `clientA` เลยแม้ทั้งคู่ถูกสร้างใน Node process เดียวกัน ห่างกันไม่กี่วินาที ด้วย URL และ `anon` key เดียวกันเป๊ะ — พิสูจน์ว่า default storage ใน Node เป็น in-memory ต่อ instance ไม่ใช่ shared cache ระดับ process และไม่เหมือน `localStorage` ที่แชร์กันของ brow­ser เลย นี่คือเหตุผลที่ pattern singleton จากบทที่แล้วสำคัญใน browser (client เดียว, session ที่แชร์ใน memory-หรือ-`localStorage` ตัวเดียว) และทำไม server ต้องการ adapter จริง — cookie ผ่าน `@supabase/ssr` ที่พิสูจน์แล้วในโมดูล Auth — แทนที่จะพึ่ง default in-memory นี้ข้าม request

## PKCE แบบ end to end: จาก magic-link email จริงไปถึง session จริง

`flowType: 'pkce'` เป็น flow default และแนะนำของ `supabase-js` (flow `implicit` แบบเก่าที่คืน token ตรง ๆ ใน URL fragment ยังใช้ได้อยู่แต่ไม่ใช่ default แล้ว) magic link หรือ OAuth redirect ภายใต้ PKCE จะพก authorization code `?code=` ไม่ใช่ token ตรง ๆ — client ต้องเรียก `exchangeCodeForSession(code)` เพื่อเปลี่ยน code นั้นเป็น session จริง:

```typescript
// A server-side OAuth/magic-link callback route — code + citation
// source: supabase.com/docs (_partials/oauth_pkce_flow.mdx)
export async function GET(request: Request) {
  const { searchParams, origin } = new URL(request.url);
  const code = searchParams.get('code');

  if (code) {
    const supabase = await createClient();
    const { error } = await supabase.auth.exchangeCodeForSession(code);
    if (!error) {
      return NextResponse.redirect(`${origin}/`);
    }
  }

  return NextResponse.redirect(`${origin}/auth/auth-code-error`);
}
```

`detectSessionInUrl: true` (ตารางค่าของบทที่แล้ว) ทำแบบนี้ให้อัตโนมัติสำหรับแอปฝั่ง client ล้วน ๆ ส่วน server-side callback route — ไม่มี `localStorage` ไม่มี URL ให้ auto-detect — เรียก `exchangeCodeForSession` เองแทน ตามโค้ด docs ข้างบน local stack ของคอร์สนี้ดัก email ที่ส่งออกทุกฉบับไว้ใน Mailpit ทำให้พิสูจน์ flow ทั้งหมด end to end ได้จริง ไม่ใช่แค่อ้างอิง: ส่ง magic link จริง อ่าน email จริง ตาม redirect จริง แล้ว exchange code จริง

```ts
// src/cli-auth-pkce-full-flow.ts
// @run
import { createClient } from '@supabase/supabase-js';

const API_URL = process.env.SUPABASE_URL!;
const MAILPIT_URL = 'http://127.0.0.1:55324'; // this course's fixed local Mailpit port (tools/probe/supabase/config.toml)
const email = 'cli-client-dev-pkce@example.com';

const client = createClient(API_URL, process.env.SUPABASE_ANON_KEY!, { auth: { flowType: 'pkce' } });
await client.auth.signInWithOtp({ email, options: { emailRedirectTo: 'http://127.0.0.1:3000' } });

await new Promise((r) => setTimeout(r, 500));
const list = await fetch(`${MAILPIT_URL}/api/v1/messages?limit=5`).then((r) => r.json());
const msg = list.messages.find((m: any) => m.To?.[0]?.Address === email);
const full = await fetch(`${MAILPIT_URL}/api/v1/message/${msg.ID}`).then((r) => r.json());
const verifyLink = ((full.Text || full.HTML).match(/https?:\/\/[^\s"'<>]+/g) || [])[0];
console.log('link from the real Mailpit email:', verifyLink);

// Clicking the link hits GoTrue's own /verify endpoint, which redirects to
// emailRedirectTo with the PKCE code attached — followed here with redirect: 'manual'
// instead of a real browser, to read the Location header directly.
const redirectResp = await fetch(verifyLink, { redirect: 'manual' });
const code = new URL(redirectResp.headers.get('location')!).searchParams.get('code')!;
console.log('extracted PKCE code:', code);

const { data, error } = await client.auth.exchangeCodeForSession(code);
console.log('exchangeCodeForSession error =', error?.message ?? null);
console.log('session established =', !!data.session, '| user email =', data.user?.email);

const admin = createClient(API_URL, process.env.SUPABASE_SERVICE_ROLE_KEY!);
const user = (await admin.auth.admin.listUsers()).data.users.find((u) => u.email === email);
if (user) await admin.auth.admin.deleteUser(user.id);
```

```text
link from the real Mailpit email: http://127.0.0.1:55321/auth/v1/verify?token=pkce_ee6df2f67dfa487c20b405fd1a0a508d40b204a4f359ba3e411530c9&type=magiclink&redirect_to=http://127.0.0.1:3000
extracted PKCE code: 7abcaf1d-47f2-4fda-9a0c-ac60e8266ebb
exchangeCodeForSession error = null
session established = true | user email = cli-client-dev-pkce@example.com
```

ทุก step เป็นของจริง: `pkce_...` token จริงที่ GoTrue ออกให้ใน Mailpit email จริง redirect `303` จริงจาก `/auth/v1/verify` ที่แนบ `?code=<uuid>` ต่อท้าย `emailRedirectTo` และ call `exchangeCodeForSession` จริงที่เปลี่ยน code นั้นเป็น session จริง — call เดียวกับที่ server-side callback route ข้างบนเรียก แค่ขับเคลื่อนตรง ๆ แทนที่จะผ่านการคลิกใน browser

## `getClaims()`: ยืนยันแล้วว่ามีอยู่จริงใน version นี้

บท [Sessions and JWTs](/supabase/th/auth-and-row-level-security/sessions-and-jwts/) ของโมดูล Auth พิสูจน์ `getSession()` (เร็ว ไม่ verify local-only) เทียบกับ `getUser()` (ช้ากว่า verify ผ่าน network) ด้วย token ที่ถูก tamper ไปแล้ว และครอบคลุม `getClaims()` ในฐานะตัวเลือกใหม่ ที่ verify แบบ cryptographic แต่ไม่ต้องผ่าน network ที่ official example ปัจจุบันเรียกแทน `getUser()` แล้ว — ไปอ่านการพิสูจน์ที่นั่นแทนที่จะพูดซ้ำ ยืนยันที่นี่สำหรับ version ที่ติดตั้งจริงของคอร์สนี้: `typeof supabase.auth.getClaims === 'function'` เป็น `true` บน `@supabase/supabase-js@2.117.2` ดังนั้นทุกตัวอย่างโค้ดในบทนั้นและบทนี้ถูกเช็คกับ version ที่มีมันจริง ไม่ใช่ API ในอนาคตที่ยังไม่ออก

## Protect route: ความสะดวกด้าน UX ไม่ใช่ security จริง

pattern ที่พบบ่อยฝั่ง client คือเช็ค session ก่อน render หน้าที่ป้องกันไว้ หรือก่อนยิง request ที่ต้อง authenticated:

```typescript
const {
  data: { session },
} = await supabase.auth.getSession();

if (!session) {
  redirectToLogin();
}
```

วิธีนี้มีประโยชน์จริง — เลี่ยงการ flash เนื้อหาที่ป้องกันไว้ให้ visitor ที่ signed-out เห็น และเลี่ยงการยิง request ที่รู้อยู่แล้วว่าจะ fail แต่ต้องไม่เข้าใจผิดว่านี่คือกลไก security จริง: โค้ด JavaScript ฝั่ง client ถูก inspect, แก้ไข หรือข้ามได้เสมอ และไม่มีอะไรกันคนเรียก Supabase project ของคุณตรง ๆ ด้วย token ของตัวเอง ข้าม UI ไปเลย สิ่งที่ client-side check **การันตีไม่ได้** — พิสูจน์ด้วย token ที่ถูก tamper ในบท Sessions and JWTs — คือ session ที่มันกำลังดูอยู่นั้นเป็นของจริงหรือเปล่า `getSession()` ไม่ verify signature เลยแม้แต่นิดเดียว boundary จริงที่ตัดสินว่า request จะอ่านหรือเขียน row ไหนได้คือ **row level security (RLS)** ที่ Postgres บังคับใช้เองฝั่ง server ไม่ว่า client จะเลือกเช็คหรือ render อะไรก็ตาม server-side gate ต้องใช้ `getUser()` หรือ `getClaims()` ไม่ใช่ `getSession()` — bug นั้นเป๊ะ ๆ พร้อมทางแก้ คือ `SpotTheBug` ของคอร์สนี้ในบท Sessions and JWTs

## MFA: enroll, challenge, verify — และด่าน config local จริง

Multi-factor authentication เพิ่ม factor ที่สอง (ปกติคือ TOTP authenticator app) ทับ password ยก session จาก `aal1` เป็น `aal2` (Authenticator Assurance Level — claim เดียวกับที่ decode จาก token จริงในบท Sessions and JWTs) flow คือ `enroll()` → `challenge()` → `verify()`:

```typescript
const { data: factors, error: factorsErr } = await supabase.auth.mfa.enroll({ factorType: 'totp' });
// factors.totp.qr_code — an SVG the user scans with an authenticator app
// factors.totp.secret — the same secret, for manual entry

const { data: challenge } = await supabase.auth.mfa.challenge({ factorId: factors!.id });
const { data: verified, error: verifyErr } = await supabase.auth.mfa.verify({
  factorId: factors!.id,
  challengeId: challenge!.id,
  code: userEnteredCode, // the 6-digit code from the authenticator app
});
// on success, the session is transparently upgraded to aal2
```

TOTP เปิดใช้เป็น default บน hosted Supabase project ([supabase.com/docs/guides/auth/auth-mfa](https://supabase.com/docs/guides/auth/auth-mfa)) — แต่รัน `enroll()` จริงกับ local stack ของคอร์สนี้จะได้คำตอบที่ตรงไปตรงมาว่าไม่พร้อมใช้งานที่นี่:

```ts
// src/cli-auth-mfa-enroll.ts
// @run
import { createClient } from '@supabase/supabase-js';

const API_URL = process.env.SUPABASE_URL!;
const admin = createClient(API_URL, process.env.SUPABASE_SERVICE_ROLE_KEY!);
const email = 'cli-client-dev-mfa@example.com';
const password = 'cli-pw-mfa-12345';
let user = (await admin.auth.admin.listUsers()).data.users.find((u) => u.email === email);
if (!user) user = (await admin.auth.admin.createUser({ email, password, email_confirm: true })).data.user!;

const client = createClient(API_URL, process.env.SUPABASE_ANON_KEY!);
await client.auth.signInWithPassword({ email, password }); // mfa.enroll needs a real, signed-in session

const { data, error } = await client.auth.mfa.enroll({ factorType: 'totp' });
console.log('mfa.enroll error =', error?.message ?? null);

const aal = await client.auth.mfa.getAuthenticatorAssuranceLevel();
console.log('AAL currentLevel =', aal.data?.currentLevel, '| nextLevel =', aal.data?.nextLevel);

await admin.auth.admin.deleteUser(user.id);
```

```text
mfa.enroll error = MFA enroll is disabled for TOTP
AAL currentLevel = aal1 | nextLevel = aal1
```

พูดตรง ๆ แทนที่จะหาทางเลี่ยง: `config.toml` ของ local CLI stack นี้ไม่ได้เปิด `[auth.mfa.totp]` เป็น default ดังนั้น `enroll()` ปฏิเสธถูกต้องด้วย error จริงเฉพาะเจาะจง แทนที่จะ no-op เงียบ ๆ — พิสูจน์ว่า *ด่าน* เป็นของจริง แม้ไม่มีการพิสูจน์ local ของ enrollment ที่เสร็จสมบูรณ์ `getAuthenticatorAssuranceLevel()` ยังทำงานได้และรายงาน `aal1`/`aal1` ถูกต้อง (ไม่มีการอัปเกรดค้างอยู่) สำหรับ session ที่ยังไม่ enroll นี้ โค้ดฝั่ง client ควรเรียก `getAuthenticatorAssuranceLevel()` หลัง sign-in แล้ว prompt ให้ challenge ทุกครั้งที่ `nextLevel !== currentLevel` ตาม pattern reference ของ docs เอง

## Mental Model

ทุกอย่างในบทนี้คือไอเดียเดียวที่มองจากมุมต่างกัน: client เก็บ state ที่เปลี่ยนได้ *ชิ้นเดียว* — session — และทุก API ในนี้เป็นได้แค่ทางใดทางหนึ่ง: ทาง *เปลี่ยน* state นั้น (`signInWithPassword`, `signOut`, `exchangeCodeForSession`, token refresh) หรือทาง *สังเกต* มัน (`onAuthStateChange`, `getSession`, `getUser`, `getClaims`, `getAuthenticatorAssuranceLevel`) ลำดับ event ที่พิสูจน์แล้วในบทนี้ไม่ใช่รายละเอียด implementation ที่ต้องท่องจำ — มันคือผลลัพธ์โดยตรงของ state machine นั้น: สร้าง (`INITIAL_SESSION`), establish (`SIGNED_IN`), รักษาไว้ (`TOKEN_REFRESHED` อาจหลายครั้ง) และจบ (`SIGNED_OUT`) `exchangeCodeForSession` ของ PKCE ก็แค่ call ที่เปลี่ยน state ที่บังเอิญมาผ่าน URL แทนที่จะเป็นการ submit form และธีม "UX vs. security" ทั้งบทก็ย่อลงเหลือประโยคเดียว: อะไรก็ตามที่ state machine ฝั่ง client นี้รายงานเกี่ยวกับตัวเอง น่าเชื่อถือแค่เท่าที่สิ่งสุดท้ายที่ verify มันแบบ cryptographic เท่านั้น — ซึ่งไม่เคยเป็นตัว state machine เอง มีแค่ `getUser()`/`getClaims()` ฝั่ง server หรือ RLS บน database

## Trade-off

- **Subscribe `onAuthStateChange` ครั้งเดียวทำให้ UI state sync ได้ง่ายมาก** — แลกกับ callback ที่อาจ fire บ่อยกว่าที่คิด (`SIGNED_IN` ตอน tab กลับมา focus ไม่ใช่แค่ sign-in ใหม่จริง ๆ ตาม docs ของ SDK เอง) ดังนั้นโค้ดใน callback ต้อง idempotent และเบา
- **Session แบบ in-memory บน Node เลี่ยงการแตะ disk เลยใน environment แบบ serverless/edge** — แลกกับ session ที่หายไปทันทีที่ process หรือ client instance ถูกทิ้ง ซึ่งเป็นเหตุผลที่ server จริงต้องการ cookie adapter ของ `@supabase/ssr` แทนที่จะพึ่ง default นี้
- **PKCE ไม่เอา token ไปแปะตรง ๆ ใน URL เลย** (ต่างจาก implicit flow แบบเก่า) — แลกกับ network round trip เพิ่มอีกหนึ่งครั้ง (`exchangeCodeForSession`) ก่อนจะมี session พิสูจน์แล้วด้านบนว่าเป็น step จริงที่จำเป็น ไม่ใช่ optional
- **MFA ยกระดับ assurance bar ให้ call ที่เช็คมัน** — แลกกับการไม่ทำอะไรให้ call ที่ไม่เช็ค: RLS policy หรือเช็คฝั่ง server ต้อง require `aal2` เอง (ผ่าน `auth.jwt()->>'aal'` หรือ JWT จริงของ request) MFA ถึงจะมีความหมายเกินกว่า UI ของ client เอง

## ความเข้าใจผิดที่พบบ่อย

- **"event `SIGNED_IN` ของ onAuthStateChange fire แค่ตอน sign-in ใหม่จริง ๆ เท่านั้น"** แก้ด้วย docs ของ SDK เอง อ้างตรง ๆ ในบทนี้: มัน fire ตอน re-establish session ด้วย เช่น tab กลับมา focus — เช็ค payload `session.user` ไม่ใช่แค่ชื่อ event ถ้าสิ่งที่โค้ดต้องรู้จริง ๆ คือ "user ใหม่เพิ่ง sign-in"
- **"session persist เหมือนกันไม่ว่า runtime ไหน"** พิสูจน์แล้วว่าผิด: browser default เป็น `localStorage`; Node default เป็น in-memory store scope กับ client instance เดียว พิสูจน์ที่นี่ด้วย client พี่น้องตัวที่สองใน process เดียวกันที่มองไม่เห็น session ของตัวแรกเลย
- **"PKCE แปลว่า client ไม่ต้องการ network call เลยเพื่อ sign-in เสร็จ"** พิสูจน์แล้วว่าผิด end to end: การคลิก magic link จริง redirect มาพร้อม `?code=` และ network call `exchangeCodeForSession(code)` จริงต่างหากที่เปลี่ยน code นั้นเป็น session ที่ใช้ได้ — ข้าม call นั้นไป แค่ redirect เฉย ๆ ไม่ได้อะไรเลย
- **"claim `aal` ของ JWT อยู่ใน session.user.app_metadata"** พิสูจน์แล้วว่าผิดจาก `SpotTheBug` ของบทนี้: `aal` เป็น claim ระดับบนสุดของ token เอง (decode ตรง ๆ ในบท Sessions and JWTs) ไม่เคย copy เข้า `app_metadata` เลย วิธีอ่านที่ถูกต้อง สร้างมาเพื่อสิ่งนี้โดยเฉพาะ คือ `supabase.auth.mfa.getAuthenticatorAssuranceLevel()`
