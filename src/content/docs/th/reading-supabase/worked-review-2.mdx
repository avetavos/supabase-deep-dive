prompt ที่ให้ไปคือ: *"สร้าง file sharing: user อัปโหลดไฟล์เข้าโฟลเดอร์ตัวเอง มี resumable upload สำหรับไฟล์ใหญ่ และสร้าง share link ที่ใช้ได้กับใครก็ตามที่มี URL"* สิ่งที่ตามมาอ่านดูเหมือน draft แรกที่ทำงานได้จริง -- bucket สร้างได้, upload สำเร็จ, share link เปิดในหน้าต่าง incognito ใหม่โดยไม่ต้อง login ส่วนสุดท้ายนั่นแหละคือกับดัก: "เปิดได้โดยไม่ต้อง login" คือฟีเจอร์ที่ตั้งใจสำหรับ share link แต่เป็นพฤติกรรมที่เกิดขึ้นโดยไม่ตั้งใจกับทุกอย่างอื่นในรีวิวนี้ มันมี **บั๊กจริง 11 ตัว** ดูที่ **[AI bug catalog](/supabase/th/reading-supabase/ai-bug-catalog/)** สำหรับรูปแบบทั่วไปเบื้องหลังหลายตัว (22, 23, 24, 25, 16, 17 ล้วนโผล่ซ้ำที่นี่ในรูปแบบเฉพาะของ Storage หรือ Edge Function) ทุกข้อกล่าวอ้างด้านล่างถูกพิสูจน์บน local stack ของคอร์สนี้เอง -- `curl` จริงยิง `supabase_storage_probe` (storage-api `1.72.1`) และ process `supabase functions serve` จริงสำหรับ Edge Function ของรีวิวนี้เอง ซึ่งถูกหยุดอีกครั้งทันทีที่ทุกข้อพิสูจน์ด้านล่างถูกเก็บครบ

import * as tus from 'tus-js-client';

export function uploadLargeFile(file: File, userId: string) {
  const upload = new tus.Upload(file, {
    endpoint: `${process.env.SUPABASE_URL}/storage/v1/upload/resumable`,
    headers: {
      authorization: `Bearer ${process.env.SUPABASE_ANON_KEY}`,
      'x-upsert': 'true',

    chunkSize: 4 * 1024 * 1024, // 4MB chunks
    metadata: {

      objectName: `${userId}/${file.name}`,
      contentType: file.type,
      cacheControl: 3600,
    },
    onError: (error) => console.error('upload failed', error),
    onSuccess: () => console.log('upload complete'),
  });
  upload.start();
}

## เดินรีวิวทีละจุด

### public bucket "เพื่อความง่าย"

`storage.buckets` ถูก insert ด้วย `public: true` พิสูจน์แล้ว: ไฟล์ที่อัปโหลดผ่าน path ที่ policy เช็คตามปกติ กลับอ่านได้จาก request ที่**ไม่มี credential อะไรเลย**:

```bash
# scripts/reading-supabase/worked-review-2/public-bucket-leak.sh
curl -s -w "\nHTTP=%{http_code}\n" "$SUPABASE_URL/storage/v1/object/public/wr-files/$DANA_ID/secret-report.txt"
```

```text
dana's private-looking file

HTTP=200
```

ไม่มี `Authorization` ไม่มีแม้แต่ `apikey` -- endpoint public object (`/storage/v1/object/public/...`) คือ path เดียวเทียบเท่า PostgREST ที่**ไม่ประเมิน RLS ของ `storage.objects` เลย**สำหรับ bucket ที่ public ตามการออกแบบ เพราะ "public" หมายความแบบนั้นจริง ๆ

<SpotTheBug lang="sql" code={`insert into storage.buckets (id, name, public)
values ('wr-files', 'wr-files', true);
-- AI comment: "public for simplicity, we'll lock it down later"`}>
ทุก RLS policy ที่เขียนให้ bucket นี้ในส่วนหลังของ migration เดียวกันนั้นถูกต้องจริง ๆ แต่ไม่มีผลอะไรเลยกับการอ่าน เพราะ `public: true` เปลี่ยนเส้นทางการอ่านให้อ้อม RLS ของ `storage.objects` ไปทั้งหมดผ่าน endpoint แยกต่างหาก -- "เดี๋ยวค่อยล็อกทีหลัง" อธิบายขั้นตอนที่ต้องเกิดที่ bucket เอง ไม่ใช่ policy ที่จะมาชดเชยได้ วิธีแก้คือ `public: false` ตั้งแต่ migration แรก การเข้าถึงแบบ "share" ต่อไฟล์คือ **signed URL** (ด้านล่าง) ไม่ใช่ public ระดับ bucket เด็ดขาด
</SpotTheBug>

### ไม่มีการ scope โฟลเดอร์ -- รูปแบบ path เป็นแค่การตกแต่ง ไม่ใช่การบังคับใช้

policy `insert`/`select` ที่ AI สร้างเช็คแค่ `bucket_id = 'wr-files'` รูปแบบ path `$userId/$filename` ใน upload client เป็นแค่**ธรรมเนียม** ไม่มี policy ไหนตรวจสอบมันเลย พิสูจน์แล้ว: Erin ที่ไม่มีความสัมพันธ์อะไรกับ Dana เลย เขียนตรงเข้าไปในสิ่งที่หน้าตาเหมือนโฟลเดอร์ของ Dana:

```bash
# scripts/reading-supabase/worked-review-2/no-folder-scoping.sh
curl -s -w "\nHTTP=%{http_code}\n" -X POST "$SUPABASE_URL/storage/v1/object/wr-files/$DANA_ID/erin-intrusion.txt" \
  -H "Authorization: Bearer $ERIN_TOKEN" -H "apikey: $SUPABASE_ANON_KEY" -H "Content-Type: text/plain" \
  --data-binary @erin-intrusion.txt
```

```text
{"Key":"wr-files/56d4732b-ab57-4f1b-a6e0-a667455cf4a4/erin-intrusion.txt","Id":"7fbc5a00-51f1-4673-bce8-14cdb596d48f"}
HTTP=200
```

<SpotTheBug lang="sql" code={`create policy wr_files_insert on storage.objects
  for insert to authenticated
  with check ( bucket_id = 'wr-files' );`}>
นี่คือฝาแฝดฝั่ง storage ของ [ai-bug-catalog entry 22](/supabase/th/reading-supabase/ai-bug-catalog/): การเช็ค `bucket_id` อย่างเดียว scope แค่ไปที่ **bucket** ไม่เคยไปถึง path ข้างในเลย client code ที่ upload ไปที่ `${userId}/...` เสมอ สร้าง *ภาพลวงตา* ของการแยก per-user โดยไม่มีการบังคับใช้จริงเลย -- authenticated user คนไหนก็เขียน (และด้วย select policy ที่คู่กัน อ่าน) path ไหนในถังก็ได้ วิธีแก้คือ `(storage.foldername(name))[1] = auth.uid()::text` ในทุก `using`/`with check` ของ policy พิสูจน์ด้านล่างว่าปฏิเสธ request เดียวกันเป๊ะ
</SpotTheBug>

### `upsert: true` มี insert กับ update policy แต่ไม่มี `select` policy

TUS client ตั้ง `x-upsert: true` และ migration หลัง (ไม่ได้โชว์ข้างบน) เพิ่ม `update` policy ที่ scope ตามโฟลเดอร์ถูกต้อง -- แต่ไม่เคยมี `select` policy เลย ด้วยเหตุผลว่า "insert กับ update ได้อยู่แล้ว จะต้อง select ทำไม" พิสูจน์ด้วยการ re-upload path ที่มีอยู่แล้วจริง:

```bash
# scripts/reading-supabase/worked-review-2/upsert-no-select.sh
curl -s -w "\nHTTP=%{http_code}\n" -X PUT "$SUPABASE_URL/storage/v1/object/wr-files/$DANA_ID/secret-report.txt" \
  -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $SUPABASE_ANON_KEY" -H "Content-Type: text/plain" -H "x-upsert: true" \
  --data-binary @dana-secret-v2.txt
```

```text
{"statusCode":"403","error":"Unauthorized","message":"new row violates row-level security policy","code":"AccessDenied"}
HTTP=400
```

<SpotTheBug lang="sql" code={`create policy wr_files_insert_own_folder on storage.objects for insert to authenticated with check (...);
create policy wr_files_update_own_folder on storage.objects for update to authenticated using (...);
-- no select policy -- "they can already insert and update"`}>
ตรงกับ [ai-bug-catalog entry 23](/supabase/th/reading-supabase/ai-bug-catalog/) เป๊ะ: `upsert` compile เป็น `INSERT ... ON CONFLICT DO UPDATE` และ Postgres ต้องการเห็นแถวที่มีอยู่แล้วผ่าน select-policy ถึงจะประเมิน conflict path ได้ -- ถ้าไม่มี select policy การเช็คนั้นเองก็ถูกปฏิเสธ เรียกเดียวกันเป๊ะที่สำเร็จบน path ใหม่เอี่ยม (insert ล้วน ๆ) กลับ fail ทันทีที่ path เดิมถูก re-upload โดยไม่มีข้อความไหนพูดถึงคำว่า "select" เลยสักคำ วิธีแก้ พิสูจน์ด้านล่าง คือเพิ่ม select policy: request เดียวกันเป๊ะก็สำเร็จ
</SpotTheBug>

### signed URL ที่มีอายุ 10 ปี

`createSignedUrl(path, 315360000)` -- 315,360,000 วินาที พิสูจน์แล้ว: API ยอมรับมันโดยไม่ validate อะไรเลย และ token ที่ออกมาก็มีระยะเวลานั้นจริง:

```bash
# scripts/reading-supabase/worked-review-2/ten-year-signed-url.sh
curl -s -X POST "$SUPABASE_URL/storage/v1/object/sign/wr-files/$DANA_ID/secret-report.txt" \
  -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $SUPABASE_ANON_KEY" -H "Content-Type: application/json" \
  -d '{"expiresIn": 315360000}'
```

```text
{"signedURL":"/object/sign/wr-files/56d4732b-.../secret-report.txt?token=eyJhbGc..."}
HTTP=200
```

decode claim `iat`/`exp` ของ token ที่คืนมายืนยันสิ่งนี้ เป็นวินาที:

```text
{'url': 'wr-files/56d4732b-.../secret-report.txt', 'scope': 'download', 'iat': 1790671228, 'exp': 2106031228}
years: 9.99315537303217
```

<SpotTheBug lang="ts" code={`.createSignedUrl(path, 315360000) // "a share link that never expires, basically"`}>
ไม่มี cap ฝั่ง server บน `expiresIn` ที่จะจับเรื่องนี้ได้เลย -- ยืนยันด้านบนด้วย request จริงที่ถูกยอมรับ "share link" ควรจะหมดอายุ; signed URL ที่มีอายุยืนยาวกว่า session, การเปลี่ยนรหัสผ่าน และกระบวนการ offboarding ของบริษัทจริงแทบทุกกรณี ในทางปฏิบัติก็คือรหัสผ่านที่สองที่เพิกถอนไม่ได้สำหรับไฟล์นั้น เพราะ signed URL ของ Supabase Storage เพิกถอนทีละอันก่อนหมดอายุ (`exp`) ไม่ได้ -- ทางเดียวที่จะตัดทิ้งก่อนกำหนดคือ rotate signing mechanism ระดับ bucket/project ซึ่งทำให้ signed URL ที่ยังค้างอยู่ตัวอื่นทั้งหมดใช้ไม่ได้ไปด้วย วิธีแก้คือกำหนดวันหมดอายุสั้น ๆ อย่างตั้งใจ (นาทีถึงชั่วโมงต้น ๆ สำหรับ share link เลือกตามฟีเจอร์ ไม่ใช่ตัวเลขที่อ่านได้ว่า "แทบไม่หมดอายุเลย")
</SpotTheBug>

### `cacheControl: 3600` เป็นตัวเลข และเป็นค่าวินาทีดิบไม่ว่าจะทางไหน

มีความผิดพลาดแยกกันสองอย่างซ้อนอยู่บน field เดียว อย่างแรก metadata ของ TUS ตั้ง `cacheControl: 3600` -- เป็น **number** -- ในขณะที่ type คือ `string`:

```ts
// @expect-error Type 'number' is not assignable to type 'string'.
import { createClient } from '@supabase/supabase-js';
const supabase = createClient('http://x', 'x');
await supabase.storage.from('wr-files').upload('x/y.txt', new Blob(), {
  cacheControl: 3600,
});
```

```text
error TS2322: Type 'number' is not assignable to type 'string'.
```

อย่างที่สอง แม้แก้เป็น string `'3600'` แล้ว ค่านั้นก็ถูกใช้**ตามตัวอักษรเป๊ะ**เป็นเนื้อหาของ header ไม่ถูกแปลงเป็น `Cache-Control` directive ที่ถูกต้อง:

```bash
# scripts/reading-supabase/worked-review-2/cachecontrol-literal.sh
curl -s -X POST "$SUPABASE_URL/storage/v1/object/wr-files/$DANA_ID/cache-test.txt" \
  -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $SUPABASE_ANON_KEY" -H "cache-control: 3600" \
  --data-binary @dana-secret.txt
curl -sI "$SUPABASE_URL/storage/v1/object/wr-files/$DANA_ID/cache-test.txt" -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $SUPABASE_ANON_KEY" | grep -i cache-control
```

```text
cache-control: 3600
```

<SpotTheBug lang="ts" code={`metadata: {
  ...
  cacheControl: 3600,
},`}>
`Cache-Control: 3600` (เปล่า ๆ ไม่มีชื่อ directive) ไม่ใช่ HTTP ที่ถูกต้อง -- cache ที่ทำตาม spec ไม่มีข้อผูกมัดต้องเคารพมันเลย และยืนยันข้างบน storage API เก็บและคืนค่าตามตัวอักษรที่ได้รับมาเป๊ะ ไม่มีการ validate เลยว่ามันเป็น directive จริงหรือเปล่า browser หรือ CDN จะทำอะไรกับ header ที่ค่าไม่ถูกต้องนั้นไม่มีการรับประกันอะไรเลย วิธีแก้คือ `cacheControl: '3600'` (เป็น string ผ่าน `tsc`) จัดรูปแบบเป็น directive จริง -- `'max-age=3600'` -- ซึ่งเป็นสิ่งที่ตัวอย่างจริงอื่น ๆ ในบท Storage ของคอร์สนี้ใช้กันหมด
</SpotTheBug>

### TUS chunk size ไม่ใช่ 6MB -- และช่องว่าง local/hosted ที่ควรพูดออกมาดัง ๆ

docs ชัดเจนและแคบมากตรงนี้ อ้างตรง ๆ จาก [supabase.com/docs/guides/storage/resumable-uploads](https://supabase.com/docs/guides/storage/resumable-uploads) (ดึงมาใหม่สำหรับรีวิวนี้): *"chunkSize: 6 * 1024 * 1024, // NOTE: it must be set to 6MB (for now) do not change it."* client ที่ AI สร้างตั้ง `chunkSize: 4 * 1024 * 1024` พิสูจน์ตรง ๆ กับ bucket ของรีวิวนี้เอง -- upload จริง 10,000,000 ไบต์ chunk แรกพอดี 4,000,000 ไบต์ (ไม่ใช่ 6MB):

```bash
# scripts/reading-supabase/worked-review-2/tus-wrong-chunk.sh
curl -s -w "\nHTTP=%{http_code}\n" -X PATCH "$LOCATION" \
  -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $SUPABASE_ANON_KEY" \
  -H "Tus-Resumable: 1.0.0" -H "Upload-Offset: 0" -H "Content-Type: application/offset+octet-stream" \
  --data-binary @wr-chunk1-4mb.bin
```

```text
HTTP=204
```

...และ upload เต็ม 10,000,000 ไบต์เสร็จสมบูรณ์โดยไม่มี error เกิดขึ้นตรงไหนเลย:

```text
{"id":"...","bucket_id":"wr-files","size":10000000,...}
```

<SpotTheBug lang="ts" code={`chunkSize: 4 * 1024 * 1024, // 4MB chunks`}>
บน **local stack นี้โดยเฉพาะ** `docker exec supabase_storage_probe env` แสดง `STORAGE_BACKEND=file` -- backend เป็น filesystem ไม่ใช่ S3 multipart backend ที่ hosted Supabase ใช้ ซึ่งเป็นเหตุผลพอดีว่าทำไมข้อกำหนด 6MB (ข้อจำกัด minimum-part-size ของ S3 multipart ที่ docs ส่งต่อมาตรง ๆ ไม่ใช่ limit ที่ Supabase ตั้งขึ้นเอง) ไม่เคยทำให้เกิด error จริงที่นี่ พิสูจน์ไว้ข้างบน การส่ง client ตัวนี้เป๊ะไปที่ **hosted** Supabase (S3-backed) คาดว่าจะ fail จริงและต่างออกไป ตามคำเตือนชัดเจนในตัว docs เอง -- นี่คือช่องว่าง local-กับ-hosted ของจริงที่รีวิวนี้ตั้งใจพูดออกมาดัง ๆ แทนที่จะกลบไว้: test ที่ผ่านแค่ local ที่นี่คือความมั่นใจปลอม วิธีแก้ง่าย ๆ คือทำตาม docs ตามตัวอักษร: `chunkSize: 6 * 1024 * 1024` ไม่เปลี่ยนแปลง
</SpotTheBug>

### Edge Function เซ็น URL ด้วย anon key -- RLS บล็อกทุกคน รวมถึงเจ้าของไฟล์เองด้วย

function body ของ `share-link` สร้าง Supabase client ด้วย `SUPABASE_ANON_KEY` และไม่เคย forward `Authorization` header ของผู้เรียกเลย ทุก request ที่ function ทำจึงรันในฐานะ anonymous จริง ๆ -- ไม่มี `auth.uid()` เลย พิสูจน์แล้ว: Dana เจ้าของไฟล์ที่ authenticated จริง ขอ link ไปที่ไฟล์ของตัวเองจาก function:

```bash
# scripts/reading-supabase/worked-review-2/edge-anon-blocks-owner.sh
curl -s -w "\nHTTP=%{http_code}\n" -X POST "$FUNCTIONS_URL/wr-share-link-anon" \
  -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $ANON_KEY" -H "Content-Type: application/json" \
  -d '{"path":"'"$DANA_ID"'/secret-report.txt"}'
```

```text
{"data":null,"error":{"name":"StorageApiError","message":"Object not found","status":400,"statusCode":"404","code":"NoSuchKey"}}
HTTP=200
```

function เองคืน `HTTP 200` -- *request* ไปที่ function สำเร็จ -- ในขณะที่ *storage call ข้างในมัน* fail กับทุกคน ด้วยข้อความ error ("Object not found") ที่ไม่ให้เบาะแสเลยว่าสาเหตุจริงคือ RLS ปฏิเสธ request ที่ไม่มี identity เลย ไม่ใช่ไฟล์ที่หายไป

<SpotTheBug lang="ts" code={`const client = createClient(
  Deno.env.get('SUPABASE_URL')!,
  Deno.env.get('SUPABASE_ANON_KEY')!,
)
const { data, error } = await client.storage.from('wr-files').createSignedUrl(path, ...)`}>
นี่คือ failure mode ตรงข้ามของ [ai-bug-catalog entry 25](/supabase/th/reading-supabase/ai-bug-catalog/) (ที่ ship `service_role` กว้างเกินไป) -- ที่นี่ function scope แคบเกินไป และ RLS -- ที่ป้องกันผู้เรียกอื่นทุกคนอย่างถูกต้อง -- ก็บล็อกคนเดียวที่ควรจะสำเร็จด้วย เพราะ function ไม่เคยระบุตัวตนว่าใครเป็นคนเรียกจริง ๆ วิธีแก้ไม่ใช่แค่ "เปลี่ยนไปใช้ `service_role`" เฉย ๆ (แค่นั้นจะสร้างบั๊ก service_role-อยู่ผิดที่แบบรีวิวก่อนหน้าขึ้นมาใหม่ ทำให้ใครก็ขอไฟล์ของใครก็ได้) -- แต่คือ `service_role` ที่ใช้**หลังจาก**ที่ function ตรวจสอบตัวตนผู้เรียกจริงแล้ว และเช็คว่า path ที่ขอเป็นของเขาจริง พิสูจน์ด้านล่าง
</SpotTheBug>

### header CORS ที่หายไปบน response จริง -- ถูกบดบังโดย Kong บน `OPTIONS` ตอนอยู่ local

ทั้งสอง function ที่ AI สร้างไม่ได้ตั้ง CORS header ของตัวเองเลย บน **local stack นี้** Kong ตอบ `OPTIONS` preflight เองก่อนที่ function ไหนจะเห็น request เลยด้วยซ้ำ (บันทึกไว้แล้วใน [Writing and Invoking a Function](/supabase/th/edge-functions/writing-and-invoking-a-function/)) -- ทำให้การ probe ด้วย `OPTIONS` กับทั้งสอง function หน้าตาเหมือนกันเป๊ะและไม่ให้สัญญาณอะไรเลย ความต่างจริง ๆ โผล่แค่ใน response จริงเท่านั้น:

```bash
# scripts/reading-supabase/worked-review-2/cors-real-response.sh
curl -s -i -X POST "$FUNCTIONS_URL/wr-share-link" -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $ANON_KEY" \
  -H "Content-Type: application/json" -H "Origin: https://example.com" -d '{"path":"'"$DANA_ID"'/secret-report.txt"}' \
  | grep -i access-control

curl -s -i -X POST "$FUNCTIONS_URL/wr-share-link-anon" -H "Authorization: Bearer $DANA_TOKEN" -H "apikey: $ANON_KEY" \
  -H "Content-Type: application/json" -H "Origin: https://example.com" -d '{"path":"'"$DANA_ID"'/secret-report.txt"}' \
  | grep -i access-control
```

```text
--- fixed function's real response headers ---
access-control-allow-origin: *
access-control-allow-headers: authorization, apikey, content-type
access-control-allow-methods: POST, OPTIONS

--- broken function's real response headers ---
Access-Control-Allow-Origin: *
(nothing else -- no access-control-allow-headers, no access-control-allow-methods, from the function itself)
```

<SpotTheBug lang="ts" code={`Deno.serve(async (req) => {
  const { path } = await req.json()
  // no OPTIONS handling, no CORS headers set anywhere in this function
  ...
})`}>
Kong ใส่ `Access-Control-Allow-Origin: *` เปล่า ๆ ลงทุก response อยู่แล้วไม่ว่าจะยังไง ซึ่งเป็นตัวการที่ทำให้บั๊กนี้มองไม่เห็นเลยจาก `curl` OPTIONS probe และจากการ test local ทั่วไป -- การเช็ค preflight ของ browser จริงต้องการ `Access-Control-Allow-Headers` ที่ระบุทุก header ที่ไม่ใช่ simple header ที่ request จริงส่งไป (ที่นี่คือ `authorization` กับ `apikey`) อย่างชัดเจนด้วย ซึ่งมีแค่ function ที่แก้แล้วที่ตั้งไว้ วิธีแก้คือตอบ `OPTIONS` อย่างชัดเจนและตั้ง CORS header เดียวกันบนทุก response พิสูจน์ไว้ข้างบน ไม่พึ่ง default ของ gateway
</SpotTheBug>

### `verify_jwt` -- และช่องว่างของ shared stack ที่ควรพูดตรง ๆ

ทั้งสอง function ไม่ได้ตั้ง `verify_jwt = false` ดังนั้น default (`true`) ควรจะ gate ทุก request ที่ชั้น gateway ก่อนที่ code ของ function เองจะรัน -- ตรงตามที่พิสูจน์ไว้แล้วสำหรับ `edge-hello` ใน [Writing and Invoking a Function](/supabase/th/edge-functions/writing-and-invoking-a-function/) พิสูจน์กับ function**เดิมนั้น** บน shared stack เดียวกันเป๊ะ ตอนนี้เลย:

```bash
# scripts/reading-supabase/worked-review-2/verify-jwt-existing-function.sh
curl -s -w "\nHTTP=%{http_code}\n" "$FUNCTIONS_URL/edge-hello"
```

```text
{"code":"UNAUTHORIZED_NO_AUTH_HEADER","message":"Missing authorization header","msg":"Missing authorization header"}
HTTP=401
```

แต่ request ที่ไม่มี header เหมือนกันเป๊ะ ยิงไปที่ function**ของรีวิวนี้เองที่เพิ่งเพิ่มใหม่** กลับไม่ถูก gateway ปฏิเสธเลย -- มันไปถึง code ของ function เอง ซึ่งคืน `401` ของตัวเองแทน:

```bash
# scripts/reading-supabase/worked-review-2/verify-jwt-new-function.sh
curl -s -w "\nHTTP=%{http_code}\n" -X POST "$FUNCTIONS_URL/wr-share-link" -H "apikey: $ANON_KEY" -H "Content-Type: application/json" -d '{"path":"x"}'
```

```text
{"error":"not authenticated"}
HTTP=401
```

<Callout title="artifact ของ shared stack ไม่ใช่คุณสมบัติด้าน security">
harness ของคอร์สนี้ไม่เคย restart shared local stack เลย (ตาม hard rules ของโมดูลนี้เอง) -- และ declarative gateway config ของ Kong รวมถึง route `verify_jwt` ต่อ function ถูก provision ตอนที่ stack (หรือ `supabase functions serve`) เริ่มทำงานจากรายการ function บน disk **ณ ตอนนั้น** function ที่ถูกเพิ่มเข้าไปใน filesystem หลังจากนั้น บน shared stack ที่รันอยู่แล้ว จะถูก serve โดย Edge Runtime แต่ไม่เคยได้การเช็คระดับ gateway นั้นต่อสายย้อนหลังให้เลยถ้าไม่ restart ซึ่งคอร์สนี้ตั้งใจไม่ทำเด็ดขาด นี่คือ artifact ของการพัฒนาบน local/shared stack ยืนยันด้านบนด้วยการเช็คเดียวกันที่สำเร็จกับ function *เก่า* (`edge-hello`) แต่ fail กับ function *ใหม่เอี่ยม* บน stack ที่รันอยู่*ตัวเดียวกัน* -- ไม่ใช่ข้อความเกี่ยวกับ hosted Supabase ซึ่ง provision `verify_jwt` ต่อ function ตอน deploy นี่คือเหตุผลพอดีที่ function ที่แก้แล้วในรีวิวนี้ตรวจสอบตัวตนผู้เรียกใน**code ของตัวเอง**ด้วย (`anon.auth.getUser(token)`) แทนที่จะเชื่อ config `verify_jwt` เพียงอย่างเดียว -- ชั้นป้องกันเดียวที่ยังถูกต้องเสมอไม่ว่า gateway จะอยู่ในสถานะไหน
</Callout>

```ts
// supabase/functions/wr-share-link/index.ts
import { createClient } from 'jsr:@supabase/supabase-js@2'

const corsHeaders = {
  'Access-Control-Allow-Origin': '*',
  'Access-Control-Allow-Headers': 'authorization, apikey, content-type',
  'Access-Control-Allow-Methods': 'POST, OPTIONS',
}

Deno.serve(async (req) => {
  if (req.method === 'OPTIONS') {
    return new Response(null, { headers: corsHeaders })
  }

  const authHeader = req.headers.get('Authorization') ?? ''
  const token = authHeader.replace('Bearer ', '')

  const anon = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_ANON_KEY')!,
  )
  const { data: userData, error: userErr } = await anon.auth.getUser(token)
  if (userErr || !userData.user) {
    return new Response(JSON.stringify({ error: 'not authenticated' }), {
      status: 401,
      headers: { ...corsHeaders, 'Content-Type': 'application/json' },
    })
  }

  const { path } = await req.json()
  const ownerFolder = path.split('/')[0]
  if (ownerFolder !== userData.user.id) {
    return new Response(JSON.stringify({ error: 'forbidden: not your file' }), {
      status: 403,
      headers: { ...corsHeaders, 'Content-Type': 'application/json' },
    })
  }

  const admin = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!,
  )
  const { data, error } = await admin.storage.from('wr-files').createSignedUrl(path, 3600)
  return new Response(JSON.stringify({ data, error }), {
    headers: { ...corsHeaders, 'Content-Type': 'application/json' },
  })
})
```

```ts
// src/reading-supabase/worked-review-2/folder-isolation.ts
// @run
import { createClient } from '@supabase/supabase-js';

const url = process.env.SUPABASE_URL!;
const anonKey = process.env.SUPABASE_ANON_KEY!;
const serviceKey = process.env.SUPABASE_SERVICE_ROLE_KEY!;
const admin = createClient(url, serviceKey);
const stamp = Date.now();

async function makeUser(email: string) {
  const { data, error } = await admin.auth.admin.createUser({
    email,
    password: 'wr-Passw0rd!',
    email_confirm: true,
  });
  if (error) throw error;
  const signInClient = createClient(url, anonKey);
  const { data: signIn, error: sErr } = await signInClient.auth.signInWithPassword({
    email,
    password: 'wr-Passw0rd!',
  });
  if (sErr) throw sErr;
  return { id: data.user.id, client: createClient(url, anonKey, {
    global: { headers: { Authorization: `Bearer ${signIn.session!.access_token}` } },
  }) };
}

async function main() {
  const dana = await makeUser(`wr+run-dana-${stamp}@example.com`);
  const erin = await makeUser(`wr+run-erin-${stamp}@example.com`);

  const { error: uploadErr } = await dana.client.storage
    .from('wr-files')
    .upload(`${dana.id}/report.txt`, new Blob(['dana report']), { contentType: 'text/plain' });
  if (uploadErr) throw uploadErr;
  console.log('dana uploaded into her own folder');

  const { error: intrusionErr } = await erin.client.storage
    .from('wr-files')
    .upload(`${dana.id}/erin-intrusion.txt`, new Blob(['intrusion']), { contentType: 'text/plain' });
  if (!intrusionErr) {
    throw new Error('folder isolation broken -- erin wrote into dana\'s folder');
  }
  console.log('erin correctly blocked from writing into dana\'s folder:', intrusionErr.message);

  const { data: signedUrl, error: signErr } = await dana.client.storage
    .from('wr-files')
    .createSignedUrl(`${dana.id}/report.txt`, 60);
  if (signErr) throw signErr;
  console.log('dana signed her own file:', !!signedUrl.signedUrl);

  await admin.auth.admin.deleteUser(dana.id);
  await admin.auth.admin.deleteUser(erin.id);
  console.log('folder isolation test passed');
}

main().catch((err) => {
  console.error(err);
  throw err;
});
```

## สิ่งที่เปลี่ยนและทำไม

| # | บั๊ก | ทางแก้ |
|---|---|---|
| 1 | สร้าง bucket ด้วย `public: true` "เพื่อความง่าย" | `public: false` -- พิสูจน์แล้ว: request ไม่ระบุตัวตนอ่านไฟล์ได้โดยไม่มี credential เลยถ้าไม่แก้ |
| 2 | storage policy เช็คแค่ `bucket_id` ไม่มีโฟลเดอร์ | `(storage.foldername(name))[1] = auth.uid()::text` -- พิสูจน์แล้ว: authenticated user คนไหนก็เขียนโฟลเดอร์ไหนก็ได้ถ้าไม่แก้ |
| 3 | `upsert: true` มี insert/update policy ไม่มี select | เพิ่ม `select` policy -- RLS fail จริงตอน re-upload ถ้าไม่แก้ |
| 4 | `createSignedUrl(path, 315360000)` -- อายุ 10 ปี | อายุสั้น ตั้งใจกำหนด -- พิสูจน์แล้ว: ไม่มี cap ฝั่ง server จับเรื่องนี้เลย |
| 5 | `cacheControl: 3600` (number) และถูกใช้เป็นค่า header ตามตัวอักษร | `cacheControl: 'max-age=3600'` -- error `tsc` จริงถ้าไม่แก้ และเป็น header ที่ไม่ถูกต้องทั้งสองทาง |
| 6 | TUS `chunkSize: 4 * 1024 * 1024` | `chunkSize: 6 * 1024 * 1024` ตาม docs -- local (file-backed) ยอมรับมันอยู่ดี; hosted (S3-backed) จะไม่ยอม |

## Mental Model

บั๊กระดับ bucket (1) กับบั๊กทรง RLS (2, 3) มีคุณสมบัติร่วมกันอย่างหนึ่ง: มัน compile ผ่าน มันรันได้ และ request ที่**ผิด**คือตัวที่ "ทำงานได้" -- public bucket เสิร์ฟทุกคนอย่างมีความสุข policy ไม่มีโฟลเดอร์ปล่อยให้ upload ไหนก็ผ่าน `upsert` บน path ใหม่สำเร็จและ fail แค่ตอนครั้งที่สอง บั๊ก identity สอง Edge Function (7 และตัวตรงข้ามในเวอร์ชันที่แก้แล้ว) แสดงรูปทรงเดียวกันจากคนละทิศ: กว้างเกินไป (สไตล์ catalog-25) ไม่พังให้เห็นแต่เปิดให้ทุกคน แคบเกินไป (บั๊กจริงของรีวิวนี้) พังคนเดียวที่ควรสำเร็จ บั๊กที่เกี่ยวกับ infrastructure (6, 10, 11) เป็นบั๊กที่ผิดได้แบบซื่อที่สุด: แต่ละตัวมีข้อกำหนดหรือ limit จริงที่มีเอกสารรองรับ แต่ไม่แสดงเป็น error บน **local stack เฉพาะนี้** ด้วยเหตุผลที่ควรเข้าใจ (file backend เทียบกับ S3 backend; จังหวะ snapshot config ของ Kong; flag ที่ comment ไว้บน local) มากกว่าจะจำไว้ว่า "ที่นี่มันก็ใช้ได้"

## Trade-offs

- **public bucket เป็นตัวเลือกที่ถูกต้องจริง ๆ สำหรับเนื้อหาที่ตั้งใจให้ public** (asset การตลาด, avatar สาธารณะ) -- บั๊กที่นี่ไม่ใช่ "public bucket ผิด" แต่คือการใช้มันกับเนื้อหาที่คำอธิบายฟีเจอร์เรียกว่า "sharing" ซึ่งบอกเป็นนัยถึงการเข้าถึงที่ scope ได้และเพิกถอนได้ ที่ public bucket แสดงออกไม่ได้เลย
- **`service_role` ข้างใน Edge Function ที่ใช้หลังจากเช็ค identity ชัดเจนแล้ว เป็น code ที่มากกว่าการเชื่อ RLS อย่างเดียว** -- แลกมาด้วยประโยชน์ที่ function บังคับใช้ logic การอนุญาตที่ RLS แสดงออกเองไม่ได้จริง ๆ (ที่นี่คือ "โฟลเดอร์ต้องตรงกับผู้เรียกที่ยืนยันแล้ว" ซึ่ง RLS ของ storage.objects ก็ทำได้เหมือนกัน แต่กฎ sharing ของแอปจริงมักต้องการ lookup ที่ RLS มองไม่เห็น เช่น table grant ที่ชัดเจน)
- **signed-URL อายุสั้นปลอดภัยกว่าแต่สะดวกน้อยกว่า** -- share link ที่หมดอายุใน 1 ชั่วโมง หมายความว่าการ re-share อย่างถูกต้องภายหลังต้องสร้างใหม่ ซึ่งเป็นแรงเสียดทานที่อายุ 10 ปี "แก้" ได้ด้วยการเอาคุณสมบัติด้านความปลอดภัยออกไปทั้งหมด ไม่ใช่ด้วยความสะดวกที่ดีขึ้น

## ความเข้าใจผิดที่พบบ่อย

- **"การเช็ค `bucket_id` ใน storage policy scope การเข้าถึงไปที่ไฟล์ของ user คนนั้น"** พิสูจน์ไว้ข้างบน: มัน scope แค่ไปที่ *bucket* ซึ่ง authenticated user ทุกคนในรีวิวนี้ใช้ร่วมกัน -- การแยกระดับโฟลเดอร์คือการเช็ค `storage.foldername(name)` อย่างชัดเจนที่ policy ที่ AI สร้างไม่เคยเขียนเลย
- **"ถ้า `curl -X OPTIONS` ดูโอเค แปลว่า CORS setup ของ function โอเค"** พิสูจน์ไว้ข้างบนด้วยสอง function ที่ให้ response `OPTIONS` เหมือนกันเป๊ะบน local (Kong ตอบก่อนที่ function ไหนจะรัน) แต่ response POST จริงต่างกันจริง ๆ -- มีแค่ตัวเดียวที่ตั้ง header ที่ preflight ของ browser ต้องการจริง
- **"`verify_jwt = true` (default) ป้องกัน function เสมอก่อน code ของมันเองจะรัน"** พิสูจน์ไว้ข้างบนบน shared stack ที่ไม่เคย restart ตัวนี้เป๊ะ: มันป้องกันสำหรับ function ที่มีอยู่ตอน stack เริ่มทำงานครั้งล่าสุด และไม่ป้องกันเลยตอนนี้ สำหรับ function ที่เพิ่มเข้ามาทีหลัง -- ซึ่งเป็นเหตุผลพอดีที่ function ที่แก้แล้วในรีวิวนี้เช็ค identity ใน code ของตัวเองด้วย
