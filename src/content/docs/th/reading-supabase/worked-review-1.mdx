```sql
language plpgsql

as $$
declare
  v_user_id uuid;
```

## เดินรีวิวทีละจุด

### `user_id text` อ้างอิง `auth.users(id)` — migration รันไม่ได้ตั้งแต่ต้น

`auth.users.id` เป็น `uuid` การประกาศ `wr_members.user_id` เป็น `text` แล้วชี้ foreign key ไปหามัน ถูกปฏิเสธก่อนที่จะมีแถวไหนถูกเขียนเลยด้วยซ้ำ -- พิสูจน์ด้วย `create table` จริง:

```sql
-- @expect-error foreign key constraint "wr_members_user_id_fkey" cannot be implemented
create table public.wr_members (
  tenant_id uuid not null references public.wr_tenants(id),
  user_id text not null references auth.users(id),
  role text not null default 'member',
  primary key (tenant_id, user_id)
);
```

```text
ERROR:  foreign key constraint "wr_members_user_id_fkey" cannot be implemented
DETAIL:  Key columns "user_id" and "id" are of incompatible types: text and uuid.
```

<SpotTheBug lang="sql" code={`user_id text not null references auth.users(id),`}>
นี่คือบั๊กเดียวในรีวิวนี้ที่ไม่มีวันไปถึง production -- Postgres ปฏิเสธการสร้าง constraint ไปเลย ทำให้ `supabase db push`/`--apply` fail ดัง ๆ ใน CI ก่อนที่ RLS policy, RPC หรือ client call ไหน ๆ จะถูกเขียนถึง table นี้ด้วยซ้ำ ใส่ไว้ในรีวิวนี้เพราะมันเป็นนิสัยของ AI ที่พบบ่อยจริง ๆ: ใช้ `text` เป็น default กับทุกคอลัมน์ที่หน้าตาเป็น id แทนที่จะ match กับ primary key type จริงของ table ที่อ้างถึง (`auth.users.id` เป็น `uuid` เสมอ) วิธีแก้คือ `user_id uuid not null references auth.users(id) on delete cascade` -- type ตรงกัน และดูบั๊กถัดไปว่าทำไม `on delete cascade` ถึงสำคัญด้วย
</SpotTheBug>

### ไม่มี `on delete cascade` — ลบ tenant แล้ว fail ทันที

ไม่มี foreign key ไหนใน schema ที่ AI สร้างระบุ `on delete cascade` เลย Postgres เลย default เป็น `no action` พิสูจน์ด้วยการลอง delete tenant ที่มี project อยู่แล้ว:

```sql
-- ran directly against this review's schema, see output below
delete from public.wr_tenants where id = '11111111-1111-1111-1111-111111111111';
```

```text
ERROR:  update or delete on table "wr_tenants" violates foreign key constraint "wr_projects_tenant_id_fkey" on table "wr_projects"
DETAIL:  Key (id)=(11111111-1111-1111-1111-111111111111) is still referenced from table "wr_projects".
```

<SpotTheBug lang="sql" code={`tenant_id uuid not null references public.wr_tenants(id),`}>
"ลบ tenant แล้ว fail ดัง ๆ" ฟังดูเหมือน safety feature จนกว่าจะเป็น code path เดียวที่ support engineer ต้องรีบทำภายใต้ความกดดันเวลา -- และ `on delete cascade` ที่หายไปแบบเดียวกันบน `wr_members.tenant_id`/`user_id` หมายความว่าการลบ user account ตัวเดียว (`auth.admin.deleteUser`) จะทิ้ง membership row ที่กำพร้าไว้เงียบ ๆ แทน ซึ่งอันตรายกว่าในทิศทางตรงข้าม วิธีแก้คือใส่ `on delete cascade` บนทุก foreign key ที่ scope ตาม tenant อย่างตั้งใจ (ลบ tenant แล้ว member กับ project ของมันหายไปด้วย) แทนที่จะปล่อยไว้ที่ default ของ Postgres
</SpotTheBug>

### เช็ค tenant ด้วยการอ่าน `auth.users` ตรง ๆ — policy มองไม่เห็นแถวไหนเลย ไม่ว่าใครก็ตาม

policy `select` ที่ AI สร้างบน `wr_projects` อ่าน `auth.users.raw_user_meta_data` เพื่อหา tenant ของผู้เรียก `auth.users` เป็นของ `supabase_auth_admin`; ทั้ง `anon` และ `authenticated` ไม่ได้รับสิทธิ์อะไรบนมันเลย -- ยืนยันตรง ๆ:

```sql
-- ran directly against this review's schema, see output below
select grantee, privilege_type from information_schema.role_table_grants
where table_schema = 'auth' and table_name = 'users' and grantee in ('anon', 'authenticated', 'service_role');
```



```text
{"code":"42501","details":null,"hint":"Grant the required privileges to the current role with: GRANT SELECT ON auth.users TO authenticated;","message":"permission denied for table users"}
```

<SpotTheBug lang="sql" code={`using (
  tenant_id = (
    select (raw_user_meta_data->>'tenant_id')::uuid
    from auth.users where id = auth.uid()
  )
)`}>
มีปัญหาแยกกันสองอย่างซ้อนอยู่ใน clause เดียว อย่างแรก อันที่พิสูจน์ไว้ข้างบน: `authenticated` ไม่มี grant อะไรเลยบน `auth.users` ในโปรเจกต์ Supabase มาตรฐาน ดังนั้น policy นี้ปฏิเสธ**ทุกคน**ที่เรียก ตลอดเวลา -- ไม่ใช่ "tenant ผิด" แต่คือ `42501` แข็ง ๆ บน query ที่ไม่ทันได้ไปถึงขั้น RLS filter ด้วยซ้ำ อย่างที่สอง ต่อให้ข้ามเรื่อง permission error ไป `raw_user_meta_data` ก็คือสิ่งที่ `supabase.auth.updateUser({ data: { ... } })` เขียนพอดี -- ผู้เรียกตั้ง `tenant_id` ของตัวเองเป็นค่าอะไรก็ได้ตามใจ ดังนั้นแม้แต่เวอร์ชัน `security definer` ของ query เดียวกันนี้ก็จะยอมให้ user self-assign membership เข้า tenant ไหนก็ได้ วิธีแก้คือ table `wr_members` เฉพาะที่เป็น single source of truth ของ tenant membership เช็คผ่าน helper `security definer` (`wr_is_member(tenant_id)`) -- ไม่ใช้ metadata ของ `auth.users` สำหรับการตัดสินใจเรื่อง authorization เด็ดขาด
</SpotTheBug>

### `using (true)` ทั้ง `select` และ `update` ไม่มี `with check` — cross-tenant hijack เต็มรูปแบบ

table `wr_members` ที่ AI สร้าง (ไม่ได้โชว์ด้านบน -- สร้างเหมือน `wr_projects` เป๊ะ `select`/`update` เป็น `using (true)` ทั้งคู่) ทำผิดพลาดแบบเดียวกับที่ catalog บั๊ก 5 อธิบายไว้ แต่ข้าม tenant แทนที่จะข้ามแค่แถวใน table เดียว พิสูจน์ด้วย `PATCH` ข้าม tenant จริง: Alice (owner ของ Acme, tenant `1111…`) ย้าย membership row ของ Bob เองจาก Globex เข้ามาที่ tenant ของตัวเอง เป็น owner:

```bash
# scripts/reading-supabase/worked-review-1/hijack-membership.sh
curl -s -w "\nHTTP=%{http_code}\n" -X PATCH "$SUPABASE_URL/rest/v1/wr_members?user_id=eq.$BOB_ID" \
  -H "apikey: $SUPABASE_ANON_KEY" -H "Authorization: Bearer $ALICE_TOKEN" \
  -H "Content-Type: application/json" -H "Prefer: return=representation" \
  -d '{"tenant_id":"11111111-1111-1111-1111-111111111111","role":"owner"}'
```

```text
[{"tenant_id":"11111111-1111-1111-1111-111111111111","user_id":"911ac6cd-81d5-428a-ab9b-d303f6cb60dd","role":"owner"}]
HTTP=200
```

ยืนยันฝั่ง server ในฐานะ `postgres`: แถวจริงของ Bob (ไม่มี `SQLSTATE` ไม่มี error ตรงไหนใน chain นี้เลย) ตอนนี้มี `tenant_id` เป็น Acme -- Alice ให้สิทธิ์ตัวเอง และเอา Bob ออกจากบริษัทของเขาเอง ด้วย `PATCH` request เดียวที่ไม่ได้พูดถึง tenant ของ Bob เลยแม้แต่คำเดียว

<SpotTheBug lang="sql" code={`create policy wr_members_select on public.wr_members
  for select using (true);

create policy wr_members_update on public.wr_members
  for update using (true);
-- no with check -- reused from using(true), so it is also true`}>
`select using (true)` อ่านได้ว่า "team directory มองเห็นได้ทุกคน" -- เป็นทางเลือกที่ดูสมเหตุสมผล อาจถึงขั้นตั้งใจ แต่พอจับคู่กับ `update using (true)` และไม่มี `with check` มันไม่ใช่เรื่อง visibility อีกต่อไป กลายเป็น "authenticated user คนไหนก็ได้ ใน tenant ไหนก็ได้ เขียน membership row ไหนให้เป็นรูปร่างอะไรก็ได้" -- พิสูจน์ไว้ข้างบนด้วยการ reassign แถวที่ Alice ไม่มีความสัมพันธ์อะไรด้วยเลยจริง ๆ วิธีแก้ด้านล่างไม่ใช่การเขียน `using` clause ให้แคบลงบน `update` -- แต่คือ**ไม่มี update policy ทั่วไปบน table นี้เลย**: การเปลี่ยน role กับ tenant ต้องอยู่หลัง RPC ที่เช็คสิทธิ์ (คู่ที่เหมาะกับ `wr_invite_member` คือ `wr_set_member_role` ที่ gate ด้วยเงื่อนไขว่าผู้เรียกต้องเป็น `owner` อยู่แล้ว) ไม่ใช่ update ทั้ง row แบบเหมารวมเด็ดขาด
</SpotTheBug>

### `security definer` RPC ไม่มี `set search_path = ''` — insert ไปลงที่ table ของผู้โจมตีเงียบ ๆ

`wr_invite_member` เป็น `security definer` ไม่มี `set search_path` owner ของ function (`postgres`) ไม่แตะ schema ไหนนอกจาก `public` เลย -- แต่ `search_path` ของ session **ฝั่งผู้เรียก** ต่างหากที่ resolve การอ้างอิง `wr_members` แบบไม่ qualify schema ของ function ตอนเรียกจริง:

```sql
-- ran directly against this review's schema, see output below
create schema wr_evil;
create table wr_evil.wr_members (tenant_id uuid, user_id uuid, role text);
set search_path to wr_evil, public;
select public.wr_invite_member('11111111-1111-1111-1111-111111111111', 'wr+bob@example.com', 'owner');
select * from wr_evil.wr_members;
select count(*) as real_table_untouched from public.wr_members
  where user_id = '911ac6cd-81d5-428a-ab9b-d303f6cb60dd' and tenant_id = '11111111-1111-1111-1111-111111111111';
```

```text
current_setting
-----------------
wr_evil, public

                                 wr_invite_member
-----------------------------------------------------------------------------------
 (11111111-1111-1111-1111-111111111111,911ac6cd-81d5-428a-ab9b-d303f6cb60dd,owner)
(1 row)

 tenant_id | user_id | role
-----------+---------+------
 1111...   | 911a... | owner

 real_table_untouched
-----------------------
                     0
```

`returning *` ของ function เองรายงานว่าสำเร็จ -- แถวที่หน้าตาถูกต้องเป๊ะ -- ในขณะที่ `insert` จริง (และแถวที่มันคืนมา) ทั้งคู่ resolve ไปที่ `wr_evil.wr_members` ไม่ใช่ table จริง `public.wr_members` ไม่ได้รับการเขียนนี้เลยแม้แต่นิดเดียว

```ts
// src/reading-supabase/worked-review-1/tenant-isolation.ts
// @run
import { createClient } from '@supabase/supabase-js';

const url = process.env.SUPABASE_URL!;
const anonKey = process.env.SUPABASE_ANON_KEY!;
const serviceKey = process.env.SUPABASE_SERVICE_ROLE_KEY!;
const admin = createClient(url, serviceKey);
const stamp = Date.now();

async function makeTenantAndOwner(tenantName: string, email: string) {
  const { data: tenant, error: tErr } = await admin
    .from('wr_tenants')
    .insert({ name: tenantName })
    .select()
    .single();
  if (tErr) throw tErr;

  const { data: created, error: uErr } = await admin.auth.admin.createUser({
    email,
    password: 'wr-Passw0rd!',
    email_confirm: true,
  });
  if (uErr) throw uErr;

  const { error: mErr } = await admin
    .from('wr_members')
    .insert({ tenant_id: tenant.id, user_id: created.user.id, role: 'owner' });
  if (mErr) throw mErr;

  // A fresh, throwaway client for sign-in -- calling signInWithPassword on
  // `admin` itself would swap ITS session to this user's, so every later
  // admin.from(...) call would run as that user (RLS-scoped), not service_role.
  const signInClient = createClient(url, anonKey);
  const { data: signIn, error: sErr } = await signInClient.auth.signInWithPassword({
    email,
    password: 'wr-Passw0rd!',
  });
  if (sErr) throw sErr;

  return { tenant, userId: created.user.id, token: signIn.session!.access_token };
}

async function main() {
  const acme = await makeTenantAndOwner('wr-run-acme', `wr+run-alice-${stamp}@example.com`);
  const globex = await makeTenantAndOwner('wr-run-globex', `wr+run-bob-${stamp}@example.com`);

  await admin.from('wr_projects').insert([
    { tenant_id: acme.tenant.id, name: 'acme-roadmap', created_by: acme.userId },
    { tenant_id: globex.tenant.id, name: 'globex-roadmap', created_by: globex.userId },
  ]);

  const aliceClient = createClient(url, anonKey, {
    global: { headers: { Authorization: `Bearer ${acme.token}` } },
  });
  const bobClient = createClient(url, anonKey, {
    global: { headers: { Authorization: `Bearer ${globex.token}` } },
  });

  const { data: aliceSees } = await aliceClient.from('wr_projects').select('name');
  const { data: bobSees } = await bobClient.from('wr_projects').select('name');

  if (aliceSees?.length !== 1 || aliceSees[0].name !== 'acme-roadmap') {
    throw new Error(`isolation broken: alice saw ${JSON.stringify(aliceSees)}`);
  }
  if (bobSees?.length !== 1 || bobSees[0].name !== 'globex-roadmap') {
    throw new Error(`isolation broken: bob saw ${JSON.stringify(bobSees)}`);
  }
  console.log('alice sees only', aliceSees.map((p) => p.name));
  console.log('bob sees only', bobSees.map((p) => p.name));

  const { error: hijackErr, data: hijackData } = await aliceClient
    .from('wr_members')
    .update({ tenant_id: acme.tenant.id, role: 'owner' })
    .eq('user_id', globex.userId)
    .select();
  if (hijackErr) throw hijackErr;
  if (hijackData && hijackData.length > 0) {
    throw new Error('cross-tenant hijack succeeded -- fix regressed');
  }
  console.log('cross-tenant membership hijack correctly blocked, 0 rows matched');

  await admin.auth.admin.deleteUser(acme.userId);
  await admin.auth.admin.deleteUser(globex.userId);
  await admin.from('wr_tenants').delete().in('id', [acme.tenant.id, globex.tenant.id]);

  console.log('two-tenant isolation test passed');
}

main().catch((err) => {
  console.error(err);
  throw err;
});
```

> **จะช้าลง ไม่ใช่ผิด:**
> 10. `auth.uid()` ไม่ wrap บน policy ของ activity log -- วันนี้ก็ช้าประมาณ 5 เท่าแล้วที่ 50k แถว แย่ลงเรื่อย ๆ ตามจำนวนแถว wrap มันซะ
>
> ยินดี pair ด้วย -- ไม่มีอันไหนต้อง redesign เลย ส่วนใหญ่แค่ย้ายจุดเช็คไปที่ถูกที่

## Mental Model

สามในสิบบั๊กนี้ไม่เคยแสดง error อะไรเลยตอน manual test แบบ happy-path (3, 4, และกรณี `service_role` ของ 7) -- มันดูเหมือนมี access *มากกว่า* ที่ตั้งใจ หรือ access ที่ถูกต้องเป๊ะ จนกว่าจะมีผู้เรียกคนใดคนหนึ่งหรือแถวใดแถวหนึ่งเฉพาะถูกลอง ที่เหลือแบ่งชัดเจนตาม *เวลา* ที่มันโผล่: ตัวหนึ่ง (1) ถูก Postgres เองจับก่อน deploy; สองตัว (2, 10) ถูกต้องแต่ช้าหรือเปราะบางมากกว่าจะผิด; และอีกสี่ตัวที่เหลือ (6, 8, 9 และ trigger ซึ่งคือ 10 ในตาราง) เงียบจนกว่า operation ตรงจุดนั้นจริง ๆ -- การ insert, การ lookup ที่ได้ศูนย์แถว, การลบ tenant, การ signup -- จะไปแตะ path ที่หายไป แอป multi-tenant คูณปัญหานี้ทวีคูณ: ความผิดพลาดแบบไม่มี insert policy ที่เป็นบั๊กเดียวในแอป blog table เดียว กลายเป็นบั๊ก *ต่อ table* และความผิดพลาดแบบใช้ `auth.users` เป็น authorization โผล่ทุกจุดที่เช็คว่า "ผู้เรียกคนนี้อยู่ tenant ไหน" ไม่ใช่แค่ครั้งเดียว

## Trade-offs

- **helper `security definer` อย่าง `wr_is_member()` รวมทุกการเช็ค membership ไว้ที่ function เดียว** -- แลกมาด้วยชั้นอ้อมเพิ่ม: อ่าน `using` clause ของ policy อย่างเดียวไม่บอกเงื่อนไขจริงอีกต่อไป ต้องไปอ่าน helper ด้วย และ RLS ของทุก table ตอนนี้ขึ้นกับ function ตัวนี้ตัวเดียวว่าถูกต้องอยู่เสมอ
- **การตัด update policy ทั่วไปบน `wr_members` ออกทั้งหมด (ส่งการเปลี่ยน role/tenant ผ่าน `wr_invite_member` เท่านั้น) ปิด cross-tenant hijack ได้สมบูรณ์** -- แลกมาด้วยการเสียความสะดวกของ `PATCH` ธรรมดาสำหรับอะไรก็ตามที่เกี่ยวกับ membership แม้แต่ field ที่ไม่มีพิษภัยที่ฟีเจอร์ในอนาคตอาจอยากให้ member แก้เองได้ นั่นต้องมี policy scope แคบเฉพาะของตัวเอง อย่างตั้งใจ ไม่ใช่ใช้ตัวนี้ซ้ำ
- **`on delete cascade` บนทุก foreign key ที่ scope ตาม tenant ทำให้การลบ tenant เป็น operation เดียวจบครบ** -- แลกมาด้วยการไม่มีขั้นตอนยืนยันที่ชั้น database เลย: cascade ตัวเดียวกันที่ทำให้ cleanup ง่าย ก็ทำให้ `delete from wr_tenants` ที่พลาดกู้คืนไม่ได้ถ้าไม่มี backup เร็วพอ ๆ กับที่มันสะดวก

## ความเข้าใจผิดที่พบบ่อย

- **"ถ้า policy compile ผ่านแล้วคืน 200 แปลว่ามันทำตามที่ตั้งใจ"** พิสูจน์ไว้ข้างบนสองครั้งในทิศตรงข้ามกัน: policy ที่อ่าน `auth.users` คืน `403` แข็ง ๆ กับทุกคน (ดูเหมือนพัง แต่จริง ๆ แค่ผิด) ในขณะที่ `using (true)` บน `wr_members` คืน `200` สะอาด ๆ ตอน cross-tenant hijack (ดูเหมือนโอเค แต่จริง ๆ คือบั๊ก)
- **"`security definer` คือทางแก้เวลา RLS มาขวาง"** พิสูจน์ไว้ข้างบน: `security definer` ที่ไม่มี `set search_path = ''` ไม่ได้แค่ข้าม RLS ตามที่ตั้งใจ (งานจริงของมัน) -- มันยังปล่อยให้ session ของ *ผู้เรียก* hijack ว่าชื่อที่ไม่ qualify schema จะ resolve ไปที่ table ไหน เงียบ ๆ ทั้งฝั่งอ่านและ -- โชว์ครั้งแรกในคอร์สนี้ที่นี่ -- ฝั่งเขียนด้วย
- **"trigger บน `auth.users` ถูก scope อยู่แค่ฟีเจอร์ที่มันถูกเพิ่มเข้าไปให้"** พิสูจน์ไว้ข้างบน: มันรันทุกการ signup ทุก user จากทุกฟีเจอร์ -- บั๊ก permission ใน trigger ที่เขียนไว้ให้ "ฟีเจอร์ profile ใหม่" กลายเป็น "ทั้งแอป onboard ใครไม่ได้เลย" นี่คือเหตุผลที่ `security definer` สำคัญกับ trigger บน `auth.users` ยิ่งกว่า RPC ธรรมดาด้วยซ้ำ
