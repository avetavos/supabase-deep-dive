## ไอเดียในหนึ่งประโยค

Supabase คือ **Backend as a Service** แบบ open-source ที่สร้างรอบ database **Postgres** จริงที่ไม่ได้ถูกดัดแปลง — คุณได้ auto-generated API, auth, storage และ realtime มาให้ฟรี แต่แกนกลางยังคงเป็น Postgres ธรรมดาที่ query ด้วย SQL ตรง ๆ ได้ตลอดเวลา

## Postgres มาก่อน service มาทีหลัง

ถ้าคุณสร้าง backend เองตั้งแต่ศูนย์ สุดท้ายคุณจะต้องเขียน authentication service, query API แบบใดแบบหนึ่ง, realtime layer สำหรับ push update สด ๆ และ file storage service เอง — ทั้งหมดนี้วางอยู่บน database ที่คุณเลือก แนวคิดของ Supabase คือให้ทุกอย่างนี้มาสร้างเสร็จแล้ว เชื่อมต่อกันแล้ว และรันอยู่บน **database ที่คุณเป็นเจ้าของเต็มตัวและ query ตรงได้เสมอ**

จุดหลังนี้แหละคือความต่างสำคัญจาก Firebase Firestore ของ Firebase เป็น NoSQL document store แบบ proprietary ไม่มี schema ตายตัว data model และ query ของคุณถูกล็อกไว้กับ shape API เฉพาะของ Firebase ไม่มีทาง escape ไปใช้ SQL ได้เลย Supabase เดิมพันตรงกันข้าม database เป็น Postgres มาตรฐาน ดังนั้น

- คุณต่อด้วย `psql`, Postgres driver ตัวไหนก็ได้ หรือ ORM ที่คุยกับ Postgres ได้
- schema ของคุณคือ table แบบ relational, foreign key และ constraint — ไม่ใช่ document shape ที่ซ่อนอยู่
- ถ้าวันหนึ่งอยากเลิกใช้ Supabase คุณ `pg_dump` database ออกมารันที่ไหนก็ได้ที่รัน Postgres

```sql
-- This is just Postgres. No proprietary query language, no vendor-specific data model.
select id, username, created_at
from public.profiles
where created_at > now() - interval '7 days'
order by created_at desc;
```

## service หลักโดยภาพรวม

หนึ่ง Supabase project คือ Postgres database หนึ่งตัว บวก service ห่อรอบอีกชั้น แต่ละตัวจะมี module ของตัวเองในคอร์สนี้ ตอนนี้เก็บไว้แค่เป็นแผนที่ orientation ยังไม่ต้องลงลึก

- **Postgres database** — ที่เก็บข้อมูลจริง SQL ธรรมดา feature relational เต็มรูปแบบ
- **Auto-generated API** — REST/RPC API ผ่าน **PostgREST** และ GraphQL API ผ่าน **pg_graphql** สร้างขึ้นตรงจาก schema ของคุณ
- **Auth (GoTrue)** — สมัครสมาชิก, sign-in, จัดการ session และ social/SSO provider
- **Storage** — object store แบบ S3-compatible สำหรับไฟล์ มี access policy ของตัวเอง
- **Realtime** — subscribe การเปลี่ยนแปลงใน database หรือใช้ broadcast/presence channel แบบ ephemeral ผ่าน WebSocket
- **Edge Functions** — logic ฝั่ง server ที่เขียนเองด้วย TypeScript รันบน Deno ที่ edge

ทั้งหมดนี้ตั้งค่าได้จาก dashboard **Supabase Studio** (GUI บนเว็บ) หรือจาก **Supabase CLI** ซึ่งคุณจะได้ setup ในบทถัดไป

```typescript
import { createClient } from '@supabase/supabase-js';

const supabase = createClient(
  process.env.SUPABASE_URL!,
  process.env.SUPABASE_ANON_KEY!
);

// Under the hood this is a PostgREST request against the profiles table.
const { data, error } = await supabase
  .from('profiles')
  .select('id, username, created_at')
  .order('created_at', { ascending: false });
```

**Kong คือส่วนที่ diagram ข้างบนย่อทิ้งไป**: ไม่มีใครคุยกับ PostgREST, GoTrue, Realtime หรือ Storage ตรง ๆ เลย — ทุก request ไม่ว่าจะเป็น `supabase-js`, `curl` หรือ Studio UI ต้องผ่าน **Kong** ซึ่งเป็น API gateway ก่อนเสมอ Kong คือตัวที่แปลง "หลาย service แยกกันบนหลาย port" ให้กลายเป็น `API_URL` เดียว (`http://127.0.0.1:55321` บน stack นี้) ที่คุณใช้มาตั้งแต่บทที่แล้ว โดย route request ต่อไปตาม path (`/rest/v1/...` ไป PostgREST, `/auth/v1/...` ไป GoTrue และต่อ ๆ ไป)

## ทำไมไม่สร้างเองไปเลย

ไม่มีอะไรตรงนี้ที่เป็นเวทมนตร์ที่คุณสร้างเองไม่ได้ — PostgREST, GoTrue และตัวอื่น ๆ ล้วนเป็น open-source project ที่ self-host แยกเองได้ สิ่งที่ Supabase ประหยัดให้จริง ๆ คืองาน integration หนึ่ง project, credential ชุดเดียว, dashboard เดียว และ service ที่รู้วิธีคุยกันเองและคุยกับ Postgres instance เดียวกันอยู่แล้ว คุณยังคงต้องเขียน schema, SQL และ access rule เอง — Supabase แค่เอา plumbing รอบ ๆ ออกไปให้

## อ่านโค้ดที่ AI สร้าง

AI assistant ถูกสั่งว่า "add a bio field when creating a profile" แล้วมันไปดึงตัวอย่างสไตล์ Firebase จาก training data มาใช้ ผลลัพธ์คือ:

ERROR:  column "bio" of relation "fnd_profiles_demo" does not exist
LINE 2: insert into public.fnd_profiles_demo (id, username, bio)
\`\`\`

นี่คือประเด็นของหัวข้อ "Postgres มาก่อน" ที่กลายเป็นรูปธรรม: ต่างจาก Firestore ที่การเขียนฟิลด์เพิ่มลง document แค่เพิ่มมันเข้าไปเฉย ๆ Postgres มีชุด column ที่ประกาศตายตัวต่อ table หนึ่งตัว และ `insert` ที่เอ่ยชื่อ column ที่ไม่เคยถูกสร้างจะพังทันทีแทนที่จะรับ shape อะไรก็ได้แบบเงียบ ๆ ทางแก้ไม่ใช่การแก้ query — แต่คือ migration (`alter table public.fnd_profiles_demo add column bio text;` หัวข้อของบทถัดไป) ที่ประกาศ column นั้นก่อน AI assistant ที่ train มาหนักกับตัวอย่าง schemaless database จะมีสัญชาตญาณ "ใส่ field เข้าไปเลย" เป็นนิสัย แต่แกน relational ของ Supabase ปฏิเสธสัญชาตญาณนั้นที่ระดับ database ทุกครั้ง ซึ่งตรงกับ trade-off เรื่อง portability และ validation ที่พูดถึงข้างบนพอดี

## Mental Model

มองทุก service ของ Supabase เป็น **client ของ Postgres database ตัวเดียวกัน** ไม่ใช่ product แยกที่บังเอิญแชร์ dashboard เดียวกัน `.from('profiles').select()` ของ `supabase-js` ไม่ใช่ primitive พิเศษของ Supabase — มันคือ wrapper บาง ๆ ที่ขอให้ PostgREST รัน `select * from public.profiles` ผ่าน HTTP ผ่าน Kong flow สมัครสมาชิกของ Auth ไม่ใช่เวทมนตร์ — มันคือ GoTrue insert row เข้า `auth.users` เมื่อมีอะไรทำงานไม่ตรงกับที่คิด วิธีที่เชื่อถือได้คือถามว่า "สิ่งนี้กลายเป็น SQL อะไรจริง ๆ และ `psql` บอกอะไรถ้ารันตรง ๆ" ซึ่งเป็น debugging path ที่คอร์สนี้วนกลับมาใช้ตลอด

## Trade-offs

- **Postgres core จริงที่ไม่ถูกดัดแปลงให้พลัง SQL เต็มรูปแบบ, extension ทุกตัวใน ecosystem ของ Postgres และทางออกแบบ `pg_dump`** — **แลกมาด้วย schema discipline ที่ schemaless store ไม่ต้องจ่าย**: ทุก column ต้องถูกประกาศก่อนถึงจะเขียนได้ พิสูจน์ข้างบนด้วย insert ที่ AI สร้างที่พังทันทีแทนที่จะ "ใช้ได้เลย"
- **การรวม Auth, Storage, Realtime และ Edge Functions เป็น managed service ประหยัดงาน integration ของการต่อ open-source project แยก 5 ตัวเข้าด้วยกัน** — **แลกมาด้วยพื้นที่ต้องเรียนรู้ที่กว้างขึ้นตั้งแต่แรก**: คอร์สนี้มี 7 module เพราะมีพฤติกรรมของ 7 service ที่แยกกันจริง ๆ ต้องเข้าใจ ไม่ใช่แค่ตัวเดียว
- **การตั้งค่าทุกอย่างผ่าน Studio หรือ CLI ทำให้เปลี่ยนแปลงรายวันเร็ว** — **แลกมาด้วยการต้องมี migration (บทถัดไป) เพื่อให้ทุกอย่าง reviewable และ reproduce ได้** ความตึงเครียดแบบ "แก้ผ่าน GUI vs. ไฟล์ version-controlled" แบบเดียวกับที่โผล่ใน infrastructure-as-code ทุกที่

## ความเข้าใจผิดที่พบบ่อย

- **"Supabase ก็แค่ Firebase ที่ใช้ SQL แทน NoSQL"** ความต่างของ data model ไม่ใช่แค่ผิวเผิน — มันเปลี่ยนว่า write หนึ่งครั้งทำอะไรได้บ้าง พิสูจน์ข้างบนแล้ว: `insert` สไตล์ Firestore ที่มี field ที่ไม่ประกาศไว้พังทันทีใน Postgres แทนที่จะสำเร็จแบบเงียบ ๆ
- **"เพราะมันคือ Postgres service เฉพาะของ Supabase คือ add-on ที่ไม่สนใจก็ได้"** มันคือ process จริงแยกกันพร้อม container ของตัวเอง (พิสูจน์ด้วย `docker ps` output ข้างบน) ไม่ใช่ SQL view บาง ๆ — GoTrue จัดการ session และ JWT จริง, Storage proxy object store แบบ S3-compatible จริง และการเข้าใจพฤติกรรมจริงของแต่ละตัว (ไม่ใช่แค่ "มันคือ Postgres ข้างใน") คือเนื้อหาส่วนใหญ่ของคอร์สนี้
- **"ทุกอย่างผ่าน PostgREST หมด"** พิสูจน์ข้างบนแล้ว: Kong route ตาม path ไปยัง backend service ที่ *ต่างกัน* ถึง 5 ตัว (PostgREST, GoTrue, Realtime, Storage, Edge Runtime) — PostgREST จัดการแค่ `/rest/v1` เท่านั้น
