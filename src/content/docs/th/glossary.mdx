ศัพท์ของ Supabase วางซ้อนกันหลายชั้นบน Postgres ธรรมดา: ชั้น **role กับ grant** (`anon`/`authenticated`/`service_role`, `[api] schemas`) ที่ตัดสินว่า request จะไปถึง table ได้หรือไม่; **Row Level Security** (`using`/`with check`, `permissive`/`restrictive`) ที่ตัดสินว่าเห็น row ไหนได้บ้างเมื่อไปถึงแล้ว; **Auth** (GoTrue, JWT, Auth Hook) ที่ตัดสินว่า request นั้นอ้างว่าเป็นใคร; **Data API** ที่ auto-generate ขึ้นมา (PostgREST, `pg_graphql`, RPC) ที่แปลง schema ให้กลายเป็น endpoint; **Edge Functions** (Deno, โมเดล isolate) สำหรับ logic ที่ไม่ควรอยู่ใน SQL; **Realtime** กับ **Storage** (WAL replication, `realtime.messages`, `storage.objects`) ที่สร้างขึ้นจาก row และ policy ของ Postgres ธรรมดาข้างใต้ทั้งหมด; และเครื่องมือฝั่ง **client กับ production** (supabase-js, Supavisor, migration, branching) ที่ผูกทุกอย่างเข้าด้วยกัน เวลาอ่านบทเรียนแล้วเจอคำที่ไม่คุ้น ให้กลับมาดูที่นี่ — ทุกคำนิยามด้านล่างมาจากบทเรียนที่พิสูจน์กับ Supabase stack จริงที่รันในเครื่องของคอร์สนี้ (Postgres 17.6, PostgREST, GoTrue, Realtime, Storage, Edge Runtime) ไม่ใช่จากความจำ

## A

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| `aal` / `amr` | claim สอง claim ใน JWT ที่บอกว่า session นี้ authenticate มาอย่างไร: `aal` (**A**uthenticator **A**ssurance **L**evel) เป็น `aal1` สำหรับปัจจัยเดียว และ `aal2` เมื่อผ่าน MFA แล้ว; `amr` (**A**uthentication **M**ethods **R**eference) เป็น array บันทึกแต่ละวิธีที่ authenticate พร้อม timestamp (`[{"method":"password","timestamp":...}]`) และจะมี entry ที่สองเพิ่มขึ้นถ้า session ถูกอัปเกรดด้วย MFA ภายหลัง | [Sessions and JWTs](/supabase/th/auth-and-row-level-security/sessions-and-jwts/) |
| admin API (`supabase.auth.admin.*`) | endpoint `/auth/v1/admin/*` ที่ใช้ได้เฉพาะ `service_role` — พิสูจน์แล้วด้วย `403 not_admin` จริงเมื่อเรียกด้วย `anon` key ต่างจาก `signUp()` ตรงที่ `admin.createUser()` ต้องใช้ `service_role` และมีไว้ให้ server ที่เชื่อถือได้สร้าง account *แทน* คนอื่น ไม่ใช่สิ่งที่ควรเปิดให้ browser เรียกได้ | [Authentication Methods](/supabase/th/auth-and-row-level-security/authentication-methods/) |
| `anon` key / `anon` role | public API key ที่ปลอดภัยพอจะใส่ไว้ใน client code ระบุว่า request ที่ยังไม่ authenticate ทุกตัวใน Data API เป็น Postgres role `anon` — ถูก Row Level Security บังคับใช้เหมือน role อื่น ๆ ทุกประการ RLS เองไม่ได้ปฏิบัติต่อมันเป็นพิเศษ ตั้งแต่ปลายปี 2025 โปรเจกต์ใหม่จะออก key นี้เป็น string สั้นลงรูปแบบ `sb_publishable_...` ด้วย ซึ่งทำหน้าที่เดียวกันทุกประการ | [Project Setup and the Supabase CLI](/supabase/th/foundations/project-setup-and-the-supabase-cli/) |
| anonymous sign-in | session จริงที่เป็น role `authenticated` มี row ของตัวเองใน `auth.users` และ `is_anonymous: true` — ไม่เหมือนกับ request ที่ยังไม่ authenticate แบบ role `anon` เพราะ `auth.uid()` คืนค่าจริงให้ ช่วยให้ product เลื่อนกำแพง signup ออกไปได้ แลกกับการมี row ใน `auth.users` ของคนที่อาจไม่เคย convert เลยจนกว่าจะผ่านขั้นตอน `linkIdentity` แบบชัดเจน | [Authentication Methods](/supabase/th/auth-and-row-level-security/authentication-methods/) |
| asymmetric signing (`ES256` vs `HS256`) | ค่า default จริงตั้งแต่ **1 ตุลาคม 2025** สำหรับทุกโปรเจกต์ใหม่ (อ้างจาก [supabase.com/blog/jwt-signing-keys](https://supabase.com/blog/jwt-signing-keys)): access token จริง decode ออกมาเป็น `{"alg":"ES256","kid":"..."}` ตรวจสอบได้ด้วย public key ผ่าน JWKS โดยไม่ต้องมี shared secret เลย ส่วน `anon`/`service_role` API key แบบ static เป็นกลไกเก่าแยกต่างหาก — `{"alg":"HS256"}` ไม่มี `kid` เซ็นด้วย `JWT_SECRET` แบบ shared แบบเก่า และไม่เคยถูกย้ายมาใช้ scheme แบบ per-session ใหม่นี้เลย | [Sessions and JWTs](/supabase/th/auth-and-row-level-security/sessions-and-jwts/) |
| `auth.identities` | table แยกจาก `auth.users` หนึ่ง row ต่อคู่ `(provider, person)` หนึ่งคู่ — คน ๆ เดียวกัน authenticate ได้หลายวิธีในเวลาต่างกัน (email แล้วค่อย GitHub) แต่ละหลักฐานเป็น row ของตัวเองที่ชี้กลับไปที่ row เดียวใน `auth.users` | [Authentication Methods](/supabase/th/auth-and-row-level-security/authentication-methods/) |
| `auth.uid()` / `auth.jwt()` / `auth.role()` | สามฟังก์ชันที่ policy ของ RLS ทุกอันสร้างมาจาก อ่านจาก `request.jwt.claims` ที่ PostgREST ส่งเข้ามาใน session ของ Postgres: `auth.uid()` คืนค่า claim `sub` (เป็น `null` สำหรับ `anon`/`service_role` เพราะทั้งคู่ไม่ใช่ user ที่ signed-in จริง), `auth.role()` มีค่าเสมอ (ทุก request มี claim `role`), และ `auth.jwt()` คืน object claim ที่ decode มาทั้งก้อน — จึงเป็นเหตุผลที่ custom claim อย่าง `tenant_id` ต้องอ่านผ่าน `(auth.jwt() ->> 'tenant_id')` แทนที่จะมีฟังก์ชันเฉพาะ | [Row Level Security Fundamentals](/supabase/th/auth-and-row-level-security/row-level-security-fundamentals/) |
| `auth.users` | table ที่ Auth service (GoTrue) ของ Supabase จัดการให้ — pattern มาตรฐานสำหรับผูกข้อมูลแอปเข้ากับ user คือ table `profiles` ที่ `id` เป็น foreign key ไปยัง `auth.users(id)` | [Tables, Schema, and Migrations](/supabase/th/foundations/tables-schema-and-migrations/) |
| Auth Hook (Customize Access Token Claims) | ฟังก์ชัน Postgres ที่ GoTrue เรียกตอนออก token กำหนดผ่าน `[auth.hook.custom_access_token]` ใน `config.toml` รับ event เป็น `jsonb` (`user_id` + claim ที่ประกอบไว้แล้ว) และคืน `{"claims": {...}}` — เป็นกลไกเดียวที่ใส่ custom claim อย่าง `tenant_id` เข้าไปใน JWT ได้ เพราะ GoTrue เองไม่เคยใส่ให้เอง เรียกได้เฉพาะ `supabase_auth_admin` เท่านั้น และ hook มีผลกับ token ที่ออก **ใหม่** เท่านั้น (sign-in หรือ refresh ครั้งถัดไป) ไม่มีผลย้อนหลังกับ token ที่ออกไปแล้ว | [RLS Patterns and Pitfalls](/supabase/th/auth-and-row-level-security/rls-patterns-and-pitfalls/) |
| `authenticated` role | Postgres role ที่ request ซึ่ง log in แล้วทุกตัวถืออยู่ พร้อม JWT claim (รวม `auth.uid()`) ที่ policy ของ RLS ใช้ได้ — ต่างจาก `anon` ตรงที่ PostgREST execute query ด้วย role ไหน ตาม JWT ของ request นั้น | [The Supabase Architecture](/supabase/th/foundations/the-supabase-architecture/) |
| `auto_expose_new_tables` | ค่าตั้งค่าใน `config.toml` ที่ควบคุมว่า table ใหม่เอี่ยมใน schema `public` จะถูก grant ให้ `anon`/`authenticated`/`service_role` อัตโนมัติโดยไม่ต้อง `grant` เองหรือไม่ พิสูจน์แล้วจริง: ค่า default ของ CLI ที่ scaffold ในเครื่องตกกลับไปเป็น `true` ทั้งที่ฝั่ง hosted กำลัง rollout ค่า `false` เป็น default ใหม่แบบเป็นขั้นตอน — เปิดให้เลือกเองได้ตั้งแต่ 28 เมษายน 2026, เป็น default สำหรับโปรเจกต์ใหม่ตั้งแต่ 30 พฤษภาคม 2026, และบังคับใช้กับโปรเจกต์เดิมทั้งหมดตั้งแต่ 30 ตุลาคม 2026 ([changelog](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)) | [Securing the Data API](/supabase/th/auto-generated-api/securing-the-data-api/) |

## B

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| branch (Supabase branch) | Postgres instance แยกต่างหากจริง ๆ — มี schema, Data API, Auth, และ Storage ของตัวเอง — สร้างขึ้นเพื่อมีอายุเท่ากับ Git branch หรือ pull request ไม่ใช่แค่ feature flag ใน database ที่ใช้ร่วมกัน `supabase branches create --persistent` จะอยู่ต่อไปแม้ push ใหม่เรื่อย ๆ ส่วน `--with-data` จะ clone ข้อมูล production เข้ามาด้วย | [Branching and the Migrations Workflow](/supabase/th/production-and-ecosystem/branching-and-migrations-workflow/) |
| broadcast | ชั้น messaging ชั่วคราวของ Realtime ที่ไม่ขึ้นกับ database เลย: `channel.on('broadcast', ...)` รับ payload JSON อะไรก็ได้ที่ส่งมาด้วย `channel.send()` โดยไม่ต้องต่อสาย table แบบ `postgres_changes` เลย | [Realtime Broadcast and Presence](/supabase/th/realtime-and-storage/realtime-broadcast-and-presence/) |
| `broadcast_changes()` (`realtime.broadcast_changes()`) | ฟังก์ชัน Postgres ที่เรียกจาก trigger เพื่อส่ง payload รูปทรงเดียวกับ `postgres_changes` (`payload.payload.record`) ผ่าน Broadcast แทนเส้นทาง RLS แบบ per-subscriber — พิสูจน์แล้วว่าเขียนด้วย `private = true` เสมอ จึงต้องตั้ง RLS บน `realtime.messages` เหมือน private channel อื่นทุกประการ ไม่มีโหมด broadcast แบบ public ให้เลย | [Realtime Broadcast and Presence](/supabase/th/realtime-and-storage/realtime-broadcast-and-presence/) |
| bucket | container ระดับบนสุดของ Storage เป็นแค่ row ใน `storage.buckets` (`createBucket` เป็น wrapper บาง ๆ ของ `insert` เดียวกันนั้นเอง) ตั้งเป็น `public` ได้ (อ่านผ่าน URL ได้โดยไม่ต้อง auth) หรือ `private` (คุมการเข้าถึงต่อ-request ผ่าน `storage.objects` RLS) | [Storage Buckets and Policies](/supabase/th/realtime-and-storage/storage-buckets-and-policies/) |
| `BYPASSRLS` | attribute ของ Postgres role ที่ `service_role` มี พิสูจน์แล้วว่าข้าม RLS ไปเลยทั้งหมด ไม่ขึ้นกับ policy ใด ๆ — Postgres ไม่แม้แต่จะไปหา policy ที่ตรงกันให้ role ที่มี `BYPASSRLS` เลย ไม่ว่า Data API จะ expose schema นั้นหรือไม่ | [Securing the Data API](/supabase/th/auto-generated-api/securing-the-data-api/) |

## C

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| `cache-control` | HTTP response header ธรรมดา ตั้งค่าต่อ-object ตอน upload ผ่าน option `cacheControl` และถูก echo กลับแบบ **คำต่อคำ** — พิสูจน์แล้วว่า `cacheControl: '3600'` (ตัวอย่างจาก docs เอง) ทำให้ได้ header ตัวจริงที่ไม่ตรงมาตรฐาน `cache-control: 3600` ไม่ใช่ `max-age=3600` โดยไม่มีการตรวจสอบความถูกต้องเลย ทำงานเหมือนกันไม่ว่าจะเปิด image transformation หรือไม่ | [Image Transformations and CDN](/supabase/th/realtime-and-storage/image-transformations-and-cdn/) |
| channel | การเชื่อมต่อ Realtime ที่ตั้งชื่อไว้ (`supabase.channel('name')`) ที่รับ subscription ทั้ง `postgres_changes`, `broadcast`, และ `presence` พร้อมกันได้ — การ authorize ของ private channel และ filter ของ `postgres_changes` ทั้งคู่อิง string channel/topic เป๊ะ ๆ นี่คือเหตุผลที่คอร์สนี้ตั้งชื่อ channel แบบ scope เจาะจงเสมอ (`rt:private-room-1`) | [Realtime Broadcast and Presence](/supabase/th/realtime-and-storage/realtime-broadcast-and-presence/) |
| CI (migrations through CI) | การรัน `supabase db push` เป็นส่วนหนึ่งของ pipeline เดียวกับที่ทดสอบ migration บน preview branch มาแล้ว แทนที่จะให้ใครสักคนวาง SQL ลง production ด้วยมือ — ขั้นตอนที่ทำให้ migration ถูก apply "แบบเดียวกันทุกครั้ง" แทนที่จะ drift ออกจาก version control | [Branching and the Migrations Workflow](/supabase/th/production-and-ecosystem/branching-and-migrations-workflow/) |
| `config.toml` | ไฟล์ตั้งค่า CLI ของโปรเจกต์ในเครื่อง — `[api] schemas`, `auto_expose_new_tables`, `[auth.hook.custom_access_token]`, `[functions.<name>] verify_jwt`, `refresh_token_reuse_interval` และอื่น ๆ — ทุก gate ที่คอร์สนี้พิสูจน์ว่าเป็น error หรือพฤติกรรมจริง ล้วนสืบกลับไปที่ key จริงในไฟล์เดียวนี้ | [Securing the Data API](/supabase/th/auto-generated-api/securing-the-data-api/) |
| CORS preflight | request `OPTIONS` ที่ browser ส่งเองก่อน request ข้าม origin ที่ไม่ธรรมดา ถูกตรวจสอบฝั่ง browser ล้วน ๆ — `curl` ไม่บังคับ CORS เลย ดังนั้น `200` จาก `curl` พิสูจน์แค่ว่า function รันได้ แต่ไม่พิสูจน์อะไรเลยว่า browser client ข้าม origin จริงจะอ่าน response ได้หรือไม่ บน local stack นี้ Kong gateway ของ CLI เองตอบ `OPTIONS` ก่อนที่ branch `req.method === 'OPTIONS'` ของ function เองจะถูกเรียกถึงด้วยซ้ำ — เป็นความแปลกเฉพาะในเครื่อง ส่วน Edge Functions บน hosted คาดหวังให้ function เองเป็นคนตอบ | [Writing and Invoking a Function](/supabase/th/edge-functions/writing-and-invoking-a-function/) |
| `count=exact` / `count=planned` / `count=estimated` | สามโหมดของ `Prefer: count=...` รายงานผ่าน `Content-Range`: `exact` รัน `count(*)` จริง; `planned` อ่านค่าประมาณของ planner (พิสูจน์แล้วได้ `720` บน table 3 row จริงที่ยังไม่ ANALYZE — ไม่ใช่ bug แต่เป็นสิ่งที่ planner เดาจริง ๆ); `estimated` ใช้ค่านับจริงถ้าต่ำกว่า `db-max-rows` แล้วถอยไปใช้ `planned` ถ้าเกิน | [The REST API (PostgREST)](/supabase/th/auto-generated-api/the-rest-api-postgrest/) |
| `createSignedUrl` / signed URL | URL แบบจำกัดเวลาสำหรับ object ใน private bucket ฝัง JWT ที่เซ็นจริงพร้อม claim `exp` ที่ตรวจฝั่ง server — พิสูจน์แล้วว่า request หลังหมดอายุจะได้ error `InvalidJWT` จริง ไม่ใช่แค่ hint ฝั่ง client ที่ยังใช้ได้เงียบ ๆ ต่างจาก `getPublicUrl` ที่สร้าง URL โดยไม่ตรวจสอบอะไรเลย แม้กับ object ใน private bucket | [Storage Buckets and Policies](/supabase/th/realtime-and-storage/storage-buckets-and-policies/) |

## D

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| Data API exposure | ด่านแรกจากสองด่านที่เป็นอิสระต่อกันที่ request ต้องผ่าน: Postgres `grant` (ให้ `anon`/`authenticated`/`service_role`) ตัดสินว่า table หรือ function เข้าถึงผ่าน PostgREST ได้เลยหรือไม่ ประเมินก่อนที่ RLS จะทำงานเสียอีก table ที่มี RLS แบบ permissive แต่ไม่มี grant จะได้ `42501` จริง ไม่ใช่ผลลัพธ์ที่ถูก RLS กรอง — RLS ไม่เคยถูกเรียกดูเลย | [Securing the Data API](/supabase/th/auto-generated-api/securing-the-data-api/) |

| presence | มุมมองใน memory ของ Realtime ที่ sync กันว่าใครกำลังเชื่อมต่อ channel อยู่และล่าสุด `track()` อะไรไว้ผ่าน `presenceState()` — ไม่ได้ผูกกับ table ไหนเลย หายไปทันทีที่ socket disconnect (เป็น event `leave` อัตโนมัติ) ไม่ใช่ record ที่ query ได้แบบถาวรเลย | [Realtime Broadcast and Presence](/supabase/th/realtime-and-storage/realtime-broadcast-and-presence/) |
| `prepare: false` | option ของ driver `postgres` npm ที่ต้องใช้เมื่อผ่าน Supavisor **transaction mode** เพราะ prepared statement ที่สร้างบน backend connection ที่ pool ไว้ตัวหนึ่ง จะไม่มีอยู่บน backend ตัวอื่นที่ query ถัดไปไปตกอยู่ — เป็นวิธีแก้ตามเอกสาร ตรงกับ `?pgbouncer=true` ของ Prisma เอง สำหรับปัญหาความเข้ากันไม่ได้จริงที่ถูกอ้างอิงไว้ | [Edge Functions and the Database](/supabase/th/edge-functions/edge-functions-and-the-database/) |
| private channel | channel (`config: { private: true }`) ที่จำกัดให้เฉพาะ client ที่ authenticated แล้ว โดยส่งการ authorize ผ่าน RLS บน `realtime.messages` แทนที่จะใช้ logic ของ Realtime เอง `realtime.messages` มาพร้อม RLS เปิดใช้งานแต่ **ไม่มี** policy เลย — พิสูจน์แล้วว่าได้ `CHANNEL_ERROR` จริงเมื่อยังไม่มี policy เลย และต้องเรียก `client.realtime.setAuth(token)` เองด้วย ต่างจาก `postgres_changes` ที่ดึง session มาให้อัตโนมัติ | [Realtime Broadcast and Presence](/supabase/th/realtime-and-storage/realtime-broadcast-and-presence/) |
| publication (`supabase_realtime`) | publication ของ Postgres ที่ `alter publication supabase_realtime add table <t>` ต่อสาย table เข้าไป — ขั้นตอน opt-in ขั้นตอนเดียวที่ถ้าไม่ทำ `postgres_changes` จะไม่ streaming อะไรให้ table นั้นเลย ไม่ว่า code ฝั่ง subscribe จะดูถูกต้องแค่ไหน | [Realtime: Postgres Changes](/supabase/th/realtime-and-storage/realtime-postgres-changes/) |
| publishable key / secret key | ตั้งแต่ปลายปี 2025 รูปแบบ key ใหม่กว่า (`sb_publishable_...`/`sb_secret_...`) ที่มาแทน JWT `anon`/`service_role` แบบเดิม — บทบาทความน่าเชื่อถือเหมือนเดิม (publishable ปลอดภัยพอใส่ฝั่ง client, secret bypass RLS และอยู่ฝั่ง server เท่านั้น) เป็น string สั้นลงไม่ใช่ JWT หมุนเวียน (rotate) ได้โดยไม่ downtime key เดิมยังใช้ได้ต่อ | [Project Setup and the Supabase CLI](/supabase/th/foundations/project-setup-and-the-supabase-cli/) |

| session mode (Supavisor, port `5432`) | ให้ client มี connection Postgres เฉพาะตัวตลอดเวลาที่ยังเชื่อมต่ออยู่ — feature parity เต็มรูปแบบรวมถึง prepared statement แลกกับการถือ pool slot ไว้หนึ่งช่องต่อ client ตลอดเวลา จึงไม่ scale ไปสู่ client แบบสั้น ๆ จำนวนมากได้เท่า transaction mode | [Connection Pooling and Supavisor](/supabase/th/production-and-ecosystem/connection-pooling-and-supavisor/) |
| Smart CDN | edge caching สำหรับรูปที่ transform แล้ว มีเฉพาะบน hosted เท่านั้น key ด้วยไฟล์และ transform parameter ที่เจาะจง — ตามเอกสาร ใช้เวลาได้ถึงประมาณ 60 วินาทีให้การ invalidate cache หลัง update แพร่กระจายไปทั่ว และใช้ได้กับ request แบบ signed-URL ด้วย ไม่ใช่แค่ public เท่านั้น (มาจากเอกสาร ไม่สามารถ reproduce บน local Docker stack ที่ไม่มี CDN edge) | [Image Transformations and CDN](/supabase/th/realtime-and-storage/image-transformations-and-cdn/) |
| `stable` / `immutable` / `volatile` | คำสัญญาเรื่อง volatility ของ Postgres function ใช้แค่โดย PostgREST เพื่อตัดสินว่า HTTP verb ไหนปลอดภัย (`stable`/`immutable` ปลดล็อก `GET` ที่ cache ได้) — บังคับใช้ระดับ transaction ไม่ใช่ระดับ route: function ที่ติด label ผิดแล้วพยายามเขียนข้างใน transaction แบบอ่านอย่างเดียวของ `GET` จะพังด้วย error จริง (`25006`) แทนที่จะถูกปฏิเสธตั้งแต่แรกด้วยข้อความสุภาพ | [Database Functions as RPC](/supabase/th/auto-generated-api/database-functions-as-rpc/) |
| Storage (`storage.objects` / `storage.buckets`) | ไม่ใช่ระบบ permission แยกต่างหาก — เป็น API บาง ๆ อยู่หน้า blob store ที่เข้ากันได้กับ S3 สำหรับข้อมูล ไบต์ บวกกับ table จริงของ Postgres, `storage.objects`, สำหรับทุกอย่างเกี่ยวกับมัน (owner, path, bucket, content type) ทุกการตัดสินใจเรื่องการเข้าถึง row เป็น RLS ล้วน ๆ พิสูจน์แล้วด้วย error รูปแบบ `403`/`42501` เดียวกับ RLS ของ table อื่น ๆ | [Storage Buckets and Policies](/supabase/th/realtime-and-storage/storage-buckets-and-policies/) |
| `storage.foldername()` | แยก path ของ object ออกเป็น array ของ segment (`(storage.foldername(name))[1]`) — pattern มาตรฐานคือให้ segment แรกเป็น `auth.uid()` ของ user ที่ upload เอง ดังนั้น policy ที่เทียบมันจะจำกัด user แต่ละคนให้อยู่ในโฟลเดอร์ของตัวเองเท่านั้น พิสูจน์แล้วสด ๆ ว่า user คนหนึ่งเขียนเข้าโฟลเดอร์ของอีกคนถูกปฏิเสธด้วย error RLS รูปแบบเดียวกับ policy ของ table ธรรมดา | [Storage Buckets and Policies](/supabase/th/realtime-and-storage/storage-buckets-and-policies/) |
| Studio | GUI บนเว็บ (Table Editor, SQL Editor, Query Performance, Advisors, Database > Replication) สำหรับตั้งค่าโปรเจกต์โดยไม่ต้องเขียนทุกการเปลี่ยนแปลงเอง — การแก้ schema ผ่าน GUI เป็นของจริงและมีผลทันที แต่มองไม่เห็นใน `git log` จนกว่าจะถูกจับมาเป็น migration ด้วย `db diff` | [Tables, Schema, and Migrations](/supabase/th/foundations/tables-schema-and-migrations/) |
| `@supabase/ssr` | client แบบ cookie ที่เชื่อม browser กับ server code (Server Components, Route Handlers, middleware) ที่ client แบบ `localStorage` ธรรมดาเข้าไม่ถึง — ทั้งสองฝั่งอ่าน/เขียน cookie *เดียวกัน* และการตั้ง plumbing ของ `setAll`/cache-header ผิด เป็นสาเหตุที่เอกสารเองอ้างถึงซ้ำ ๆ ว่าทำให้ user ถูก log out แบบสุ่ม | [Sessions and JWTs](/supabase/th/auth-and-row-level-security/sessions-and-jwts/) |
| Supavisor | connection pooler ของ Supabase อยู่หน้าลิมิต connection พร้อมกันของ Postgres (หลักร้อยต้น ๆ เป็น default) — ตรงกับปัญหาที่ traffic ของ serverless/Edge Function สร้างขึ้นพอดี จากการที่แต่ละตัวพยายามเปิด connection ตรงของตัวเอง | [Connection Pooling and Supavisor](/supabase/th/production-and-ecosystem/connection-pooling-and-supavisor/) |

## T

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| `tenant_id` claim pattern | custom claim (ไม่ใช่ claim default ของ GoTrue — จะเป็น `null` ใน policy ถ้าไม่มี Auth Hook ใส่ให้) ที่ทำให้ policy แบบ multi-tenant เช็คได้จากการอ่าน JWT ครั้งเดียวแทนที่จะ join ทุก query — พิสูจน์แล้วว่าซ่อน row ของ tenant อื่นได้ถูกต้องเมื่อ hook ต่อสายให้แล้ว และมีผลแค่กับ token **ใหม่** เท่านั้น ไม่มีผลย้อนหลัง | [RLS Patterns and Pitfalls](/supabase/th/auth-and-row-level-security/rls-patterns-and-pitfalls/) |
| transaction mode (Supavisor, port `6543`) | ถือ connection ของ Postgres ไว้แค่ระหว่าง transaction เดียวแล้วคืนกลับ pool ทันที — ทำให้ pool เล็ก ๆ รองรับ client แบบสั้น ๆ จำนวนมากได้ (คำแนะนำ default สำหรับ Edge Functions และ serverless) แลกกับการไม่มี feature ระดับ session อย่าง prepared statement | [Connection Pooling and Supavisor](/supabase/th/production-and-ecosystem/connection-pooling-and-supavisor/) |
| TUS | protocol การ upload แบบ resume ที่ Storage implement ไว้ที่ `/storage/v1/upload/resumable` แนะนำให้ใช้เมื่อไฟล์ใหญ่กว่าประมาณ 6MB หรือ connection ไม่เสถียร — พิสูจน์แล้วทีละ chunk ด้วย `curl` ดิบ ๆ: `POST` เพื่อสร้าง, `PATCH` พร้อม `Upload-Offset` เพื่อส่งไบต์, `HEAD` เพื่อยืนยันว่า server มีไบต์อยู่กี่ไบต์แล้วหลังจากจำลอง connection หลุด | [Storage Buckets and Policies](/supabase/th/realtime-and-storage/storage-buckets-and-policies/) |

## U

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| `using` / `with check` | สองด่านแยกกันในสองจังหวะที่ต่างกัน: `using` คุมว่า row ที่ **มีอยู่แล้ว** อันไหนถูก target ได้บ้าง (select/update/delete) ล้มเหลวแบบ **เงียบ** — `delete` ที่ไม่มี policy match จะได้ `DELETE 0` จริง ไม่มี error `with check` คุมว่า row ที่กำลังจะ **กลายเป็น** อะไรได้รับอนุญาตไหม (insert/update) ล้มเหลวแบบ **ดัง** ด้วย `42501` จริง Postgres ใช้ `using` แทน `with check` ถ้าไม่ได้ระบุ `with check` ไว้ ดังนั้น `using` ที่ scope ด้วย ownership ก็ปลอดภัยอยู่แล้วแม้ไม่มี `with check` แยกต่างหากเลย | [Row Level Security Fundamentals](/supabase/th/auth-and-row-level-security/row-level-security-fundamentals/) |

## V

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| `verify_jwt` | ค่าตั้งค่าต่อ-function (`true` เป็น default) ที่ปฏิเสธ request ก่อนที่ code ของ function เองจะรันเลย ถ้าไม่มี JWT ของ Supabase ที่ valid — พิสูจน์แล้วด้วย error body จริงที่มีโครงสร้าง (`UNAUTHORIZED_NO_AUTH_HEADER`, `UNAUTHORIZED_INVALID_JWT_FORMAT`) ต่างจากอะไรก็ตามที่ code ของ function เองจะสร้างได้ ตรวจแค่ว่า token เป็น JWT ที่เซ็นถูกต้องจริง — `anon` key ของโปรเจกต์เองผ่านการตรวจนี้ เพราะตัวมันเองก็เป็น JWT ที่ valid `verify_jwt = false` จำเป็นสำหรับ webhook receiver ที่ไม่มี JWT ของ Supabase ให้ยื่นเลย | [Writing and Invoking a Function](/supabase/th/edge-functions/writing-and-invoking-a-function/) |

## W

| WAL (write-ahead log) | บันทึกทุกการเขียนของ Postgres เองแบบเรียงลำดับและทนทาน เก็บไว้เพื่อ crash recovery และ replication — เป็น stream เดียวกันเป๊ะ ๆ ที่ `postgres_changes` ของ Realtime แตะผ่าน logical replication ซึ่งเป็นเหตุผลที่มันสืบทอดคุณสมบัติของ Postgres เอง (ไม่มีอะไร stream จนกว่า table จะอยู่ใน publication; row เก่าจำกัดแค่ replica identity เว้นแต่จะขยายไว้) | [Realtime: Postgres Changes](/supabase/th/realtime-and-storage/realtime-postgres-changes/) |
