## ใจความสำคัญในหนึ่งประโยค

ทุก request ที่ไปถึง PostgREST authenticate เข้า Postgres ด้วย login role เดียวเท่านั้นคือ `authenticator` ซึ่งจากนั้นจะทำ `SET LOCAL ROLE` จริง ๆ ไปเป็น `anon`, `authenticated`, หรือ `service_role` เฉพาะช่วง transaction นั้น — `session_user` ไม่เคยเปลี่ยน แต่ `current_user` เปลี่ยนทุกครั้ง และการสลับนี้คือกลไกทั้งหมดที่ RLS, grant, `security definer` ในคอร์สนี้ยืนอยู่บน

## พิสูจน์: สาย role จริง จาก `\du`

Local stack ของคอร์สนี้ ถาม query ตรง ๆ (`docker exec -i supabase_db_probe psql -U postgres -c '\du'`):

```text
                                      List of roles
         Role name          |                         Attributes
----------------------------+------------------------------------------------------------
 anon                       | Cannot login
 authenticated              | Cannot login
 authenticator              | No inheritance
 dashboard_user             | Create role, Create DB, Cannot login, Replication
 pgbouncer                  |
 postgres                   | Create role, Create DB, Replication, Bypass RLS
 service_role               | Cannot login, Bypass RLS
 supabase_admin             | Superuser, Create role, Create DB, Replication, Bypass RLS
 supabase_auth_admin        | No inheritance, Create role
 supabase_etl_admin         | Replication, Bypass RLS
 supabase_functions_admin   | No inheritance, Create role
 supabase_privileged_role   | Cannot login
 supabase_read_only_user    | Bypass RLS
 supabase_realtime_admin    | No inheritance, Cannot login
 supabase_replication_admin | Replication
 supabase_storage_admin     | No inheritance, Create role
```

`anon`, `authenticated`, และ `service_role` ทั้งหมดขึ้น **Cannot login** — ไม่มีตัวไหนเลยเป็น role ที่ PostgREST (หรืออะไรก็ตาม) เปิด connection ฐานข้อมูลเป็นตัวมันจริง ๆ `authenticator` ตรงกันข้าม — ขึ้น **No inheritance** แต่ไม่มีข้อความเรื่อง login rights เลย เพราะค่า default (login ได้) คือสิ่งที่น่าสนใจตรงนี้ — มันคือ role เดียวในรายการนี้ที่ *ถูกใช้* เปิด connection จริง สมาชิกภาพยืนยันสายนี้ตรง ๆ (join `pg_auth_members` กลับไปที่ชื่อ role):

```text
    member     |   member_of
---------------+---------------
 authenticator | anon
 authenticator | authenticated
 authenticator | service_role
```

`authenticator` เป็นสมาชิกของทั้งสามตัว และเพราะมัน **No inheritance** (`rolinherit = false` ยืนยันด้านล่าง) การเป็นสมาชิกอย่างเดียวไม่ให้อะไรอัตโนมัติเลย — มันต้อง `SET ROLE` ไปเป็นตัวใดตัวหนึ่งก่อนสิทธิ์ของ role นั้นจะมีผล นี่คือการตัดสินใจออกแบบที่แบกทุกอย่างไว้: ถ้า `authenticator` inherit ได้ ทุก connection จะแบก union ของสิทธิ์ `anon` + `authenticated` + `service_role` (รวมถึง `BYPASSRLS` ของ `service_role`) โดยอัตโนมัติทุก request ไม่ว่า PostgREST จะตั้งใจสลับเข้าไปจริงหรือไม่

```sql
-- sql/int_role_attrs.sql
select rolname, rolinherit, rolcanlogin, rolbypassrls
from pg_roles
where rolname in ('anon','authenticated','service_role','authenticator','postgres')
order by rolname;
```

```text
    rolname    | rolinherit | rolcanlogin | rolbypassrls
----------------+------------+-------------+--------------
 anon           | t          | f           | f
 authenticated  | t          | f           | f
 authenticator  | f          | t           | f
 postgres       | t          | t           | t
 service_role   | t          | f           | t
```

สังเกตความไม่สมมาตรที่ `rolbypassrls` เผยตั้งแต่ต้น — `service_role` มี `BYPASSRLS = true`, `anon` กับ `authenticated` ไม่มี พิสูจน์ว่าสิ่งนี้มีผลกับ query จริงยังไง อยู่ด้านล่าง หลัง RPC

## พิสูจน์: `SET LOCAL ROLE` ต่อ request ของ PostgREST กับ JWT claims จาก RPC

RPC ที่รายงานตรง ๆ ว่า transaction ปัจจุบันเห็นอะไร ใช้กับตารางและ function ที่ namespace เฉพาะของบทนี้ (`security invoker` เป็นค่า default อยู่แล้ว เขียนชัดไว้; `set search_path = ''` ตามกฎของคอร์สนี้เองใน [`database-functions-as-rpc`](/supabase/th/auto-generated-api/database-functions-as-rpc/) เรื่อง schema injection):

```sql
-- supabase/migrations/9501_int_roles_whoami.sql
create table public.int_orders (
  id uuid primary key default gen_random_uuid(),
  note text
);

create or replace function public.int_whoami()
returns table (current_user_ text, session_user_ text, jwt_claims text)
language sql
security invoker
set search_path = ''
as $$
  select
    current_user::text,
    session_user::text,
    current_setting('request.jwt.claims', true);
$$;

grant execute on function public.int_whoami() to anon, authenticated, service_role;
```

เรียก RPC `int_whoami()` ตัวเดียวกันสามครั้ง — ต่อคีย์ครั้งละครั้ง ไม่แก้โค้ดเลย เปลี่ยนแค่ header `Authorization`:

```text
$ curl -s -X POST "$API_URL/rest/v1/rpc/int_whoami" -H "apikey: $ANON_KEY" -H "Authorization: Bearer $ANON_KEY" -H "Content-Type: application/json" -d '{}'
[{"current_user_":"anon","session_user_":"authenticator","jwt_claims":"{\"exp\":1983812996,\"iss\":\"supabase-demo\",\"role\":\"anon\"}"}]

$ curl -s -X POST "$API_URL/rest/v1/rpc/int_whoami" -H "apikey: $ANON_KEY" -H "Authorization: Bearer <a real signed-in user's access_token>" -H "Content-Type: application/json" -d '{}'
[{"current_user_":"authenticated","session_user_":"authenticator","jwt_claims":"{\"aal\":\"aal1\",\"amr\":[{\"method\":\"password\",\"timestamp\":1790667710}],\"app_metadata\":{...},\"aud\":\"authenticated\",\"email\":\"int-roles+demo2@example.com\",\"exp\":1790671310,\"iat\":1790667710,\"is_anonymous\":false,\"iss\":\"http://127.0.0.1:55321/auth/v1\",\"phone\":\"\",\"role\":\"authenticated\",\"session_id\":\"b170be4a-e1ce-4231-8e51-8f283bd94907\",\"sub\":\"3a307b8b-1a47-4671-a197-a2a31af06052\",\"user_metadata\":{...}}"}]

$ curl -s -X POST "$API_URL/rest/v1/rpc/int_whoami" -H "apikey: $SERVICE_ROLE_KEY" -H "Authorization: Bearer $SERVICE_ROLE_KEY" -H "Content-Type: application/json" -d '{}'
[{"current_user_":"service_role","session_user_":"authenticator","jwt_claims":"{\"exp\":1983812996,\"iss\":\"supabase-demo\",\"role\":\"service_role\"}"}]
```

อ่านคอลัมน์ `session_user_` ลงมา: มันขึ้น `authenticator` ในทั้งสามคำตอบ — ทุกอันนี้คือ connection ของ login role *ตัวเดียวกัน* อาจจะเป็น pooled backend ตัวเดียวกันด้วยซ้ำ `current_user_` ต่างหากที่เปลี่ยนจริง ในแต่ละครั้ง ให้ตรงกับ claim `role` ข้างใน JWT ที่ PostgREST ถอดจาก header `Authorization` นี่ไม่ใช่ PostgREST กรอง row เองในโปรเซสของมันแล้วแกล้งทำเป็น database role — มันคือ `SET LOCAL ROLE <role>` จริง ๆ ที่ถูกยิงเข้าไปใน transaction ก่อน query ของคุณจะรัน ยืนยันอิสระจากกันด้วย `pg_stat_activity`:

```text
$ docker exec -i supabase_db_probe psql -U postgres -c "select usename, count(*) from pg_stat_activity where usename is not null group by usename order by 1;"
        usename         | count
------------------------+-------
 authenticator          |     2
 postgres               |    32
 supabase_admin         |    29
 supabase_storage_admin |     1
```

ทุก backend connection ที่ PostgREST เป็นเจ้าของใน `pg_stat_activity` ขึ้น `usename = authenticator` — pool ที่ PostgREST ถืออยู่คือ pool ของ connection `authenticator` ไม่เคยเป็น pool ของ `anon`/`authenticated`/`service_role` `LOCAL` ใน `SET LOCAL ROLE` สำคัญตรงนี้: การสลับ role ถูก scope อยู่แค่ transaction ปัจจุบัน แล้ว revert อัตโนมัติเมื่อมันจบ นี่แหละคือเหตุผลที่ pooled connection ส่งต่อไปให้ request *ถัดไป* ที่ authenticate มาคนละแบบได้เลย โดยไม่ต้อง reset อะไรด้วยมือ

`jwt_claims` ด้านบนยังตอบด้วยว่า `auth.jwt()`, `auth.uid()`, และ `auth.role()` (ใช้ทั่วทั้งโมดูล Auth & RLS) เอาข้อมูลมาจากไหน: `current_setting('request.jwt.claims', true)` คือ session-local GUC ตัวจริงที่ PostgREST เติมด้วย `set_config('request.jwt.claims', <jwt-json>, true)` ก่อน query ของคุณจะรัน — helper function พวกนั้นเป็นแค่ wrapper บาง ๆ รอบ setting ตัวเดียวกันนี้ ไม่ใช่กลไกแยกต่างหาก

## พิสูจน์: `BYPASSRLS` เป็น role attribute ไม่ใช่ grant

`rolbypassrls = t` ของ `service_role` จาก output `\du`/`pg_roles` ด้านบนไม่ใช่แค่ของตกแต่ง เปิด RLS บน `int_orders` โดย **ไม่มี policy เลย** (สถานะ default-deny) แล้ว insert หนึ่งแถวในฐานะ `postgres`:

```sql
-- sql/int_orders_rls_on.sql
alter table public.int_orders enable row level security;
insert into public.int_orders (note) values ('secret-order-1');
```

```text
$ curl -s "$API_URL/rest/v1/int_orders?select=*" -H "apikey: $ANON_KEY" -H "Authorization: Bearer $ANON_KEY"
[]

$ curl -s "$API_URL/rest/v1/int_orders?select=*" -H "apikey: $SERVICE_ROLE_KEY" -H "Authorization: Bearer $SERVICE_ROLE_KEY"
[{"id":"48af4473-246e-4e13-8e8b-5d34fc439c33","note":"secret-order-1"}]
```

ตารางเดียวกัน แถวเดียวกัน ไม่มี policy สักตัว request ของ `anon` เป็นไปตาม default ของ RLS เอง (ไม่มี policy ⇒ ไม่เห็นแถวไหนเลย) และได้ array ว่างกลับมา — ไม่ใช่ error, `int_orders` เป็นตารางที่มองเห็นได้ปกติทุกอย่าง แค่ดู "ว่างเปล่า" จากฝั่ง `anon` request ของ `service_role` ข้าม RLS ไปเลยเพราะ Postgres เช็ก `rolbypassrls` *ก่อน* จะประเมิน policy ใด ๆ เลยด้วยซ้ำ — นี่แหละคือเหตุผลที่โมดูล Edge Functions บอกคุณได้ว่า "ใช้ `service_role` ข้างใน function เท่านั้น ห้ามใช้ฝั่ง client" เป็นกฎ โดยที่ยังไม่ต้องโชว์กลไก: นี่แหละคือกลไกนั้น

## พิสูจน์: ทำไม `int_orders` ถึงมองเห็นได้จาก `anon` ตั้งแต่แรก ก่อนมี grant ใด ๆ

พิสูจน์ `select`/`insert` ด้านบนทำงานได้เพราะ `pg_default_acl` ถาม query ตรง ๆ กับ `public`:

```text
$ docker exec -i supabase_db_probe psql -U postgres -c "select defaclrole::regrole, defaclobjtype, defaclacl from pg_default_acl where defaclnamespace::regnamespace::text='public';"
 defaclrole |  defaclobjtype  |                                                                 defaclacl
------------+-----------------+---------------------------------------------------------------------------------------------------------------------------------------------
 postgres   | r (tables)      | {postgres=arwdDxtm/postgres,anon=arwdDxtm/postgres,authenticated=arwdDxtm/postgres,service_role=arwdDxtm/postgres}
 postgres   | f (functions)   | {postgres=X/postgres,anon=X/postgres,authenticated=X/postgres,service_role=X/postgres}
```

`ALTER DEFAULT PRIVILEGES` สำหรับ role `postgres` ใน schema `public` grant `arwdDxtm` (select/insert/update/delete/... — DML เต็ม) ให้ **ทุกตารางในอนาคต** และ `X` (execute) ให้ **ทุก function ในอนาคต** แก่ `anon`, `authenticated`, และ `service_role` โดยอัตโนมัติอยู่แล้ว — ก่อนที่ migration ของบทนี้จะรัน `grant` แบบชัดเจนด้วยซ้ำ นี่คือกลไกจริงเบื้องหลังพฤติกรรม auto-expose บน local stack ที่ [Securing the Data API](/supabase/th/auto-generated-api/securing-the-data-api/) พิสูจน์จากมุมมองข้างนอกไปแล้ว ("ตารางใหม่เอี่ยมเข้าถึงได้โดยไม่ต้อง config อะไรเลย") — บทนั้นโชว์ *ว่า* มันเกิดขึ้น และวันที่ phased-rollout ที่กำลังเปลี่ยนมันบน hosted project; default ACL entry นี้คือ *เหตุผล* ที่มันเกิดขึ้นวันนี้บนโปรเจกต์ไหนก็ตาม (hosted หรือ local) ที่ยังมีมันอยู่: `postgres` (หรือ `supabase_admin` ซึ่งแบก default ACL ของตัวเองที่เหมือนกันเป๊ะ โชว์อยู่ใน raw query ด้านบน) เป็นเจ้าของ `public` และ pre-authorize สาม role นี้ไว้แล้วสำหรับทุกอย่างที่สร้างที่นั่น

<Callout title="Default ACL นี้แหละคือสิ่งที่ auto_expose_new_tables เอาออก">
การตั้ง `auto_expose_new_tables = false` ใน `config.toml` (พูดถึงใน Securing the Data API) ไม่ได้เปลี่ยน RLS และก็ไม่ได้เปลี่ยน `pg_default_acl` entry นี้ด้วย — tooling ของ Supabase เพิ่มขั้นตอน `revoke` ชัดเจนควบคู่ไปด้วย ทำให้ตาราง *ใหม่* หยุด inherit default grant พวกนี้ ทั้งที่กฎ default ACL เองไม่ได้เปลี่ยน ลอง query `pg_default_acl` เองหลังพลิก setting นั้นแล้วสร้างโปรเจกต์ใหม่ ถ้าอยากดูว่า entry ย้ายไปไหมหรือมี revoke มาซ้อนทับ — พิสูจน์ในบทนี้ด้านบนคือกับ default ที่ยังไม่ได้พลิกของ CLI
</Callout>

## อ่านโค้ดที่ AI เขียน

<SpotTheBug lang="sql" code={`-- AI-generated "make this function safely admin-only"
create or replace function public.int_admin_only_report()
returns setof public.int_orders
language plpgsql
security definer
as $$
begin
  if current_user <> 'service_role' then
    raise exception 'admins only';
  end if;
  return query select * from public.int_orders;
end;
$$;

grant execute on function public.int_admin_only_report() to authenticated;`}>
มีบั๊กสองตัวซ้อนกันอยู่ตรงนี้ เป็นอิสระจากกัน ตัวแรก พิสูจน์ RPC ของบทนี้เองด้านบนโชว์ไปแล้วว่า `current_user` เปลี่ยนตาม role ที่เซ็น JWT ของ request — แต่ function นี้เป็น `security definer` ซึ่งทำให้มันรันด้วยสิทธิ์ของ **เจ้าของ function** (role ที่รัน `create function` ปกติคือ `postgres` บน local) ไม่ใช่ของผู้เรียก `current_user` ข้างใน function นี้คือ `postgres` ทุกครั้งที่เรียก ไม่ว่า `anon`, `authenticated`, หรือ `service_role` จะเป็นคนเรียกก็ตาม — ดังนั้น `current_user <> 'service_role'` เป็น `true` เสมอไม่มีเงื่อนไข exception เลยยิงทุกครั้งสำหรับทุกคนที่เรียก รวมถึง admin ตัวจริงด้วย ตัวที่สอง ถึงจะแก้เช็ก identity แล้ว (เช็ก role จริงของผู้เรียกผ่าน JWT claim หรือถอด `security definer` กลับไปเป็น invoker ซึ่งเป็นค่า default) ก็ยังเหลือช่องโหว่ schema-injection ที่ [บทเรื่อง RPC](/supabase/th/auto-generated-api/database-functions-as-rpc/) ของคอร์สนี้พิสูจน์ไปแล้ว — ไม่มี `set search_path = ''` ดังนั้น function ที่เป็น `security definer` จะ resolve ชื่อที่ไม่ qualify (ในนี้ `public.int_orders` qualify แล้ว แต่ function หน้าตาเดียวกันที่เรียก helper แบบไม่ qualify จะไม่) ตาม `search_path` ของ session ที่เรียกอยู่ตอนนั้น ไม่ใช่ค่าคงที่ วิธีแก้สำหรับบั๊กเฉพาะของบทนี้: เช็ก identity จาก `current_setting('request.jwt.claims', true)::json->>'role'` (พิสูจน์ด้านบนแล้วว่ารายงาน role จริงที่ผู้เรียกสลับเข้าไปได้แม่นยำ) แทนที่จะใช้ `current_user` ซึ่ง `security definer` ทำให้ไร้ความหมายสำหรับจุดประสงค์นี้ไปแล้ว
</SpotTheBug>

## Mental Model

ลองคิดว่า `authenticator` คือ bouncer ที่มีสถานะ "อยู่ในบัญชีเงินเดือน" (login ได้) แค่คนเดียว — bouncer ไม่เคย inherit สิทธิ์ VIP อัตโนมัติเลย (`NOINHERIT`) และสำหรับทุก ๆ request มันเช็ก wristband (claim `role` ใน JWT) แล้วก้าวเข้าไป เฉพาะ transaction นั้น ในโซนที่กั้นไว้ (`anon`/`authenticated`/`service_role`) ตามที่ wristband บอก แล้วก้าวออกมาทันทีที่ transaction จบ `session_user` คือ "bouncer คนไหน" (เหมือนเดิมเสมอ); `current_user` คือ "โซนไหนกำลังมีผลอยู่" (เปลี่ยนทุก request) grant และ RLS policy ถูกเขียนกับโซนที่กั้นไว้ ไม่เคยเขียนกับตัว bouncer

## Trade-offs

| ทางเลือก | ข้อดี | ต้นทุน |
|---|---|---|
| `authenticator` แบบ `NOINHERIT` + `SET LOCAL ROLE` ต่อ request | Login role pooled ตัวเดียว, ใช้ connection ซ้ำข้าม caller ที่ authenticate ต่างกันโดยสิ้นเชิงได้, ความเสี่ยง privilege inherit โดยไม่ตั้งใจเป็นศูนย์ | มี `SET LOCAL ROLE` + `set_config` เพิ่มทุก request (overhead จริงแต่เล็ก — คือราคาของ connection pool เดียวที่รองรับทุก auth state) |
| `BYPASSRLS` ของ `service_role` เป็น role attribute ไม่ใช่ grant ต่อตาราง | คิดง่ายมาก ("คีย์นี้ข้าม RLS จบ") — ไม่มีข้อยกเว้นต่อตารางให้ต้อง audit | มันข้าม RLS ของ **ทุก** ตารางพร้อมกัน; คีย์ `service_role` ที่หลุดไปถึง client คือการ bypass RLS ทั้งหมด ไม่ใช่แค่บาง scope (นี่แหละคือเหตุผลที่ Edge Functions เก็บมันไว้ฝั่ง server เท่านั้น) |
| Default ACL (`ALTER DEFAULT PRIVILEGES`) grant `anon`/`authenticated`/`service_role` ล่วงหน้าบน object ใหม่ | Data API เข้าถึงได้แบบ zero-config ตอน prototype บน local | เป็นกับดักตัวเดียวกับที่ hosted phased rollout (Securing the Data API) กำลังถอยกลับ — ตารางที่ลืมไว้เข้าถึงได้ทันทีที่สร้าง ไม่ว่า RLS จะเปิดหรือไม่ |

## ความเข้าใจผิดที่พบบ่อย

- **"PostgREST เปิด connection ฐานข้อมูลคนละตัวต่อ role"** พิสูจน์ว่าผิดด้านบนด้วย `pg_stat_activity`: ทุก pooled backend มี `usename` เป็น `authenticator` login role เดียว, `SET LOCAL ROLE` ต่อ transaction — ไม่ใช่ pool แยกต่อระดับสิทธิ์
- **"`security definer` ทำให้ function รันเป็น role ที่เรียกมัน แค่มีสิทธิ์เพิ่ม"** พิสูจน์ว่าผิดใน SpotTheBug: `security definer` ทำให้ function รันเป็น **เจ้าของ** ซึ่งตรงข้ามกับผู้เรียกเลย — นี่แหละคือเหตุผลที่การเช็ก `current_user` ข้างในเพื่อ authorization นั้นกลับด้าน
- **"ตารางใหม่ต้องมี grant ชัดเจนก่อน `anon` ถึงจะแตะมันได้"** พิสูจน์ว่าผิดด้านบน: `pg_default_acl` grant DML เต็มให้ `anon`/`authenticated`/`service_role` บนทุกตาราง `public` ใหม่โดยอัตโนมัติอยู่แล้วบน stack นี้ (และ stack ไหนก็ตามที่ยังไม่ได้พลิก) — RLS ต่างหาก ไม่ใช่ grant ที่หายไป คือสิ่งที่กั้นการเข้าถึงจริงในชีวิตประจำวัน
- **"`BYPASSRLS` ข้าม RLS แค่ตารางที่บอก role ไว้ชัดเจนว่าให้ bypass"** พิสูจน์ว่าผิดด้านบน: มันเป็น boolean role attribute (`rolbypassrls`) ที่ไม่มี scope ต่อตารางเลย — เปิดหรือปิด สำหรับทุกตาราง ทุกที่
